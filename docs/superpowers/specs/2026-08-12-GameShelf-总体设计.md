# GameShelf 总体设计与分阶段范围

- 状态：V0.1 范围收缩，待复审
- 日期：2026-08-12
- 最近修订：2026-08-13
- 目标平台：Windows 10 / Windows 11 x64
- 发布形式：PyInstaller onedir 便携版
- 项目定位：本地优先的个人游戏库与存档定位工具

## 1. 背景与目标

GameShelf 用于整理用户电脑上的单机游戏，尤其关注 Galgame、DLsite 同人游戏、RPG Maker 游戏以及其他无法由 Steam 等平台统一管理的作品。

V0.1 首发版必须做到：

1. 扫描用户指定的一个或多个游戏根目录，建立可浏览的本地游戏库。
2. 为每个游戏记录封面、安装路径、主程序和一个或多个存档位置。
3. 安装路径和存档路径可直接在 Windows 资源管理器中打开。
4. 用户可以手动添加、验证、移除和打开一个或多个存档位置。
5. 已实现的静态规则只作为用户主动触发的辅助建议，不成为首发版可用性的前置条件。
6. 所有应用自有的持久化数据位于程序旁边的 `data` 目录，整个目录可直接迁移。
7. 应用默认离线运行，不上传游戏目录、文件列表或存档内容。

## 2. 分阶段范围

### 2.1 V0.1 首发版包含

- 多游戏根目录管理。
- 每个根目录独立配置扫描模式、最大深度、排除项和启用状态。
- 游戏目录发现、主程序推荐和人工覆盖。
- 大封面网格主页与右侧详情抽屉。
- 单张封面：本地选择、剪贴板粘贴、替换和移除。
- 启动游戏、打开安装目录、打开一个或多个存档位置。
- 手动维护多个存档位置，并可验证、打开和移除记录；移除记录不删除存档文件。
- 已实现的静态存档建议，包括引擎提示、Ludusavi 本地清单和自定义清单；它们只在用户明确点击“查找存档”后运行，失败或不可用不得阻塞手动管理。
- 正式与实验性引擎识别器。
- Windows 10 / 11 x64 onedir 便携构建。
- SQLite 数据迁移和迁移前自动备份。

### 2.2 V0.1 不包含

- 翻译、文本提取、游戏资源解包、DLL 注入或作弊修改。
- Steam、Epic、GOG、DLsite 等平台账户或商店 API 对接。
- 在线抓取封面、游戏资料或云同步。
- 引导式启动监控与动态存档检测；计划在 V0.2 实现。
- 孤立存档扫描、反推游戏、存档专用卡片和忽略列表；计划在 V0.3 实现。
- 自动/手动存档备份与恢复；不早于 V0.4 考虑。
- 多封面、裁切编辑器或复杂图片编辑。
- 自动删除、移动或修改游戏和存档文件。
- 对所有未知引擎存档位置作确定性承诺。

## 3. 核心原则

### 3.1 游戏发现不依赖引擎

任何普通 Windows 游戏都可以进入游戏库。引擎识别只是附加能力，不是准入白名单。

### 3.2 三层能力分离

1. **游戏发现**：依据目录结构、PE 可执行文件和通用信号发现游戏。
2. **引擎识别**：依据稳定文件组合、少量文件头、脚本结构和 PE 元数据识别引擎。
3. **存档定位**：V0.1 以人工确认和手动选择为主，仅在用户主动请求且存在可靠规则时给出静态建议；V0.2 再以动态监控补充未知位置。

识别出引擎不等于一定能定位存档。每个结果必须携带置信度与可解释证据。

### 3.3 用户确认优先

人工选择的主程序、引擎和存档位置优先于自动结果。后续扫描不得静默覆盖人工确认值；只有对应文件丢失时才提示重新选择。

### 3.4 只读扫描

扫描和识别不得执行游戏 EXE，不得解包受保护资源，不得写入游戏目录，不得删除或移动用户文件。

### 3.5 渐进交付

V0.1 的完成标准是“稳定好用的游戏书架”，不是“自动找到所有未知存档”。自动建议、动态检测和孤立存档反推分别属于独立能力，任何一层失败都不能影响游戏库浏览、启动或手动存档路径管理。已经实现的后续能力可以保留，但不能扩大 V0.1 的必需范围，也不能在打开详情页时隐式执行耗时扫描。

## 4. 主要用户流程

### 4.1 首次启动

1. 应用检测程序目录是否可写。
2. 创建或打开 `data` 目录和 SQLite 数据库。
3. 用户添加一个或多个游戏根目录。
4. 每个根目录默认使用“直接子目录是一款游戏”模式。
5. 扫描完成后进入封面网格；无封面的游戏显示统一占位图。

如果程序目录不可写，显示明确错误并建议将整个程序目录移动到普通可写位置，不建议以管理员身份长期运行。

### 4.2 日常启动

1. 立即读取 SQLite 缓存并显示已有游戏，不等待磁盘扫描。
2. 后台执行轻量快速扫描。
3. 仅在某个根目录完成一次成功的完整扫描后，更新该根目录下游戏的缺失状态。
4. 用户可随时手动重新扫描、取消扫描或查看错误详情。

### 4.3 游戏详情

点击封面卡片打开右侧详情抽屉，包含：

- 封面和标题。
- 安装状态与识别到的引擎。
- 启动游戏。
- 打开安装目录。
- 存档位置列表，每项可打开。
- 手动添加存档位置；用户可按需点击“查找存档”获取静态辅助建议。
- 修改主程序和高级启动参数。
- 更换或移除封面。

### 4.4 引导式动态存档检测（V0.2）

1. 用户在详情页点击“检测存档”。
2. 应用建立轻量基线并开始监听常用目录。
3. 应用启动游戏并追踪其进程树。
4. 用户进入游戏创建或覆盖一次存档。
5. 用户点击“我刚刚保存了”；该时间点用于提高候选评分。
6. 游戏退出、用户手动停止或到达合理超时时间后，进入短暂静默期并聚合事件。
7. 应用显示候选文件或目录、置信度和证据。
8. 用户确认一个或多个存档位置，或转入扩大扫描/手动选择。

### 4.5 孤儿存档扫描（V0.3）

1. 用户选择扫描范围；默认只扫描常见用户数据目录，可选指定磁盘扩大扫描。
2. 使用 Ludusavi 规则、引擎特征和路径结构发现候选。
3. 结果进入“孤儿存档”页，不自动关联。
4. 用户可以：
   - 关联到已有游戏；
   - 创建没有安装目录的“存档专用卡片”；
   - 修改名称；
   - 忽略候选。
5. 每个候选显示推断的游戏、引擎、置信度和证据。

如果文件只使用 `save01.dat` 等通用名称且不存在目录/内容元数据，应明确标为低置信，不能伪装成确定结果。

## 5. 游戏根目录与扫描语义

### 5.1 多根目录

根目录数量不设业务上限。每个根目录独立保存：

- 显示路径和规范化去重键。
- 是否启用。
- 扫描模式。
- 最大递归深度。
- 排除目录/模式。
- 最近扫描时间、状态和错误。

示例：

```text
D:\文件夹a\游戏a
D:\文件夹a\游戏b
D:\文件夹a\文件夹aa\游戏c
D:\文件夹b\游戏d
```

推荐配置：

- `D:\文件夹a`：递归扫描，最大深度 2。
- `D:\文件夹b`：直接子目录模式。

### 5.2 扫描模式

#### 直接子目录模式

根目录的每个直接子目录默认视为一款候选游戏。适合结构整齐的收藏目录，误判少且速度快。

即使子目录暂时没有找到可启动 EXE，也保留为游戏条目并标记“尚未选择主程序”，而不是丢弃目录。

#### 有限递归模式

递归到用户设置的最大深度。目录一旦被高置信识别为游戏根目录，默认不再把它内部的素材、运行时或插件目录当作独立游戏。

### 5.3 去重与移动

- 同一个安装目录被重叠根目录扫描到时，只保留一条游戏记录。已有记录保持原根目录归属；新记录选择包含它的最具体根目录（路径最长者），保证行为确定。
- 规范化键处理大小写、路径分隔符、尾部空格/点和 `\\?\` 前缀。
- 扫描避免跟随会形成循环的符号链接或目录联接。
- 游戏疑似移动时，依据相对主程序、PE 元数据、引擎证据和轻量指纹提出匹配建议，由用户确认是否复用原记录。
- 根目录脱机、权限失败或扫描取消时，不把其游戏标为缺失。
- 整个 GameShelf 目录迁移到另一台电脑后，如果外部游戏根目录盘符发生变化，原根目录显示“不可访问”，用户可以把它重新映射到新路径；游戏的相对目录和人工设置继续复用。

## 6. 主程序推荐与启动

### 6.1 推荐规则

正向信号：

- 位于游戏根目录或符合引擎启动结构。
- 文件产品名、描述或图标与目录/游戏标题接近。
- 周围存在匹配的引擎资源。
- 不是通用运行库安装器。

负向信号：

- `uninstall`、`unins`、`setup`、`install`、`updater`、`update`。
- crash reporter、redist、runtime、VC 安装器。
- 编辑器、打包器或开发辅助程序。
- 明显仅用于配置的程序；此类程序可列为辅助工具，但不默认启动。

扫描只读取元数据，绝不试运行候选 EXE。

### 6.2 启动配置

每个游戏支持：

- 主程序相对路径。
- 工作目录相对路径。
- 命令行参数。
- 可选环境变量。
- 检测到的 x86/x64 架构。

启动使用参数数组和 `shell=False`，不拼接未经处理的 shell 命令。高级字段默认折叠，普通用户无需配置。

不纳入 MTool 的注入、Hook、改路径或翻译专用启动参数。

### 7.3 识别实现

识别器采用插件式接口和数据规则：

```text
EngineDetector
  id
  variants
  cheap_probe(directory)
  inspect(directory, executable)
  save_hints(metadata)
```

扫描分两阶段：

1. 便宜探测：文件名、目录结构和扩展名组合。
2. 深入探测：仅对候选读取少量文件头、脚本配置或 PE 版本资源。

结果包含：

- `engine_id`
- `engine_variant`
- `confidence`
- `evidence[]`
- 规则版本

用户可以人工修正；人工值与自动值分开保存，以便规则升级后仍能展示新建议而不覆盖用户决定。界面显示当前采用值，并可展开查看最新自动建议。

### 7.4 MTool 的使用边界

MTool 官网的公开支持列表用于核对需要覆盖的引擎名称。本地旧版目录只用于观察公开可见的数据文件组织和文件名，不反编译、不反汇编、不绕过保护，也不复制其私有代码、Hook 或资源。

GameShelf 的识别规则依据引擎官方结构、公开文档、许可兼容的开源资料和自行编写的测试样本独立实现。

## 8. 存档定位设计

本章描述长期能力边界。V0.1 只要求手动位置管理稳定可用；静态规则是可选的按需辅助。动态监听属于 V0.2，删除本体后的孤立存档反推属于 V0.3。

### 8.1 存档来源

一个游戏可以有多个存档位置，每项记录来源：

- `manual`：用户选择。
- `dynamic`：启动监控确认。
- `ludusavi`：精确清单规则。
- `engine`：引擎通用提示。
- `legacy_scan`：孤儿/扩大扫描发现。

人工确认的路径优先级最高。

### 8.2 路径类型

- 目录。
- 单个文件或文件模式。
- 注册表键；主要用于 Unity PlayerPrefs 等少数情况，界面明确标为“注册表偏好数据”。

数据库优先保存可迁移模板，例如：

```text
<winAppData>\RenPy\project-name
<winLocalAppData>\GameName
<winLocalAppDataLow>\Company\Product
<winDocuments>\My Games\GameName
<game>\save
```

同时保存最近一次展开后的显示路径和规范化键。

### 8.3 静态规则

1. 只有用户明确点击“查找存档”后，才运行静态匹配；打开游戏详情或存档区域不得自动解析规则清单。
2. 优先运行轻量的引擎提示，再使用 Ludusavi 本地快照和 `data/manifests/custom` 中的自定义清单补充建议。
3. 清单只在用户点击更新时联网更新，更新前后记录版本并可回退。
4. 查看清单版本或完整性状态时只执行快速元数据和摘要校验，不完整解析大型 YAML；完整解析仅发生在匹配、首次实际使用或下载验证阶段。
5. 引擎规则只在足够稳定时提供路径提示，不把资源格式识别器等同于存档规则。
6. 下载的规则先校验 schema、版本和完整性，再原子替换当前快照；失败时继续使用旧版本。
7. 所有自动结果都是待确认建议；静态来源不可用时，手动添加、验证和打开存档位置仍必须正常工作。

### 8.4 动态监听范围（V0.2）

默认监听：

- 游戏安装目录。
- Documents。
- Saved Games。
- AppData/Roaming。
- AppData/Local。
- AppData/LocalLow。
- ProgramData 中当前用户可访问部分。
- 用户添加的自定义位置。
- 已确认存档位置的父目录。

无法访问的目录被跳过并列入结果摘要，不要求管理员权限。

### 8.5 动态候选评分（V0.2）

加分：

- 在“我刚刚保存了”时间点附近创建或修改。
- 多次保存时重复变化。
- 位于游戏安装目录、已识别的公司/产品目录或常见存档目录附近。
- 文件名/扩展名符合存档习惯。
- 路径、公司名、产品名或引擎元数据与游戏匹配。

降分或过滤：

- 日志、缓存、临时文件。
- shader cache、GPU cache。
- telemetry、崩溃报告和转储。
- 浏览器通用缓存。
- 与本次游戏无关的高频后台程序写入。

事件按路径合并，不因同一文件被连续写入而重复显示。

监听缓冲区溢出时，对监控时间窗执行回退式元数据扫描，并在结果中标记“事件可能不完整”。

普通目录变化 API 通常不提供可靠的写入进程 PID，因此 GameShelf 不声称某个文件“确定由游戏进程写入”。进程树只用于启动、退出和检测会话生命周期。注册表也不做全局实时监听，只对引擎规则给出的目标键在会话前后做快照比较。

### 8.6 Unity 特殊处理

- 通过 `UnityPlayer.dll`、与 EXE 对应的 `*_Data`、`globalgamemanagers` 等组合识别。
- Windows Player 的常见持久化目录为 `LocalLow/<Company>/<Product>`。
- Company/Product 优先来自可可靠读取的构建/PE 元数据；不可靠时仅进行名称相似度候选匹配。
- 对足够明确的游戏检查对应 PlayerPrefs 注册表键。
- Unity 游戏可以自定义任意保存方式，因此所有自动结果仍需置信度和用户确认。

### 8.7 删除本体后的反推限制（V0.3）

- Ren'Py、Unity 等常在用户目录留下引擎/项目结构，反推成功率相对较高。
- RPG Maker、WOLF、NScripter 等常把存档放在游戏目录；如果整个目录已删除，存档可能一同消失。
- 厂商定制引擎可能只留下无语义文件名，无法可靠确定游戏名。
- 低置信候选不得自动绑定或自动改名。

## 9. 封面处理

### 9.1 输入

- 本地 JPEG、PNG、WebP、BMP 等常见位图。
- Windows 剪贴板中的截图。

### 9.2 非破坏性处理

1. 将输入复制/编码到 `data/covers/original/<game_uuid>.<ext>`；JPEG/PNG/WebP 保持合适格式，BMP 等格式解码后规范化为 PNG，并处理 EXIF 方向。
2. 生成书架使用的 2:3 WebP 缩略图到 `data/covers/thumbs/<game_uuid>.webp`。
3. 书架默认居中裁切，详情页完整显示原图。
4. 原图足以支持以后增加取景位置调整，不在首版实现编辑器。
5. 替换时先写入临时文件并校验，再更新数据库；数据库切换成功后才删除应用管理的旧副本。
6. 永不删除用户最初选择的源图片。

解码时限制异常尺寸和资源使用，避免损坏图片或超大图片拖垮界面。

## 10. 界面与状态

### 10.1 主页

- 默认大封面网格。
- 顶部提供搜索、状态筛选、引擎筛选、添加根目录、扫描入口。
- 卡片展示标题、安装/缺失/仅存档状态和必要的轻量标记。
- 不在封面上堆叠大量路径文字。

### 10.2 详情抽屉

- 保持主页上下文，不强制跳转新页面。
- 所有路径操作给出清晰标签。
- 多个存档位置分别显示来源和置信度。
- 自动建议与已确认值采用不同视觉状态。

### 10.3 专用页面/弹窗

- 根目录与扫描设置。
- 扫描进度与错误详情。
- 引导式存档检测向导（V0.2）。
- 孤儿存档审阅（V0.3）。
- 应用设置与规则版本。

### 10.4 错误呈现

界面显示可行动的简短信息，例如“根目录暂时无法访问，已有游戏状态未改变”；日志保存底层错误和堆栈。

任务错误不得令主界面不可用。V0.1 的扫描、封面处理和规则更新支持取消或安全失败；V0.2 的动态检测遵循相同原则。

## 11. 技术架构

### 11.1 技术栈

- 前端：Vue 3 + TypeScript + Vite。
- 桌面壳：pywebview，Windows 使用 WebView2。
- 后端/核心：Python。
- 数据库：SQLite。
- 打包：PyInstaller onedir x64。

### 11.2 技术路线选择与权衡

选择 Vue 3 + TypeScript + pywebview + Python 的原因：

- 游戏库是封面、筛选、抽屉和向导较多的视觉界面，Web 前端更适合快速迭代。
- Python 对 Windows 文件系统扫描、SQLite、图片处理、规则解析和进程管理有成熟库。
- pywebview 允许使用系统 WebView2，主体体积和内存成本通常低于完整 Electron。
- 前后端通过小型白名单桥接隔离，避免引入本地通用 HTTP 业务 API。

已评估但未选择：

- **Python + PySide6/Qt Widgets**：单语言后端集成直接，但封面库和复杂响应式交互的开发效率较低，现代视觉细节需要更多定制。
- **.NET/WPF**：Windows 原生集成优秀，但会把核心实现迁移到另一套技术栈，不符合本次已确认的 Python 路线。
- **Tauri**：产物较轻，但需要 Rust 命令层；文件扫描与规则核心仍需重写或增加 Python sidecar，首版复杂度更高。
- **Electron**：前端生态最直接，但运行时体积与资源占用更高，不符合轻量便携目标。

固定版 WebView2 会增大完整便携包体积，但换取 Windows 10 干净环境无需安装依赖；这是 V0.1 完整包接受的权衡。

### 11.3 边界

```text
Vue UI
  ├─ LibraryGrid
  ├─ GameDetailDrawer
  ├─ ScanRootWizard
  ├─ SaveDetectionWizard          # V0.2
  └─ OrphanSaveReview             # V0.3
          │
          ▼ typed pywebview bridge
Python application services
  ├─ GameLibraryService
  ├─ ScanService
  ├─ LaunchService
  ├─ SaveDetectionService         # V0.2
  ├─ OrphanSaveService            # V0.3
  ├─ EngineDetectionService
  └─ CoverService
          │
          ▼
Infrastructure
  ├─ SQLite repositories
  ├─ Windows filesystem/process/registry adapters
  ├─ Engine rule provider
  └─ Ludusavi manifest provider
```

不使用 Flask/FastAPI 承载业务 API。前端只能调用白名单 pywebview bridge 方法；耗时任务返回任务 ID，通过事件或轮询读取进度和结果。

### 11.4 并发

- pywebview 桥接调用可能来自不同线程，业务层不直接共享可变 SQLite 连接。
- SQLite 写操作由单一写入队列/工作线程串行化。
- 读取使用短生命周期连接或受控连接池。
- 磁盘扫描、封面处理和规则扫描在后台可取消任务中运行。
- 前端不假定结果按调用顺序返回，所有任务使用 UUID。

### 11.5 本地资源服务

- Vue 构建产物随程序打包。
- 封面等本地资源通过受控的本地只读资源端点或后端读取，不允许任意 `file://` 路径访问。
- 会话使用 pywebview 提供的唯一 token；资源请求限制为允许的资源 ID。
- 发布模式关闭调试工具。

## 12. 便携目录结构

```text
GameShelf/
├─ GameShelf.exe
├─ _internal/                 # PyInstaller onedir 运行文件
├─ runtime/                   # 可选固定版 WebView2 Runtime
└─ data/
   ├─ library.db
   ├─ config.json
   ├─ covers/
   │  ├─ original/
   │  └─ thumbs/
   ├─ manifests/
   │  ├─ ludusavi/
   │  └─ custom/
   ├─ webview/
   ├─ db_backups/
   ├─ logs/
   └─ temp/
```

所有 GameShelf 自有持久化数据必须位于 `data`。

- pywebview 显式设置 `storage_path=data/webview`，避免默认写入 `%APPDATA%\pywebview`。
- 临时文件优先写入 `data/temp` 并在异常退出后的下次启动清理。
- Windows/WebView2 本身的系统级运行时更新或操作系统日志不属于应用库数据，但不得将用户配置依赖于这些位置。
- 应用关闭后复制整个目录到另一位置，应能保留数据库、封面、规则与设置；运行中复制不保证获得一致数据库快照。

为保证未安装 WebView2 的 Windows 10 也可直接运行，正式完整便携包优先携带可再分发的固定版 WebView2 Runtime，并显式设置运行时路径；后续可额外发布依赖系统 Runtime 的精简包。

## 14. 数据一致性与迁移

- 启用 SQLite 外键。
- 运行时使用 WAL，并由单写入队列串行化写事务；数据库备份或便携迁移前执行 checkpoint。
- 所有多表修改使用事务。
- 文件与数据库联合修改使用“先生成并验证文件，再提交数据库，最后清理旧文件”的补偿式流程。
- 数据库 schema 使用递增版本号。
- 每次迁移前先 checkpoint，并复制到 `data/db_backups`。
- 只保留有限数量的自动数据库备份，清理策略不会触碰存档备份或用户文件。
- 应用启动发现迁移失败时，以只读方式保留旧数据库并提供明确恢复说明，不继续写入。

## 15. 安全与隐私

- 默认完全离线。
- 除非用户主动更新 Ludusavi 清单，不发起联网请求。
- 不上传文件名、游戏标题、安装路径、存档路径或存档内容。
- 前端桥接只暴露按业务用途划分的白名单方法。
- 后端验证前端传入的游戏 ID、根目录 ID 和资源 ID，不提供任意 shell 执行接口。
- 打开目录和启动游戏使用 Windows API/安全参数调用。
- 扫描限制并发和文件头读取大小。
- 对符号链接、目录联接、权限错误和长路径做防护。
- 日志默认不记录存档内容；路径可在导出诊断时选择脱敏。

## 16. 性能与可靠性

- 首屏只读数据库，目标是在普通游戏库规模下快速出现缓存内容。
- 根目录扫描采用分批提交和进度事件，避免一次构造巨大内存列表。
- 便宜引擎探测优先，只有候选目录才读取文件头。
- 目录变化监听只在引导式检测会话期间启用，不常驻监视整个系统。
- 文件事件聚合并限制候选数量。
- 取消任务应停止继续枚举，并保留上次成功扫描状态。
- 后台任务异常不得导致 UI 线程或数据库写入线程崩溃。

## 21. V0.1 首发版验收标准

1. 可添加至少两个根目录并分别设置直接子目录/有限递归扫描。
2. 对示例嵌套结构能找到游戏 a、b、c、d，且不会因重叠根重复。
3. 根目录离线或权限失败时，已有游戏不会被误标为缺失。
4. 未知引擎的普通 Windows 游戏仍能添加、显示和启动。
5. 正式引擎识别器显示置信度和证据，人工覆盖后不会被扫描改回。
6. 每个游戏可以配置一个主程序和多个存档位置。
7. 安装目录和存档目录均可点击打开。
8. 封面可从本地选择或剪贴板粘贴，源文件删除后应用仍正常显示。
9. 用户可以手动添加、验证、打开和移除存档位置，移除记录不会删除存档文件。
10. 静态建议只在用户明确点击后运行；Ludusavi 或其他规则不可用时，游戏详情和手动存档管理仍可立即使用。
11. 查看 Ludusavi 清单状态不完整解析大型 YAML，界面不会长期停留在“正在读取清单状态”。
12. 所有应用自有持久化数据都位于 `data`，复制整个目录后仍能运行并保留数据。
13. 应用不因单个根目录、图片、规则或扫描任务失败而失去已有游戏库。
