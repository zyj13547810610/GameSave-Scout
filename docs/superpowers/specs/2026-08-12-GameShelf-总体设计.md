# GameShelf 总体设计

> 文档性质：项目最高层的当前产品与技术设计；最后更新：2026-08-25。V0.1 当前范围、V0.2.0 自定义分组、V0.2.1 批量存档发现、V0.3.0 内置规则扩展和 V0.3.1 自定义规则编辑器均已完成，V0.3.1 真实窗口人工验收已通过；V0.3.2 第二批引擎与存档规则设计已确认并待实施。V0.2.1 仍是最新本地双版本便携候选，V0.3.x 尚未构建便携包。模块细节以 01～07 固定文档为准，版本优先级以开发路线图为准。

## 1. 产品定位

GameShelf 是面向 Windows 10/11 x64 的本地优先、便携式个人游戏库与存档位置管理器，主要适用于：

- 不通过统一平台管理的单机游戏。
- Galgame、DLsite 作品及厂商自定义引擎游戏。
- RPG Maker、WOLF RPG Editor、Ren'Py、Unity 等作品。
- 用户希望自行维护封面、启动方式和存档路径的游戏。

程序不要求连接 Steam、Epic、GOG 等平台。用户指定一个或多个本地根目录，GameShelf 扫描文件夹建立游戏库。

## 2. 用户目标

用户打开应用后可以：

- 浏览电脑上的游戏封面和安装状态。
- 搜索并按状态、引擎或自定义分组筛选。
- 创建自定义分组，并为一个游戏维护多个分组归属。
- 打开安装目录或直接启动游戏。
- 修正标题、主程序、启动参数和引擎。
- 从本地选择封面或粘贴截图。
- 为每个游戏记录一个或多个存档目录、文件、通配符或注册表位置。
- 在需要时使用本地规则辅助查找存档。
- 主动启动一次引导式检测，在游戏内保存后审核新增或修改位置。
- 把整个 GameShelf 目录复制到其他本地位置继续使用。

### V0.1 首发版

- 多根目录、直接子目录或递归游戏扫描，以及可关闭的启动快速核验、手动完整扫描、持久分析缓存和 1～4 全局共享分析并发。
- 游戏库、标题与版本号分离、封面、搜索、状态/引擎筛选、主页批量管理和详情抽屉。

- 静态引擎识别、证据展示、歧义处理和手动覆盖。

### V0.2

- 已实现用户创建、重命名和删除扁平自定义分组；一个游戏可属于多个分组。详情中的分组区位于存档位置下方并默认折叠，主页批量管理按钮在原位置切换进入和退出状态。

## 4. 核心产品原则

### 4.1 游戏发现与引擎识别分离

扫描器判断“这是一个需要展示的游戏目录”，引擎识别器判断“它可能使用什么引擎”。未知引擎不影响入库、封面和启动。

### 4.2 自动检测与用户采用值分离

标题、主 EXE 和引擎都区分自动检测值与用户采用值。重新扫描可以更新自动值，但不能覆盖有效手动选择。

### 4.3 所有建议先审核

移动游戏、静态存档位置、引导式检测候选和孤立存档关系都只能提出建议。没有用户确认，不自动合并游戏、写入正式存档位置或建立关联。

### 4.4 默认只读和最小权限

扫描、引擎识别和存档查找只读取批准范围内的路径和受限元数据。程序不执行发现阶段的 EXE、不解包商业资源、不请求管理员权限、不静默扫描所有磁盘。

### 4.5 本地优先与便携

应用自身数据位于程序旁 `data`。除用户明确点击 Ludusavi 更新等联网操作外，日常浏览、扫描、启动和手动管理均可离线工作。

## 5. 技术架构

```text
Vue 3 / TypeScript / Pinia
          │ 类型化桥接 API
          ▼
pywebview 桌面窗口
          │
          ▼
Python 应用服务
├─ 游戏库与扫描
├─ 启动与 Windows 适配器
├─ 封面处理
├─ 共享规则文件仓储、不可变快照、校验与诊断（V0.3）
├─ 引擎检测
├─ 存档位置与静态建议
├─ 引导式存档检测
├─ 批量存档发现与人工审核（V0.2）
├─ 自定义游戏分组（V0.2）
├─ 后台任务
└─ SQLite 串行写入
          │
          ├─ data/library.db
          ├─ data/covers
          ├─ resources/rules（只读内置规则与 Ludusavi 随包快照）
          ├─ data/rules/user（V0.3.1 用户规则）
          ├─ data/rules/ludusavi（用户主动更新后的活动快照）
          ├─ data/rules/settings.json（内置规则本地启停）
          └─ 127.0.0.1 只读 UI/封面服务
```

前端负责显示、交互和短生命周期视图状态。Python 负责所有文件系统、注册表、进程、数据库、图片和规则操作。前端不能直接访问任意本地文件路径。

## 6. 主要用户流程

### 6.1 首次启动

1. 程序创建并验证 `data`。
2. 初始化数据库和本地资源服务。
3. 用户添加一个或多个游戏根目录。
4. 用户选择直接子目录或递归扫描，并设置排除项。
5. 扫描完成后游戏卡片进入主界面。

### 6.2 日常启动

1. 立即从 SQLite 显示缓存游戏库。
2. 对已启用根目录启动后台快速核验。
3. 盘符离线、任务取消或扫描失败时保留原状态。
4. 用户需要重新发现目录时手动执行完整扫描。

### 6.3 游戏详情

用户点击卡片后在右侧抽屉中处理封面、引擎、存档位置和启动设置。主页面被半透明遮罩覆盖并锁定滚动，抽屉独立滚动。

### 6.4 存档位置

用户可以直接手动添加。静态规则只有点击“查找存档”后才运行；候选按可信度分组，接受后才保存。V0.1 还提供用户主动开始的引导式检测会话：程序启动指定游戏，结合“我刚刚保存了”时间标记汇总受限范围内的文件变化，仍由用户审核后保存。

V0.2 增加独立“批量存档”一级页面。批量扫描只在用户点击后运行，先检查规则明确位置，再对标准和自定义目录进行受限发现；结果包括已安装、本体失效、未关联和已记录位置。完整 Ludusavi 清单用于本地反向路径识别，不要求游戏已经存在于 GameShelf。所有建议都显示证据并经过人工确认，未关联结果可以关联现有游戏、创建 `save_only` 卡片或忽略；完全无法识别名称时标题才显示“未知游戏”。

### 6.5 自定义分组

V0.2 允许用户建立扁平自定义分组。一个游戏可同时属于多个分组；用户既可在详情抽屉调整单个游戏，也可在主页批量管理中把最多 500 个游戏加入或移出一个分组。主页分组筛选为单选，提供“全部分组”“未分组”和具体分组，并与搜索、状态和引擎筛选取交集。

分组只有名称，不在第一版加入父子层级、颜色、图标或自动分类规则。删除分组只删除关系，不删除游戏；分组适用于 `installed`、`missing` 和批量存档流程产生的 `save_only` 记录。

## 7. 游戏扫描模型

支持任意多个根目录：

- `children`：每个可访问直接子目录作为候选。
- `recursive`：继续向下寻找包含潜在游戏 EXE 的目录，找到后停止进入其后代。

辅助 EXE 不会阻断递归。路径按 Windows 语义规范化，重叠根目录由最具体的启用根目录拥有。完整扫描成功后才把未观察到的游戏标记为 `missing`。

当前扫描模型会保留失效游戏，便于目录离线、搬盘和未来存档反推；单条与批量删除/忽略流程已经实现。快速核验只检查已知记录，完整扫描负责发现新游戏并在成功后核对失效状态；未变化的主程序与引擎分析可复用持久缓存。

## 8. 游戏与启动模型

游戏状态：

- `installed`：安装目录当前有效。
- `missing`：本体失效或根目录被删除。
- `save_only`：仅存档卡片；可由批量存档工作台创建并参与分组，没有安装目录和主程序，不能启动或通过游戏磁盘删除流程处理。

启动配置包括主 EXE、工作目录、参数数组和环境变量覆盖。所有路径以游戏目录内相对路径保存并在启动前重新验证。进程使用 `shell=False` 启动。

## 9. 引擎识别模型

引擎检测由专用 Python 检测器和受约束的 YAML 规则组成。结果包含：

- 引擎 ID 和标签。
- 可选变体。
- 0～1 可信度。
- 可读证据。
- 规则版本。
- 正式或实验性标记。

前两名过于接近时保留歧义，不自动采用。用户可以选择已知引擎、未知引擎或自定义标签。完整引擎范围见模块 04。

V0.3 采用“双规则库 + 共享基础层”：引擎识别规则和存档位置规则保持各自适合的声明式结构，但共用稳定 ID、规则类型、内置或用户来源、正式或实验状态、版本、公开依据、优先级、安全校验和诊断。内置规则使用 `builtin` 命名空间并随 GameShelf 发布，用户规则使用 `user` 命名空间并独立存放；用户规则不能静默覆盖内置规则 ID。

V0.3.0 已校准 QLIE、Majiro、Malie、ShiinaRio、SoftPal/AmuseCraft、Entis/ERI/NOA 和 Nitroplus 七个旧实验规则，并新增 LiveMaker、CMVS/CVNS、Godot。QLIE、Majiro、Malie、ShiinaRio、Entis、Nitroplus 及三个新增引擎已转正式；SoftPal/AmuseCraft 因短魔数和真实样本证据不足继续保持实验。

V0.3.1 以规则文件为唯一事实来源，不新增规则数据库表。后端把内置规则、用户规则和本地启停设置编译为不可变运行时快照；每次游戏分析、单游戏查找或批量存档扫描在开始时捕获一个快照，任务进行中不会因编辑而改变语义。保存或导入规则时，先对完整候选目录执行结构、安全、冲突和编译校验，再原子写入并交换新快照；失败时继续使用旧快照。编辑器保存后立即影响下一次任务，但不自动重扫游戏库或存档目录；外部手工修改文件后由用户点击“刷新规则”或重启加载，第一版不提供持久目录监听。

V0.3.2 不增加新的检测执行时机。固定 GARbro 提交下的 228 个顶层目录已逐项分类：120 个由上游处理器明确描述为引擎/系统相关，Eushully、Liar 和 YU-RIS 另由具体结构确认；其中尚未实现且能由当前安全证据操作直接表达的 45 个强特征族与 7 个实验族进入本批。新增规则仍只在新增游戏分析、完整扫描或用户点击“重新检测”时执行。GARbro 候选台账只用于开发调研，不由程序加载，也不产生启动联网请求；依赖解密、复杂索引、全目录无条件枚举或新证据操作的候选不混入本批。

## 10. 封面模型

每个游戏只有一张当前封面。输入支持本地 PNG/JPEG/WebP/BMP 和剪贴板截图。后端验证格式与尺寸，保存规范化原图和 400×600 WebP 缩略图。

封面文件位于 `data/covers`，数据库只保存受管相对路径和修订号。前端通过带随机会话令牌的回环服务读取，不能读取外部任意路径。

## 11. 存档位置模型

每个游戏可拥有多个：

- 目录。
- 单个文件。
- glob 文件模式。
- 注册表键。

文件系统路径优先保存为 `<game>`、`<winAppData>`、`<winLocalAppDataLow>` 等便携模板。来源包括手动、动态、Ludusavi、引擎提示和旧存档扫描。

V0.1 包含手动位置、按需静态建议和引导式寻找存档。Ludusavi、游戏专属规则和引擎提示失败时不能影响手动操作；引导式检测失败时也不能改变已有位置。静态规则见模块 05，引导式流程见模块 06。

V0.3 静态建议合并用户与内置游戏专属规则、Ludusavi SQLite 索引，以及用户与内置引擎通用规则。只有用户点击“查找存档”后才执行：GameShelf 不启动 Ludusavi 程序，而是查询由其清单派生的本地 SQLite 索引；仅在索引缺失、损坏、版本不兼容或摘要不符时按需内部重建。实际存在的位置显示为“已找到”，可可靠推导但当前不存在的位置折叠到“可能路径 / 未发现”。多来源命中同一路径时只显示一个候选并合并证据。

V0.3.1 的存档编辑器支持两类用户规则：使用标题别名或稳定产品编号精确归属的“游戏专属存档规则”，以及基于已识别引擎和白名单元数据令牌推导位置的“引擎通用存档规则”。游戏专属规则不使用模糊名称自动归属。游戏详情提供“为此游戏创建专属存档规则”入口，跳转到独立规则管理页并预填标题、产品编号、引擎和已确认存档位置；测试规则只读取证据，不修改游戏记录、自动引擎结果或已确认位置。

V0.3.2 为每个声明式存档位置增加可选 `require_existing`：缺省为 `false`，允许可靠路径以“可能路径”展示；设置为 `true` 时，只有受限探测实际命中才生成静态候选。规则编辑器以“始终建议/仅找到时显示”下拉框呈现。Ren'Py 的安全 `config.save_directory` 字符串提取只提供 `{renpy_save_directory}` 元数据，路径、可信度和启停由 YAML 控制；RPG Maker 各世代与 NScripter 的现有文件提示迁入内置 YAML。KiriKiri 和 WOLF 仍保留需要目录内部证据的代码提示。该扩展不新增数据库表，不改变按需查找和批量扫描的用户触发边界。

| `game_analysis_cache` | 主程序与引擎分析的可丢弃持久缓存 | V0.1 |
| `save_detection_sessions` | 引导式检测会话 | V0.1 |
| `save_discoveries` | 引导式检测候选审核 | V0.1 |
| `save_scan_candidates` | 批量存档跨扫描稳定候选、匹配和审核状态 | V0.2 |
| `save_scan_observations` | 每次批量扫描发现候选的来源和证据 | V0.2 |
| `game_groups` | 自定义分组名称与稳定身份 | V0.2 |
| `game_group_memberships` | 游戏与分组的多对多关系 | V0.2 |
| `settings` | 可扩展设置 | 预留 |

数据库写入由单一线程串行执行。扫描先写观察表，成功后再用事务核对正式游戏库。

V0.2.1 当前源码使用新建 schema 4 数据库，包含 schema 3 的自定义分组关系，并正式拆分引导式候选与批量跨扫描候选。按开发期约定不提供 schema 2/3 到 schema 4 的迁移；程序检测到旧库时必须在写入前拒绝继续启动并提示用户自行移走或删除 `data/library.db`，不得自动删除数据库、封面、游戏或实际存档。删除旧数据库会失去其中保存的游戏、封面关联、存档位置和设置记录，磁盘上的封面文件本身不会被自动清理。

## 14. 并发与响应性

- SQLite 写操作串行化。
- 扫描和清单更新使用后台任务。
- 前端轮询任务快照并允许协作式取消。
- 清单状态查询不解析大型官方 YAML。
- 打开详情和展开存档区域不自动运行静态匹配。
- 封面网格使用缩略图；出现实测瓶颈前不提前引入复杂虚拟列表。
- Ludusavi 正常查询使用摘要绑定的派生 SQLite 索引，不在每次查找时解析大型 YAML。
- 规则任务捕获不可变快照；保存规则只影响后续任务，不改变正在运行的游戏扫描或存档扫描。
- 游戏扫描使用 quick/full 分工、持久分析缓存和 1～4 全局共享并发；扫描阶段、耗时和缓存复用均在界面显示。
- V0.2 分组列表和游戏关系使用固定数量的批量查询，不按游戏逐条读取关系。

## 15. 安全与隐私

- 不执行扫描发现的程序。
- 不通过 shell 拼接启动命令。
- 不跟随符号链接和重解析点越过范围。
- 文件、图片、YAML、glob、扫描深度和条目数都有上限。
- 引擎与存档规则只能使用受限声明式操作和白名单路径令牌，不得执行 Python、Shell、脚本或清单提供的 SQL。
- 用户规则不得使用任意环境变量、目录穿越、设备路径、受限范围外的网络路径或从盘符根开始的无界 `**`；glob、扫描深度、条目数、候选数和用时均有硬上限。
- 注册表操作限制到 HKCU/HKLM 的明确键。
- 不保存存档内容、剪贴板图片内容或引导式检测的原始事件流。
- 不默认联网；更新操作由用户显式触发。
- 不开放任意本地路径给前端或 HTTP 服务。
- 第三方规则和运行时必须记录来源、许可证和完整性哈希。

## 16. 错误与降级

- 根目录不可访问：保留游戏状态并显示错误。
- 扫描取消或失败：不执行缺失核对。
- 单个引擎检测器失败：保留诊断，继续扫描。
- 封面导入失败：保留旧封面。
- Ludusavi 损坏或更新失败：回退随包快照或继续使用最后一次有效活动快照；官方来源不可用时仍保留手动、用户/内置存档规则和引擎提示。
- 单个用户规则损坏：隔离该文件并显示可展开诊断，其余规则和最近有效快照继续工作。
- `data/rules/settings.json` 损坏：全部内置规则回退为启用并显示诊断；不得修改随包资源。
- 活动 Ludusavi 三件套损坏：自动回退到随包快照；更新失败不得替换当前有效文件组。
- 后台任务异常：写入日志并进入失败终态，不允许界面无限加载。

## 17. 测试策略

- Python 单元测试覆盖路径、扫描、排序、检测器、规则、存档和基础设施。

- 集成测试覆盖数据库事务、扫描核对、封面和存档服务。
- 前端组件测试覆盖游戏库、抽屉、缩放、封面、分组、引擎和存档交互。
- 商业游戏文件不进入仓库；真实误判转成合成最小夹具。
- CI 在 Windows 上运行 Python 与前端完整质量门禁。
- 发布前增加冻结产物冒烟和干净虚拟机人工验收。

## 19. 版本验收

### 19.1 V0.1 总体验收

- 用户能添加多个根目录并获得稳定、可纠正的游戏库。
- 扫描失败和离线盘不会破坏现有状态。
- 用户能设置封面、标题、主程序、引擎和多个存档位置。
- 用户能使用主页批量管理，并在批量封面工作台中逐项审核来自在线或本地来源的候选。
- 标题与版本号独立保存和展示，五档缩放、固定控制区和内部滚动在支持窗口尺寸下可操作。
- quick/full 扫描、缓存复用、全局并发和局部重新检测不会覆盖有效人工值。
- 游戏可以使用受验证配置安全启动。
- 静态存档建议只按需运行并始终经过审核。
- 用户可以主动启动一次引导式检测，在游戏内保存后审核候选位置；未确认候选不会落库。
- 引导式检测取消、失败、目录不可访问或事件溢出时有明确状态，并且不影响已有存档位置。
- 程序目录可在退出后整体复制到新的本地路径。
- 正式 onedir 包以 Windows 10/11 x64 为目标；V0.1 以自动门禁、本机和 Windows Sandbox 验收作为收尾依据，额外干净目标设备复核保留为后续可选兼容性检查。
- 自动化质量门禁与冻结冒烟测试通过。

### 19.2 V0.2 批量存档发现验收

- 扫描只能由用户显式启动，退出程序后不会在下次启动自动继续。
- 已安装未记录、已安装已记录、本体失效、Ludusavi 反向识别和完全未知候选均有明确状态。
- 强证据才自动归组，模糊名称和通用引擎结构不会冒进关联。
- 扫描具有深度、条目、候选和代表文件硬上限；取消、截断和范围不可访问不会误标旧候选。
- 忽略、关联、失效和恢复状态跨扫描及重启保留。
- 批量确认和创建仅存档卡片通过单事务写入；失败没有部分结果。
- 未确认候选不写入游戏库或存档位置，所有磁盘及注册表内容保持只读。
- 在线核对只在用户点击后打开浏览器，只使用界面展示的关键词，不自动抓取第三方站点。
- 五档缩放和最小、默认、宽窗口中的一级导航、固定控制区、候选滚动区与批量操作均可使用。

### 19.3 V0.3 引擎与存档规则验收

- 首批 10 个目标引擎分别形成“转正式、保持实验或暂不加入”的明确结论及证据。
- 规则格式、安全边界、来源、正式/实验状态、优先级和冲突处理具有自动测试。
- 存档规则正确区分实际存在和仅可推导路径，同一路径多来源去重但不丢失证据。
- 版本号不参与默认游戏名称匹配；静态规则、Ludusavi 索引查询和索引恢复仍只由用户点击触发。
- 当前电脑缺少的真实游戏列入人工验收清单，不阻塞合成夹具自动门禁，也不伪装成已完成验证。
- 规则扩展不新增持久业务表，不要求数据库迁移；损坏或无效规则只影响对应来源，手动引擎与存档位置继续可用。

V0.3.0 收口实测为 Python 963 项、前端 48 个测试文件共 197 项；Ruff、mypy、Vue 类型检查、115 模块生产构建和隔离 schema 4 源码 smoke 均通过。真实游戏不足的首批规则矩阵仍为未完成人工项，V0.3.0 没有构建便携包。

V0.3.1 自定义规则编辑器的持续验收基准为：

- “规则管理”作为与游戏库、批量存档同级的独立页面，提供引擎规则、存档规则和 Ludusavi 三个标签；正常宽度为左侧规则列表与右侧详情/编辑器，窄窗口改为列表与详情分步显示。
- 内置规则只读但可本地禁用、复制和测试；用户规则一条一个 YAML，支持创建、编辑、启停、复制、导入、导出和删除。
- 新建或复制规则默认实验；只读测试成功后可由用户标记“用户规则 · 已验证”，修改匹配、证据或路径后自动回到实验。该状态不代表 GameShelf 官方验证。
- 全量候选快照校验、原子写入、任务快照隔离、单文件损坏隔离、启停设置损坏降级和 Ludusavi 随包回退具有自动测试。
- 旧 manifest 路径不再参与运行，不执行数据库迁移或旧 `custom` 自动转换；正常启动、游戏库扫描和启动游戏仍不会查询存档规则或联网更新 Ludusavi。

V0.3.1 源码自动验收为 Python 1057 项通过、1 项平台条件跳过，前端 56 个测试文件共 234 项通过，并通过 Ruff、mypy、Vue 类型检查、141 模块生产构建和隔离 schema 4 源码 smoke。2026-08-25 用户已确认规则工作台五档缩放、三类窗口、完整规则交互、失败回退和当前可用本地游戏测试均符合预期；缺少样本的真实游戏矩阵继续后置，V0.3.1 便携包尚未构建。

V0.3.2 的新增验收基准为：GARbro 顶层候选台账锁定上游提交、记录 123 个引擎/系统相关族且不参与运行；模块 04 中 45 个强特征规则与 7 个实验规则逐条具有具体处理器依据、正反、近似魔数、跨格式碰撞与截断夹具；`require_existing` 在 schema、编辑器、导入导出、本地测试、单游戏查找和批量扫描中语义一致；Ren'Py、RPG Maker、NScripter 迁移后不产生重复候选且保持原行为；KiriKiri/WOLF 代码提示不受影响；schema 仍为 4，程序启动与普通游戏库扫描不新增存档目录访问或网络请求。
