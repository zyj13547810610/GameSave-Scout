# GameShelf 总体设计

> 文档性质：项目最高层的当前产品与技术设计；最后更新：2026-08-19。模块细节以 01～07 固定文档为准，版本优先级以开发路线图为准。

## 1. 产品定位

GameShelf 是面向 Windows 10/11 x64 的本地优先、便携式个人游戏库与存档位置管理器，主要适用于：

- 不通过统一平台管理的单机游戏。
- Galgame、DLsite 作品及厂商自定义引擎游戏。
- RPG Maker、WOLF RPG Editor、Ren'Py、Unity 等作品。
- 用户希望自行维护封面、启动方式和存档路径的游戏。

程序不要求连接 Steam、Epic、GOG 等平台。用户指定一个或多个本地根目录，GameShelf 扫描文件夹建立游戏库。

## 2. 用户目标

用户打开应用后可以：

- 浏览电脑上的游戏封面和安装状态。
- 搜索并按状态、引擎或自定义分组筛选。
- 创建自定义分组，并为一个游戏维护多个分组归属。
- 打开安装目录或直接启动游戏。
- 修正标题、主程序、启动参数和引擎。
- 从本地选择封面或粘贴截图。
- 为每个游戏记录一个或多个存档目录、文件、通配符或注册表位置。
- 在需要时使用本地规则辅助查找存档。
- 主动启动一次引导式检测，在游戏内保存后审核新增或修改位置。
- 把整个 GameShelf 目录复制到其他本地位置继续使用。

## 3. 分阶段范围

### V0.1 首发版

- 多根目录、直接子目录或递归游戏扫描，以及可关闭的启动快速核验、手动完整扫描、持久分析缓存和 1～4 全局共享分析并发。
- 游戏库、标题与版本号分离、封面、搜索、状态/引擎筛选、主页批量管理和详情抽屉。
- 80%～120% 五档便携界面缩放、固定控制区、内部独立滚动和统一深色滚动条。
- 单游戏封面管理与批量封面工作台；候选可来自 VNDB、拖放/粘贴、游戏目录浅层扫描和自定义非递归封面目录，全部由用户审核采用。
- 主程序推荐、手动启动配置、状态核对、局部重新检测以及扫描结果缓存复用。
- 静态引擎识别、证据展示、歧义处理和手动覆盖。
- 手动多存档位置，以及按需使用自定义清单、Ludusavi SQLite 索引和引擎提示生成静态建议。
- 用户主动启动的引导式存档检测；在完整监控会话内汇总受限文件和定向注册表变化，并按与保存标记的时间距离加权生成候选。
- PyInstaller onedir 双便携发布：完整离线版自带 Fixed Version WebView2 Runtime，轻量联网版使用系统 Evergreen 并随包提供受控 Bootstrapper。

### V0.2

- 用户创建、重命名和删除扁平自定义分组；一个游戏可属于多个分组，并可在详情或主页批量管理中调整归属。
- 主页按具体分组或“未分组”筛选，与搜索、状态和引擎条件共同取交集。
- 查找游戏本体删除后留下的孤立存档。
- 关联现有游戏、创建仅存档卡片或忽略候选。

### V0.3 及以后

- 存档备份、恢复、版本历史和可选同步。
- 更完整的导入导出、自定义规则编辑和可选在线元数据。

V0.1 当前范围已经完成。V0.2 的自定义分组和孤立存档发现是两个独立子项目，分别设计、实施和验收；备份与同步继续留在更晚版本。详细状态见 `GameShelf-开发路线图.md`。

## 4. 核心产品原则

### 4.1 游戏发现与引擎识别分离

扫描器判断“这是一个需要展示的游戏目录”，引擎识别器判断“它可能使用什么引擎”。未知引擎不影响入库、封面和启动。

### 4.2 自动检测与用户采用值分离

标题、主 EXE 和引擎都区分自动检测值与用户采用值。重新扫描可以更新自动值，但不能覆盖有效手动选择。

### 4.3 所有建议先审核

移动游戏、静态存档位置、引导式检测候选和孤立存档关系都只能提出建议。没有用户确认，不自动合并游戏、写入正式存档位置或建立关联。

### 4.4 默认只读和最小权限

扫描、引擎识别和存档查找只读取批准范围内的路径和受限元数据。程序不执行发现阶段的 EXE、不解包商业资源、不请求管理员权限、不静默扫描所有磁盘。

### 4.5 本地优先与便携

应用自身数据位于程序旁 `data`。除用户明确点击 Ludusavi 更新等联网操作外，日常浏览、扫描、启动和手动管理均可离线工作。

## 5. 技术架构

```text
Vue 3 / TypeScript / Pinia
          │ 类型化桥接 API
          ▼
pywebview 桌面窗口
          │
          ▼
Python 应用服务
├─ 游戏库与扫描
├─ 启动与 Windows 适配器
├─ 封面处理
├─ 引擎检测
├─ 存档位置与静态建议
├─ 引导式存档检测
├─ 自定义游戏分组（V0.2）
├─ 后台任务
└─ SQLite 串行写入
          │
          ├─ data/library.db
          ├─ data/covers
          ├─ data/manifests
          └─ 127.0.0.1 只读 UI/封面服务
```

前端负责显示、交互和短生命周期视图状态。Python 负责所有文件系统、注册表、进程、数据库、图片和规则操作。前端不能直接访问任意本地文件路径。

## 6. 主要用户流程

### 6.1 首次启动

1. 程序创建并验证 `data`。
2. 初始化数据库和本地资源服务。
3. 用户添加一个或多个游戏根目录。
4. 用户选择直接子目录或递归扫描，并设置排除项。
5. 扫描完成后游戏卡片进入主界面。

### 6.2 日常启动

1. 立即从 SQLite 显示缓存游戏库。
2. 对已启用根目录启动后台快速核验。
3. 盘符离线、任务取消或扫描失败时保留原状态。
4. 用户需要重新发现目录时手动执行完整扫描。

### 6.3 游戏详情

用户点击卡片后在右侧抽屉中处理封面、引擎、存档位置和启动设置。主页面被半透明遮罩覆盖并锁定滚动，抽屉独立滚动。

### 6.4 存档位置

用户可以直接手动添加。静态规则只有点击“查找存档”后才运行；候选按可信度分组，接受后才保存。V0.1 还提供用户主动开始的引导式检测会话：程序启动指定游戏，结合“我刚刚保存了”时间标记汇总受限范围内的文件变化，仍由用户审核后保存。孤立存档扫描留到 V0.2。

### 6.5 自定义分组

V0.2 允许用户建立扁平自定义分组。一个游戏可同时属于多个分组；用户既可在详情抽屉调整单个游戏，也可在主页批量管理中把最多 500 个游戏加入或移出一个分组。主页分组筛选为单选，提供“全部分组”“未分组”和具体分组，并与搜索、状态和引擎筛选取交集。

分组只有名称，不在第一版加入父子层级、颜色、图标或自动分类规则。删除分组只删除关系，不删除游戏；分组适用于 `installed`、`missing` 和未来孤立存档流程产生的 `save_only` 记录。

## 7. 游戏扫描模型

支持任意多个根目录：

- `children`：每个可访问直接子目录作为候选。
- `recursive`：继续向下寻找包含潜在游戏 EXE 的目录，找到后停止进入其后代。

辅助 EXE 不会阻断递归。路径按 Windows 语义规范化，重叠根目录由最具体的启用根目录拥有。完整扫描成功后才把未观察到的游戏标记为 `missing`。

当前扫描模型会保留失效游戏，便于目录离线、搬盘和未来存档反推；单条与批量删除/忽略流程已经实现。快速核验只检查已知记录，完整扫描负责发现新游戏并在成功后核对失效状态；未变化的主程序与引擎分析可复用持久缓存。

## 8. 游戏与启动模型

游戏状态：

- `installed`：安装目录当前有效。
- `missing`：本体失效或根目录被删除。
- `save_only`：未来 V0.2 使用的仅存档卡片。

启动配置包括主 EXE、工作目录、参数数组和环境变量覆盖。所有路径以游戏目录内相对路径保存并在启动前重新验证。进程使用 `shell=False` 启动。

## 9. 引擎识别模型

引擎检测由专用 Python 检测器和受约束的 YAML 规则组成。结果包含：

- 引擎 ID 和标签。
- 可选变体。
- 0～1 可信度。
- 可读证据。
- 规则版本。
- 正式或实验性标记。

前两名过于接近时保留歧义，不自动采用。用户可以选择已知引擎、未知引擎或自定义标签。完整引擎范围见模块 04。

## 10. 封面模型

每个游戏只有一张当前封面。输入支持本地 PNG/JPEG/WebP/BMP 和剪贴板截图。后端验证格式与尺寸，保存规范化原图和 400×600 WebP 缩略图。

封面文件位于 `data/covers`，数据库只保存受管相对路径和修订号。前端通过带随机会话令牌的回环服务读取，不能读取外部任意路径。

## 11. 存档位置模型

每个游戏可拥有多个：

- 目录。
- 单个文件。
- glob 文件模式。
- 注册表键。

文件系统路径优先保存为 `<game>`、`<winAppData>`、`<winLocalAppDataLow>` 等便携模板。来源包括手动、动态、Ludusavi、引擎提示和旧存档扫描。

V0.1 包含手动位置、按需静态建议和引导式寻找存档。Ludusavi、自定义清单和引擎提示失败时不能影响手动操作；引导式检测失败时也不能改变已有位置。静态规则见模块 05，引导式流程见模块 06。

## 12. 数据模型

| 表 | 用途 | 当前使用阶段 |
| --- | --- | --- |
| `scan_roots` | 多个扫描根目录与规则 | V0.1 |
| `games` | 游戏、状态、启动、引擎和封面 | V0.1 |
| `save_locations` | 已确认存档位置 | V0.1 |
| `scan_sessions` | 游戏库或孤立扫描会话 | V0.1/V0.2 |
| `scan_observations` | 完整扫描的临时观察项 | V0.1 |
| `game_analysis_cache` | 主程序与引擎分析的可丢弃持久缓存 | V0.1 |
| `save_detection_sessions` | 引导式检测会话 | V0.1 |
| `save_discoveries` | 引导式或孤立候选审核 | V0.1/V0.2 |
| `game_groups` | 自定义分组名称与稳定身份 | V0.2 |
| `game_group_memberships` | 游戏与分组的多对多关系 | V0.2 |
| `settings` | 可扩展设置 | 预留 |

数据库写入由单一线程串行执行。扫描先写观察表，成功后再用事务核对正式游戏库。

V0.2 自定义分组使用新建 schema 3 数据库，但按当前开发约定不提供 V0.1 schema 2 到 schema 3 的迁移。程序检测到旧库时必须拒绝继续启动并提示用户自行移走或删除 `data/library.db`；不得自动删除数据库、封面或游戏文件。删除旧数据库会失去其中保存的游戏、封面关联、存档位置和设置记录，磁盘上的封面文件本身不会被自动清理。

## 13. 便携目录

```text
GameShelf/
├─ resources/                   # 源码版不可变资源
└─ data/
   ├─ library.db
   ├─ config.json
   ├─ covers/original
   ├─ covers/thumbs
   ├─ manifests/ludusavi
   ├─ manifests/custom

   ├─ webview
   ├─ logs
   └─ temp
```

冻结版不可变资源放入 PyInstaller 内部目录，`data` 仍位于 `GameShelf.exe` 旁。完整打包结构见模块 07。

## 14. 并发与响应性

- SQLite 写操作串行化。
- 扫描和清单更新使用后台任务。
- 前端轮询任务快照并允许协作式取消。
- 清单状态查询不解析大型官方 YAML。
- 打开详情和展开存档区域不自动运行静态匹配。
- 封面网格使用缩略图；出现实测瓶颈前不提前引入复杂虚拟列表。
- Ludusavi 正常查询使用摘要绑定的派生 SQLite 索引，不在每次查找时解析大型 YAML。
- 游戏扫描使用 quick/full 分工、持久分析缓存和 1～4 全局共享并发；扫描阶段、耗时和缓存复用均在界面显示。
- V0.2 分组列表和游戏关系使用固定数量的批量查询，不按游戏逐条读取关系。

## 15. 安全与隐私

- 不执行扫描发现的程序。
- 不通过 shell 拼接启动命令。
- 不跟随符号链接和重解析点越过范围。
- 文件、图片、YAML、glob、扫描深度和条目数都有上限。
- 注册表操作限制到 HKCU/HKLM 的明确键。
- 不保存存档内容、剪贴板图片内容或引导式检测的原始事件流。
- 不默认联网；更新操作由用户显式触发。
- 不开放任意本地路径给前端或 HTTP 服务。
- 第三方规则和运行时必须记录来源、许可证和完整性哈希。

## 16. 错误与降级

- 根目录不可访问：保留游戏状态并显示错误。
- 扫描取消或失败：不执行缺失核对。
- 单个引擎检测器失败：保留诊断，继续扫描。
- 封面导入失败：保留旧封面。
- Ludusavi 损坏或更新失败：恢复或继续使用最后一次有效清单；没有官方清单时仍保留手动、自定义和引擎提示。
- 后台任务异常：写入日志并进入失败终态，不允许界面无限加载。

## 17. 测试策略

- Python 单元测试覆盖路径、扫描、排序、检测器、规则、存档和基础设施。
- 集成测试覆盖数据库事务、扫描核对、封面和存档服务。
- 前端组件测试覆盖游戏库、抽屉、缩放、封面、引擎和存档交互。
- 商业游戏文件不进入仓库；真实误判转成合成最小夹具。
- CI 在 Windows 上运行 Python 与前端完整质量门禁。
- 发布前增加冻结产物冒烟和干净虚拟机人工验收。

## 18. 开源边界

- 项目采用 MIT License 开源；第三方组件和数据继续按各自许可证记录。
- MTool 等现有工具只作为功能和格式调研参考，不复制其私有实现或数据。
- Ludusavi 清单随包使用时保留许可证和第三方声明。
- 用户本地游戏、封面、数据库和存档绝不提交到仓库或发布包。

## 19. V0.1 总体验收

- 用户能添加多个根目录并获得稳定、可纠正的游戏库。
- 扫描失败和离线盘不会破坏现有状态。
- 用户能设置封面、标题、主程序、引擎和多个存档位置。
- 用户能使用主页批量管理，并在批量封面工作台中逐项审核来自在线或本地来源的候选。
- 标题与版本号独立保存和展示，五档缩放、固定控制区和内部滚动在支持窗口尺寸下可操作。
- quick/full 扫描、缓存复用、全局并发和局部重新检测不会覆盖有效人工值。
- 游戏可以使用受验证配置安全启动。
- 静态存档建议只按需运行并始终经过审核。
- 用户可以主动启动一次引导式检测，在游戏内保存后审核候选位置；未确认候选不会落库。
- 引导式检测取消、失败、目录不可访问或事件溢出时有明确状态，并且不影响已有存档位置。
- 程序目录可在退出后整体复制到新的本地路径。
- 正式 onedir 包以 Windows 10/11 x64 为目标；V0.1 以自动门禁、本机和 Windows Sandbox 验收作为收尾依据，额外干净目标设备复核保留为后续可选兼容性检查。
- 自动化质量门禁与冻结冒烟测试通过。
