# Ludusavi 清单更新修复设计

## 背景

GameShelf 随程序附带一份 Ludusavi 官方清单，并允许用户在“存档规则设置”中手动点击“检查并更新清单”。当前 Windows 开发环境启用了 Git 的自动换行转换，仓库中的 `resources/manifests/ludusavi/manifest.yaml` 在检出后由 LF 变成了 CRLF，导致文件实际 SHA-256 与 `manifest-meta.json` 记录的哈希不一致。

首次初始化因此在复制内置清单前抛出 `SnapshotUpdateError`。该异常发生在后台任务中，任务注册器又只返回“任务执行失败”，所以用户既无法使用内置 Ludusavi 规则，也看不到真正原因。

## 目标

- 修复仅由 CRLF/LF 差异导致的内置清单校验失败。
- 不降低内容完整性校验：除已知换行差异外，任何内容变化仍必须被拒绝。
- 下载、验证或替换失败时，继续使用最后一次有效清单。
- 首次运行且官方清单不可用时，仅停用 Ludusavi 官方规则，不影响自定义清单和引擎内置存档规则。
- 向用户展示可理解的更新阶段和具体失败原因。
- 将意外异常的完整堆栈写入便携目录下的 `data/logs/gameshelf.log`。
- 保持现有便携目录结构，不增加数据库迁移。

## 非目标

- 不自动联网更新；只有用户主动点击按钮才访问网络。
- 不更换 Ludusavi 数据源或解析格式。
- 不为下载内容引入新的签名体系。远程清单仍通过 HTTPS 获取，下载后计算并保存 SHA-256，用于本地一致性校验。
- 不在本子项目中实现引擎识别增强、游戏移除与忽略、排除项编辑或扫描进度。这些需求分别进入后续子项目。

## 方案选择

采用“严格校验并安全修复已知换行差异”方案：

1. `.gitattributes` 明确规定内置 `manifest.yaml` 使用 LF。
2. 内置清单首先按原始字节校验 SHA-256。
3. 原始校验失败时，只尝试将 CRLF 规范化为 LF。
4. 规范化结果的 SHA-256 与元数据完全一致时才接受；否则拒绝。
5. 接受规范化结果时，将规范化后的 LF 字节写入当前有效清单，保证当前清单与元数据一致。

该方案既修复现有 Windows 工作区，也能防止其他打包或复制流程再次引入同类问题。它不会把任意哈希不一致视为可修复。

## 清单分层与目录

清单分为三层：

- **内置清单**：`resources/manifests/ludusavi`，作为首次运行的只读种子。
- **当前有效清单**：`data/manifests/ludusavi`，存档匹配只读取这一层。
- **临时下载**：`data/temp` 下的唯一临时文件，验证完成前绝不参与匹配。

`data/manifests/ludusavi/previous` 保留最近两组有效备份。每组备份必须同时包含清单和元数据，不能只备份其中一个文件。

## 首次初始化流程

1. 如果当前清单和元数据都存在，则在使用前验证二者的一致性和清单格式。
2. 当前文件组缺失或无效时，从新到旧检查 `previous` 中的成组备份；找到有效组后恢复为当前文件组。
3. 没有有效备份时，读取内置清单和内置元数据。
4. 对内置清单执行原始字节 SHA-256 校验。
5. 原始校验失败时，流式执行 `CRLF -> LF` 规范化并重新校验。
6. 只有原始内容或规范化内容与元数据完全匹配时，才通过临时文件写入当前有效清单。
7. 清单与元数据作为一组完成替换；发生异常时删除临时文件并恢复替换前状态。
8. 如果当前文件、备份和内置清单都无法验证，将 Ludusavi 官方清单标记为不可用，并保留具体原因供状态接口展示。

单独存在清单或单独存在元数据属于不完整状态，不能直接使用。提供者内部使用互斥锁保护初始化、读取和更新，避免其他线程观察到只替换了一半的文件组。

## 手动更新流程

用户点击“检查并更新清单”后，后台任务依次上报以下阶段：

1. 正在连接 Ludusavi 数据源。
2. 正在下载清单。
3. 正在验证清单。
4. 正在替换当前清单。

更新规则如下：

- 存在当前有效元数据时携带其中的 ETag；服务器返回 304 时报告“已是最新”。
- 没有任何有效官方清单时仍允许手动更新，此时不发送 ETag；成功下载并验证后建立第一组当前有效文件。
- 下载大小上限保持为 64 MiB，并继续使用既有超时设置。
- 数据只写入唯一临时文件，同时计算 SHA-256。
- 下载完成后重新读取临时文件，确认磁盘内容哈希与下载阶段计算结果一致。
- 临时文件必须是有效 UTF-8，并能通过 Ludusavi YAML 解析器验证。
- 验证成功后，先备份当前清单和元数据，再写入新清单和新元数据。
- 任一替换步骤失败时，恢复完整的旧清单与旧元数据；保留成组备份，供下次启动再次恢复。
- 只有替换全部成功后才清理多余备份，并通知存档发现服务清除内存中的官方清单缓存。

更新失败不得清除缓存或修改当前有效元数据。

## 错误模型

### 可预期错误

以下情况返回结构化更新结果，而不是让后台任务进入笼统的失败状态：

- 无法连接、DNS 或 TLS/网络错误。
- 非预期 HTTP 状态。
- 下载内容超过大小限制。
- 下载文件不是有效 UTF-8。
- YAML 格式或 Ludusavi 数据结构无效。
- 临时文件写入前后的哈希不一致。
- 备份、替换或恢复失败。
- 内置清单与元数据不匹配。

结构化结果继续使用 `updated`、`not_modified`、`invalid`、`failed` 四种状态，并携带面向用户的中文消息和仍在使用的有效清单元数据。示例：

> 更新失败：下载的清单格式无效。当前仍在使用 2026-08-10 获取的有效清单。

### 意外错误

任务注册器捕获未预料异常时：

- 使用 `logger.exception` 将完整堆栈写入 `data/logs/gameshelf.log`。
- 前端仍只收到安全的通用消息，提示用户查看日志。
- 不把堆栈、临时路径或其他内部细节直接展示给用户。

## 降级行为

### 存在最后一次有效清单

任何更新失败都继续使用该清单。设置界面保留清单来源、获取时间和简短 SHA-256，并明确说明“当前有效清单仍可使用”。

### 没有可用的官方清单

存档发现服务捕获“官方清单不可用”的专用错误，只跳过 Ludusavi 官方匹配：

- 自定义清单继续加载。
- 引擎内置存档规则继续生成建议。
- 整个“检查存档建议”操作不会因为官方清单不可用而失败。
- Ludusavi 设置区域展示官方清单不可用的原因和重试入口。

## 组件边界

### `LudusaviProvider`

- 校验内置、当前和下载清单。
- 只修复已验证的 CRLF/LF 差异。
- 管理临时文件、成组备份、替换、恢复和备份裁剪。
- 对外返回结构化结果或“官方清单不可用”的专用错误。
- 不依赖 Vue，也不决定界面布局。

### 后台任务与桥接 API

- 将提供者的进度事件转换成任务阶段消息。
- 将可预期错误作为已完成任务的结构化结果返回。
- 仅在更新成功时使存档发现缓存失效。

### `TaskRegistry`

- 保持任务隔离和安全的通用错误响应。
- 为意外异常增加完整日志记录。

### `StaticSaveDiscovery`

- 官方清单可用时照常合并 Ludusavi 建议。
- 官方清单不可用时跳过该来源，继续合并自定义规则和引擎规则。
- 更新成功并收到失效通知后，下次请求重新加载官方清单。

### 前端 `LudusaviSettings`

- 展示连接、下载、验证、替换阶段。
- 区分成功、已是最新、内容无效和更新失败。
- 失败后继续显示当前有效清单元数据。
- 任务结束后恢复按钮，允许用户再次尝试。
- 使用 `aria-live` 向辅助技术报告状态变化。

## 数据一致性与安全

- 内置元数据中的 SHA-256 是内置清单的可信期望值。
- CRLF 规范化只在规范化结果完全命中该期望值时接受。
- 下载内容的 SHA-256 在下载时计算，并在临时文件落盘后复核。
- 新文件验证完成前不触碰当前有效清单。
- 替换期间用锁阻止并发读取，并为清单与元数据准备成组回滚。
- 临时文件名使用随机 UUID，完成或失败后均尽力清理。
- 不在日志中记录清单全文。

## 测试设计

### 提供者单元测试

- 正确 LF 内置清单直接通过。
- 仅存在 CRLF 差异时规范化并通过，当前清单最终为 LF。
- 修改任意非换行内容后仍拒绝。
- 当前清单与元数据只有一个存在时不会被使用。
- 当前文件组无效时优先恢复最近的有效成组备份，再回退到内置清单。
- 没有现有清单时可以通过手动更新建立第一组有效文件。
- HTTP 304 返回“已是最新”。
- 网络失败、HTTP 异常、超限、无效 UTF-8、无效 YAML 均保留旧文件组。
- 临时文件哈希复核失败时拒绝替换。
- 清单替换失败、元数据替换失败时均恢复旧文件组。
- 更新成功后仅保留最近两组备份。

### 服务与 API 测试

- 可预期更新错误生成结构化结果和具体消息。
- 只有 `updated` 状态使存档发现缓存失效。
- 官方清单不可用时，自定义和引擎规则仍返回建议。
- 意外后台异常写入日志且前端响应不包含堆栈。

### 前端测试

- 更新期间展示阶段消息并禁用重复提交。
- 四种更新结果均展示正确文案和样式。
- 更新失败后仍展示最后一次有效清单的信息。
- 任务结束后按钮恢复可用。

### 仓库与打包检查

- 自动检查内置 `manifest.yaml` 的实际 SHA-256 与元数据一致。
- 检查 `.gitattributes` 对内置清单强制使用 LF。
- 在 Windows 开发工作区和便携版打包产物中各验证一次首次初始化。

## 验收标准

- 当前 Windows 工作区点击“检查并更新清单”不再因内置文件 CRLF 而失败。
- 更新失败不会破坏或停用最后一次有效清单。
- 用户能看到具体失败阶段和原因，不再只有“任务执行失败”。
- 无官方清单时，其他存档建议来源仍正常工作。
- 意外异常可在 `data/logs/gameshelf.log` 中定位。
- 所有新增自动化测试通过，且不需要数据库迁移。
