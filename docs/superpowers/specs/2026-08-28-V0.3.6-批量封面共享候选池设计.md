# V0.3.6 批量封面共享候选池设计

> 文档性质：V0.3.6 增量设计；设计日期：2026-08-28；状态：源码与完整自动门禁完成，真实 pywebview 流程待用户确认。

## 1. 背景与问题

批量封面当前提供两种本地目录来源，但语义不同：

- “浅层扫描”只扫描当前游戏的安装目录，找到的图片天然归属于当前游戏；
- “导入封面目录”扫描用户选择的非递归目录，再用图片文件名与批量队列中的游戏标题或安装目录末级名称进行匹配，只有达到阈值的图片才进入某个游戏的候选列表。

第二种语义无法覆盖两个常见场景：

1. 用户重装系统或重建游戏库后，只保留了旧封面文件，原数据库关联已经丢失；旧封面文件名可能是 hash、UUID 或程序生成名称。
2. 用户一次截取了多张游戏截图，文件名是时间、编号或截图工具生成的随机名称，希望在批量封面工作台中逐个选择并采用。

当数据库关联和可读文件名都不存在时，程序没有可靠信号自动推断“图片属于哪个游戏”。继续使用标题阈值过滤会让合法图片全部消失。V0.3.6 因此把“导入封面目录”改为会话级共享候选池：所有通过安全校验的图片均可供每个待处理游戏人工选择，文件名匹配只影响排序，不再决定图片是否可见。

本设计同时修复一个任务反馈缺陷：目录导入以零候选完成时，后台任务消息为空，前端把空消息回退显示为“正在收集候选…”，造成任务卡住的错觉。

## 2. 目标

- 从用户明确选择的目录导入 hash、UUID、截图编号或正常标题命名的图片。
- 每张导入图片只读取、校验并生成一次会话预览，不按游戏数量复制文件或候选实体。
- 用户切换游戏时，看到当前游戏专属候选和未使用的共享候选；文件名相关项优先，无法匹配的项仍完整保留。
- 一张共享图片采用后默认从后续游戏的候选中隐藏；用户可显示已使用图片并主动复用。
- 多次导入目录时合并共享池并按内容去重。
- 任何发现、预览、取消、关闭或失败流程都不修改或删除外部原图。
- 提供真实、可终止的进度与完成摘要，零新增也必须进入明确完成状态。
- 保持 SQLite schema 4 和配置版本 6，不持久化共享池。

## 3. 非目标

- 不根据图像内容、OCR、感知哈希或在线服务自动识别游戏。
- 不在本轮实现封面关联清单的导出、导入或数据库恢复。
- 不递归扫描所选封面目录；用户应直接选择包含原图的目录，例如旧数据中的 `covers/original`。
- 不自动采用任何图片，也不批量覆盖已有封面。
- 不把共享池保存到 SQLite、配置文件或程序重启后的缓存。
- 不改变 VNDB、拖放、剪贴板和游戏目录浅层扫描的归属语义。

## 4. 用户流程

1. 用户进入“批量封面”，队列继续默认显示没有封面的游戏，也可通过现有开关包含已有封面的游戏。
2. 用户点击“导入封面目录”并选择一个目录。
3. 后台非递归枚举目录中的受支持图片，逐张执行大小、格式、尺寸和解码校验，生成有界 WebP 预览。
4. 完成后显示“导入完成：新增 X 张、重复 Y 张、无效 Z 张”；达到边界时追加截断说明。
5. 当前游戏的候选画廊合并显示：
   - 当前游戏已有的 VNDB、拖放、剪贴板或浅层扫描候选；
   - 共享池中尚未使用的全部图片。
6. 共享图片按当前游戏标题和安装目录末级名称动态计算相关度。精确或规范化匹配排在共享候选前部，模糊结果按分数排序；低分、hash 和编号文件仍显示。
7. 用户采用一张共享图片。后端再次验证源文件内容未变化，为当前游戏保存封面，并把该共享项记录为已用于该游戏。
8. 工作台自动进入下一个游戏。默认视图不再显示任何已使用共享项。
9. 用户开启“显示已使用图片”后，可看到“已用于：游戏名”标记，并可明确把同一图片用于其他游戏。
10. 用户可以再次导入同一或另一目录；新内容合并，重复内容不新增，既有使用记录保持不变。
11. 关闭批量封面时清理会话预览和共享池内存状态，不接触外部目录。

## 5. 后端模型

### 5.1 会话级共享实体

`CoverWizardService` 的 `_Session` 增加共享候选集合和内容索引。共享实体不携带预设 `game_id`，至少包含：

- 稳定的会话内候选 ID；
- 外部源路径和导入时 SHA-256；
- 显示文件名、宽、高；
- 会话预览路径；
- 已使用游戏 ID 集合。

共享池使用候选 ID 保持导入顺序身份，使用 SHA-256 索引做跨目录、跨重复导入的内容去重。已使用关系允许一张图片对应多个游戏，以支持用户开启开关后的主动复用。

现有 `CoverCandidate` 继续表示已经归属于某个游戏的 VNDB、拖放、剪贴板和浅层扫描候选。共享实体独立建模，避免把 `图片数 × 游戏数` 展开成大量重复候选，也避免清理某个游戏候选时误删共享预览。

### 5.2 面向当前游戏的投影视图

`list_cover_candidates` 仍以 `sessionId + gameId` 查询，但增加 `includeUsed` 布尔值。服务在查询时把共享实体投影成当前游戏可用的候选 DTO：

- `gameId` 使用本次查询的游戏 ID；
- `source` 继续使用 `cover_directory`，来源标签改为清晰的“导入目录”；
- `shared` 为 `true`；游戏专属候选为 `false`；
- `usedBy` 返回最小展示信息，即使用该图片的游戏 ID 与标题；
- `matchKind`、`score` 和匹配证据按当前游戏动态计算；
- 未使用项排在已使用项之前；`includeUsed=false` 时完全排除已使用项。

共享投影只创建轻量 DTO，不复制预览文件或持久候选对象。游戏专属候选与共享投影按现有来源优先级合并；共享候选内部按“是否已使用、标题匹配等级、匹配分数、文件名、候选 ID”稳定排序。低于旧阈值的共享项不得过滤。

### 5.3 明确采用目标

`adopt_cover_candidate` 请求改为显式传入：

```text
sessionId + gameId + candidateId
```

后端不能依赖前端当前选择或共享候选中的隐式归属。采用时：

1. 验证会话、队列项和候选存在；
2. 对游戏专属候选验证其原有 `game_id` 与请求 `gameId` 一致；
3. 对共享候选允许任一会话队列游戏采用；
4. 使用现有 SHA-256 复核确保外部源未删除或改变；
5. 调用统一 `CoverService.import_file()`，继续服从当前封面自动优化设置；
6. 成功后更新队列状态，并只给共享候选增加使用记录，不删除共享预览；
7. 数据库或文件保存失败时不增加使用记录，也不改变当前队列状态。

采用游戏专属候选后仍按原逻辑清理该游戏未采用的临时候选。共享候选不参与这一清理集合。

## 6. 导入算法与边界

### 6.1 枚举与校验

- 目录必须存在、是目录且可枚举，否则任务以稳定中文错误失败。
- 只读取直接文件，跳过子目录、符号链接和重解析入口。
- 支持格式继续为 PNG、JPEG、WebP 和 BMP。
- 继续使用现有单文件 50 MiB、最长边 16,384 像素和 6,400 万像素限制。
- 每张图继续生成最大 480×720 的会话 WebP 预览。
- 单次会话最多保留 1,000 张内容唯一的共享图片。
- 枚举检查继续受 5,000 个图片文件上限约束；达到任一上限后任务完成但标记截断，提示用户拆分目录。

“1,000 张”按内容去重后的共享池总量计算，而不是单次导入文件数。已有池中重复内容只增加重复计数，不消耗新名额。

### 6.2 原子发布与取消

一次目录导入先在任务局部批次中生成新共享实体和预览，任务完成前不发布到会话共享池。发布时在向导锁内按 SHA-256 再次与当前池去重并原子合并，确保重复导入或边界竞争不会破坏索引。

用户取消、会话关闭竞争或任务异常时：

- 清理本批次已经生成但尚未发布的预览；
- 保留任务开始前的共享池、候选和使用记录；
- 不删除或改写任何外部原图。

个别图片无效属于可隔离结果：计入无效数量后继续处理。只有目录级错误、会话失效或不可恢复的内部错误才使整个任务失败。

### 6.3 导入摘要

目录导入结果和最终任务消息至少包含：

- `inspectedCount`：检查的受支持图片数；
- `addedCount`：本次实际加入共享池的唯一内容数；
- `duplicateCount`：与既有池或本批其他图片内容相同的数量；
- `invalidCount`：无法安全读取或解码的数量；
- `truncated`：是否达到文件或共享池上限。

无图片、全重复、全无效和零新增都必须调用一次最终进度报告并进入 `completed`。前端任务组件还应根据任务状态提供状态化后备文案：只有 `queued/running` 可回退到“正在收集候选…”，`completed` 的空消息必须回退为“候选收集完成”，形成前后端双重防护。

## 7. 前端交互

### 7.1 候选画廊

- Pinia store 增加会话级 `includeUsedDirectoryCandidates`，默认 `false`，不写入全局配置。
- 切换游戏或切换“显示已使用图片”后重新请求当前游戏候选。
- 共享候选卡片沿用现有图片、尺寸、来源和证据布局；已使用项额外显示“已用于：A、B”。
- 已使用项保持可点击和可采用，不做隐式确认；用户开启显示开关本身即为查看和复用意图。
- 预览图片增加浏览器惰性加载，减少大共享池首次渲染时的解码压力。
- 采用请求使用点击时捕获的 `gameId` 和 `candidateId`，响应回来前若会话或选择已经改变则丢弃陈旧视图更新。

### 7.2 队列状态

队列中的 `candidateCount` 是当前可见候选数：游戏专属候选加默认未使用共享候选。共享池非空时，尚未采用或跳过的游戏可以显示 `ready`，但不会自动选择图片。采用或复用共享图片后，后端快照重新计算其余队列项的可见候选数。

“显示已使用图片”只改变当前画廊，不改变队列默认计数和状态，避免所有游戏因开启临时开关而产生大范围状态跳动。

### 7.3 多次导入与关闭

- 再次点击“导入封面目录”执行合并导入，不替换已有共享池。
- 本轮不增加单独“清空共享池”按钮；关闭向导即清理整个短生命周期会话。
- 活跃导入期间继续禁用其他来源操作和关闭前确认，复用现有互斥与取消流程。
- 导入完成摘要保留在任务面板，直到下一次来源任务开始或向导关闭。

## 8. 安全与隐私

- 导入只由用户点击并通过系统目录选择器批准后执行。
- 程序不递归扩展授权范围，不读取图片以外文件，不上传图片、路径、文件名或 hash。
- 外部源始终只读；采用动作把解码后的封面写入程序自己的 `data/covers`，绝不移动或删除源文件。
- 预览仍只通过随机会话令牌和现有回环资源服务暴露，前端不能构造任意本地路径。
- 关闭、取消和异常清理只允许删除当前会话目录内的临时预览；必须保持现有路径边界验证。

## 9. 兼容性与迁移

- SQLite schema 保持 4，配置版本保持 6。
- 旧数据库、现有封面和现有候选来源无需迁移。
- `cover_directory` 从“按标题过滤并预绑定游戏”改为“共享、人工采用、标题只排序”，属于本轮明确的产品语义变化。
- 现有前端桥接调用需要随 `includeUsed` 和显式采用 `gameId` 同步升级；源码和 V0.3.6 生产 UI 必须同时构建，不保留旧调用兼容分支。
- 共享池不跨向导或程序重启恢复；用户需要重新选择外部目录。

## 10. 测试策略

### 10.1 Python 单元与集成测试

- hash、UUID、截图编号和低相似文件名全部进入共享池。
- 精确、规范化和模糊匹配只改变当前游戏投影的顺序，不过滤低分项。
- 同一共享池对不同游戏产生不同排序，但共享候选 ID、预览和 SHA-256 保持一致。
- 同目录重复内容、本批重复内容及第二次导入按 SHA-256 去重。
- 共享候选采用后默认隐藏；开启 `includeUsed` 后返回使用游戏信息并允许复用。
- 采用明确校验 `gameId`；游戏专属候选不能跨游戏采用。
- 采用成功、数据库失败、源文件删除和源内容改变分别保持正确状态。
- 坏图、超限图和不可读单文件被隔离；目录不存在、不是目录或不可枚举产生稳定失败。
- 取消和异常清理未发布预览并保留既有共享池。
- 1,000 张共享上限、5,000 文件检查上限和截断摘要稳定。
- 零文件、零新增、全重复和全无效任务均完成并具有完成消息。
- 关闭会话清理临时预览但保留外部原图。

### 10.2 前端测试

- 导入目录后当前游戏显示所有未使用共享图片。
- 切换游戏触发重新排序和候选刷新。
- “显示已使用图片”默认关闭、开启后显示使用标记并允许复用。
- 采用请求包含捕获的 `gameId + candidateId`，成功后进入下一游戏。
- 二次导入保留既有共享候选和完成摘要。
- `queued/running/completed/failed/cancelled` 使用正确后备文案；完成空消息不得显示“正在收集候选…”。
- 大候选列表的图片使用惰性加载，滚动和当前选择行为保持稳定。
