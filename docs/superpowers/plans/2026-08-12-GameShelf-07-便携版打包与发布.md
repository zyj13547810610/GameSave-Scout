# GameShelf 便携版打包与发布

> 文档性质：固定模块设计与发布基准；适用版本：V0.1 首个可分发版本；最后更新：2026-08-15；状态：发布设计已确认，待实施。

## 1. 发布目标与已确认边界

V0.1 产出 Windows 10/11 x64 可直接解压运行的 PyInstaller onedir 便携包：

- 用户不需要安装 Python、Node.js、Visual Studio 或项目依赖。
- 完整包自带 Microsoft Fixed Version WebView2 Runtime x64，可在没有系统 WebView2、没有网络的电脑上运行。
- 配置、数据库、封面、清单、日志和 WebView 用户数据都位于 `GameShelf.exe` 旁的 `data`。
- 整个程序目录在退出 GameShelf 后可以复制到其他本地磁盘位置继续使用。
- 发布物包含 MIT 许可证、第三方声明、构建清单和可独立验证的 SHA-256。

首版明确只做以下交付物：

- 一个完整离线 onedir 目录。
- 一个由该目录生成的 zip。
- 一个记录 zip SHA-256 的文本文件。

首版不制作 onefile、安装器、自动更新器和精简开发包，不上传产物，也不自动创建公开 Release。V0.1 不加入数据库迁移流程，开发阶段按新建数据库处理。

## 2. 当前基础与待实施范围

当前已经具备：

- 冻结模式下，可写 `data` 根目录会解析到 `GameShelf.exe` 所在目录。
- 源码模式和冻结模式都不依赖当前工作目录。
- Vue 生产构建可以生成到 `resources/ui`。
- `python -m gameshelf --smoke-test` 可以无窗口初始化应用和数据库并关闭资源。
- pywebview 用户数据目录已经指向 `data/webview`。
- Windows CI 已覆盖 Python 测试、Ruff、mypy、前端测试、类型检查和生产构建。
- 仓库已有第三方声明和 Ludusavi 许可证材料。

本模块待实施：

- 统一的源码/冻结只读资源定位与启动校验。
- 固定版 WebView2 的构建输入校验、解压、随包放置和运行时选择。
- PyInstaller 依赖、`GameShelf.spec` 和无控制台 onedir 构建。
- 单一 PowerShell 构建入口、最小 Python 发布辅助函数和相关测试。
- 冻结程序结构化冒烟测试、发布清单、MIT 许可证、第三方声明补充、zip 和 SHA-256。
- 干净 Windows 10/11 x64 环境中的人工验收。

## 3. 发布物结构

构建完成后的本地输出为：

```text
dist/
├─ GameShelf-0.1.0-win-x64/
│  ├─ GameShelf.exe
│  ├─ _internal/
│  │  └─ resources/              # UI、引擎规则、内置 Ludusavi 等只读资源
│  ├─ runtime/                   # 固定版 WebView2，根部包含 msedgewebview2.exe
│  ├─ README.txt
│  ├─ LICENSE
│  ├─ THIRD_PARTY_NOTICES.md
│  └─ release-manifest.json
├─ GameShelf-0.1.0-win-x64.zip
└─ GameShelf-0.1.0-win-x64.zip.sha256
```

发布目录不包含 `data`。首次正常启动时，程序才在 `GameShelf.exe` 旁创建 `data`。构建和压缩过程不得把开发机上的数据库、配置、封面、游戏、存档或其他本地用户数据带入发布物。

## 4. 资源与运行时定位

### 4.1 `ResourcePaths`

增加统一的只读资源定位组件 `ResourcePaths`：

- 源码模式读取仓库内的 `resources`。
- PyInstaller 冻结模式读取 `_internal/resources` 对应的冻结资源根目录。
- 应用代码不再各自推断 UI、引擎规则或 Ludusavi 种子位置，也不从系统 `PATH` 查找项目资源。
- 启动和冒烟测试一次性校验关键资源，错误信息应指出缺少的逻辑资源名称。

可写数据继续由现有应用路径组件定位到程序旁的 `data`，不得写入 `_internal/resources`。

### 4.2 `WebViewRuntime`

增加固定版 WebView2 定位组件 `WebViewRuntime`：

- 冻结版只接受 `GameShelf.exe` 旁的 `runtime`，并至少验证 `runtime/msedgewebview2.exe` 存在。
- 在创建 pywebview 窗口前设置固定运行时路径。
- WebView 用户数据仍写入 `data/webview`。
- 源码开发模式继续使用系统 WebView2，不要求仓库存在 `runtime`。

V0.1 仅支持本地文件系统路径。程序位于 UNC 或网络共享路径时直接拒绝启动，并提示用户将完整目录复制到本地可写位置；首版不回退到 Evergreen Runtime。

### 4.3 `FrozenStartupReporter`

正式 exe 使用无控制台窗口模式。冻结版在关键资源、固定运行时、程序目录可写性或早期初始化失败时，应通过原生 Windows 消息框显示可操作错误，不能只产生用户看不到的 traceback。

## 5. 固定版 WebView2 输入策略

构建者手动从 Microsoft 官方来源下载指定版本的 Fixed Version WebView2 Runtime x64 归档，再把本地归档绝对路径传给构建脚本：

```powershell
scripts/build_release.ps1 -WebView2Archive <归档绝对路径>
```

仓库内的受版本控制发布配置记录唯一允许的 WebView2 版本和归档 SHA-256。构建脚本必须：

1. 验证输入文件存在且是本地文件。
2. 计算 SHA-256 并与固定值比较，失败立即停止。
3. 使用 Windows 本机可用方式解压到构建暂存区。
4. 将归档内部目录规范化为发布目录的 `runtime`，并验证其根部存在 `msedgewebview2.exe`。
5. 保留运行时归档中随附的许可证材料。

脚本不自动联网下载、不维护下载缓存、不实现多版本管理。固定版本升级通过人工下载新归档、核验来源并更新受控版本和哈希完成。

## 6. 单一构建入口与流水线

V0.1 只提供一个用户入口 `scripts/build_release.ps1`，配合一个 `GameShelf.spec`。为避免在 PowerShell 中重复实现易错的版本、路径、哈希和 JSON 逻辑，可以使用一个最小的 `scripts/release_tools.py`，但不拆分出更多用户入口脚本。

构建脚本按以下顺序执行：

1. 验证当前系统为 Windows x64，Python 为 3.12 x64，Node 为 24，并检查 npm、锁文件、仓库根目录和 WebView2 归档输入。
2. 验证 `pyproject.toml`、`src/gameshelf/__init__.py` 和 `frontend/package.json` 中的应用版本完全一致。
3. 运行现有全部 Python 和前端质量门禁，并生成最新 UI 生产资源。
4. 使用 `GameShelf.spec` 在 `build/release` 暂存区生成无控制台 onedir 产物。
5. 校验并解压固定版 WebView2，将运行时和许可证材料放入暂存产物。
6. 写入 `LICENSE`、`THIRD_PARTY_NOTICES.md`、`README.txt` 和 `release-manifest.json`。
7. 把暂存产物复制到独立临时目录，对副本执行冻结版结构化冒烟测试；原始待压缩目录不得被首次运行产生的 `data` 污染。
8. 只有前述步骤全部成功后，才替换 `dist` 中当前版本的目录，生成 zip 并写出 zip SHA-256。

构建失败时保留 `build/release` 中有助于诊断的暂存结果，并保留 `dist` 中上一次成功产物。构建脚本不得上传、暂存或提交 Git 内容，也不得改写 Git 历史。

开发工作区存在未提交修改时允许生成本地候选包，但 `release-manifest.json` 必须记录 `gitDirty: true`。正式对外分发前应在干净工作区重新构建。

## 7. PyInstaller 约束

- 目标架构仅 Windows x64。
- 使用 onedir 和 `--windowed` 等效的无控制台窗口入口，不制作 onefile。
- 显式收集 pywebview 后端、Pillow 插件、PyYAML、pefile、证书和项目只读资源。
- 只读项目资源进入 `_internal/resources`；固定版 WebView2 位于 exe 旁的 `runtime`；运行时生成的 `data` 不进入产物。
- 构建产物不得依赖开发机绝对路径、虚拟环境、Codex 专用运行时位置或当前工作目录。
- 发布入口版本与 Python 包版本保持一致。
- `GameShelf.spec` 是唯一的 PyInstaller 正式配置来源。

## 8. 冻结版启动诊断与冒烟协议

现有文本冒烟模式继续保留。新增适合无控制台 exe 的文件输出协议：

```powershell
GameShelf.exe --smoke-test --json-output <绝对临时文件路径>
```

成功时退出码为零，并向指定文件写入至少包含以下信息的 JSON：

```json
{
  "ok": true,
  "appVersion": "0.1.0",
  "schemaVersion": 1,
  "frozen": true,
  "appRoot": "D:\\Temp\\GameShelf-0.1.0-win-x64",
  "dataDir": "D:\\Temp\\GameShelf-0.1.0-win-x64\\data",
  "resources": {
    "ui": true,
    "engineRules": true,
    "ludusaviSeed": true,
    "webView2Runtime": true
  }
}
```

构建脚本在发布目录副本中运行该命令，校验退出码、JSON 可解析性、版本、冻结状态、路径和所有关键资源结果。测试产生的 `data` 和 JSON 输出只存在于临时副本，验证后删除，不污染原始发布目录。

## 9. 发布清单、版本与哈希

`release-manifest.json` 使用 `formatVersion: 1`，至少记录：

- GameShelf 版本、UTC 构建时间、Git 提交号和 `gitDirty`。
- 目标平台 `windows-x64`。
- Python、Node、npm、PyInstaller 和 pywebview 版本。
- 数据库架构版本和引擎规则版本。
- Ludusavi SHA-256 与已记录的上游提交号。
- WebView2 版本和输入归档 SHA-256。
- `fixedRuntime: true` 和 `signed: false`。
- `GameShelf.exe`、关键只读资源和 `runtime/msedgewebview2.exe` 的实际 SHA-256。

zip 的 SHA-256 写在旁边的 `.sha256` 文件中，不写回 zip 内的发布清单，避免循环依赖。生成 zip 后必须重新打开归档验证关键文件存在，再独立重算一次 SHA-256 并与 `.sha256` 内容比较。

版本必须由以下三个受版本控制位置共同校验，不允许静默选取其中一个覆盖其他位置：

- `pyproject.toml`
- `src/gameshelf/__init__.py`
- `frontend/package.json`

## 10. 许可证、第三方声明与签名

GameShelf V0.1 使用 MIT License。仓库根目录和发布目录都包含 `LICENSE`，版权行为：

```text
Copyright (c) 2026 GameShelf Contributors
```

仓库中的 `THIRD_PARTY_NOTICES.md` 作为固定维护文件，首个 PyInstaller 实际产物生成后，按真正随包分发的 Python、Vue、Pinia、Ludusavi、WebView2 等组件人工核对并补齐。V0.1 不引入自动许可证爬取器；运行时原归档自带的许可证文件同时保留。

首个版本不进行 Authenticode 签名，发布清单明确记录 `signed: false`。构建流水线预留“产物完整、压缩前”的未来签名点，但 V0.1 不要求证书或签名工具。发布说明应提示用户：未签名的新版本可能触发 Microsoft Defender SmartScreen 的“Windows 已保护你的电脑”或未知发布者提示，并且不同文件哈希的版本需要分别积累信誉。

## 11. 文件系统安全边界

构建脚本只允许清理或替换以下已解析的仓库内目标：

- 仓库内固定的 `build/release`。
- `dist` 内与当前应用版本完全匹配的目录。
- `dist` 内与当前应用版本完全匹配的 zip 和 `.sha256`。

执行删除或替换前必须验证目标为绝对路径、父目录正确、仍位于预期仓库目录内，并拒绝重解析点、未经解析的变量、通配符和过宽目标。不得递归清理仓库根目录、用户目录、程序 `data`、外部 WebView2 归档或其他用户指定目录。

`.gitignore` 应忽略 `build/`、`dist/` 和约定的本地发布输入位置。构建日志不得输出用户游戏路径或 `data` 内容，也不得把商业游戏、用户封面或存档复制进构建区。

## 12. 自动验证与人工验收

### 12.1 自动验证

发布实现至少覆盖以下层次：

1. 单元测试：`ResourcePaths` 的源码/冻结/缺失资源，UNC 拒绝，固定运行时缺失，版本不一致，归档哈希不一致，危险清理目标拒绝和发布清单生成。
2. 全部现有质量门禁：Python 测试、Ruff、mypy、前端单元测试、TypeScript 类型检查、Vite 生产构建和源码冒烟。
3. 真实 PyInstaller 构建：对独立副本执行冻结版 JSON 冒烟，并确认所有写入仅发生在副本的 `data`。
4. 发布物完整性：正式目录没有 `data`，zip 可重新打开，关键文件齐全，独立重算哈希与 `.sha256` 一致。

本机开发与构建默认使用项目内 Conda prefix（`.venv`）提供的 Python 3.12 和 Node.js 24；正式构建入口仍必须显式校验 Node 主版本为 24，不能依赖 Codex 或某台开发机的私有 Node 路径。

### 12.2 人工验收

自动构建成功只表示“候选包已生成”。V0.1 标记为可分发前，还必须完成：

- 干净 Windows 10 和 Windows 11 x64 环境，无 Python、Node、Visual Studio 和系统 WebView2，全程离线启动。
- 中文、日文、空格路径，以及退出后跨盘符复制整个目录再启动。
- UNC/网络路径、只读目录、固定运行时缺失或损坏时显示明确的原生错误。
- 首次启动、退出后再次启动、删除整个目录即可卸载，不在系统其他位置遗留 GameShelf 自有数据。
- 添加游戏根目录、扫描、启动游戏、封面、引擎识别、静态存档查找和引导式寻找存档的主流程。
- 模块 06 已保留的真实游戏、任务管理器资源占用和多缩放人工验收。
- 首版未签名程序的 SmartScreen 实际提示与发布说明一致。

## 13. 实施顺序

1. 以测试驱动方式实现 `ResourcePaths`、`WebViewRuntime`、冻结启动错误显示和结构化冒烟协议。
2. 添加 PyInstaller 构建依赖、`GameShelf.spec` 和最小发布辅助函数。
3. 实现 `scripts/build_release.ps1` 的环境、版本、输入哈希和安全路径校验。
4. 接入 WebView2 解压、许可证、发布清单、冻结副本冒烟、zip 和 SHA-256。
5. 运行全部自动门禁，核对实际冻结依赖并更新第三方声明。
6. 完成干净 Windows 10/11 x64 和模块 06 的人工验收后，更新路线图状态。

一次性详细实施计划放入 `docs/历史归档`；后续缺陷修复和需求变化继续直接维护本文，不为每个小改动新建固定设计文档。
