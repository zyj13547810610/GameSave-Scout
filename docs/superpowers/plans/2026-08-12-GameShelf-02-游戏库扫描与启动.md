# GameShelf 游戏库扫描与启动

> 文档性质：当前有效的模块设计与验收基准；适用版本：V0.1 及后续增强；最后更新：2026-08-18；状态：V0.1 核心能力、事务式批量管理、标题与版本号分离，以及增量扫描与分析缓存均已实现。

## 1. 模块目标

用户可以配置多个本地游戏根目录，扫描其中的游戏文件夹，维护安装状态并从 GameShelf 安全启动游戏。游戏发现不依赖特定商店，也不以成功识别引擎为前提。

扫描只读取目录结构、文件名、文件大小和有限元数据，不执行发现的 EXE，也不修改游戏目录。

## 2. 多根目录

`scan_roots` 支持任意多个根目录。每个根目录独立保存：

| 字段 | 含义 |
| --- | --- |
| `id` | 稳定 UUID |
| `display_path` | 用户选择的原始可读路径 |
| `path_key` | Windows 规范化去重键 |
| `enabled` | 是否参与启动扫描和手动扫描 |
| `scan_mode` | `children` 或 `recursive` |
| `max_depth` | 递归模式最大深度，1～8 |
| `exclusions` | 相对路径或 glob 排除规则 |
| `last_scanned_at` | 最近成功完成扫描时间 |
| `last_scan_status` | 最近扫描状态 |
| `last_error` | 最近错误摘要 |

根目录按规范化路径去重。允许根目录嵌套；如果一个游戏路径同时属于多个启用根目录，最长、最具体的根目录拥有该游戏，避免重复记录。

### 示例

```text
D:\文件夹A\游戏A
D:\文件夹A\游戏B
D:\文件夹A\分类AA\游戏C
D:\文件夹B\游戏D
```

可以把 `D:\文件夹A` 和 `D:\文件夹B` 分别添加为根目录。前者使用递归模式时可发现 A、B、C；后者可独立选择直接子目录或递归模式。

## 3. 扫描模式

### 3.1 直接子目录

- 根目录下每个可访问的直接子目录都作为一个游戏候选。
- 不要求候选目录中存在 EXE。
- 不继续进入更深层目录。
- 适合 `D:\Games\游戏名` 这种结构统一的游戏库。

这种模式可能把工具目录识别为游戏，但不会因为非标准游戏没有明显 EXE 而漏掉整个文件夹。

### 3.2 递归扫描

- 从根目录向下搜索，最大深度为 1～8。
- 当前文件夹存在至少一个“潜在游戏 EXE”时，将它作为候选，并停止扫描其后代目录。
- 当前文件夹没有 EXE，或只有明确的辅助 EXE 时，继续向下扫描。
- 只检查当前层的文件来决定是否剪枝，不运行 EXE。

明确辅助 EXE 包括安装器、卸载器、更新器、崩溃处理器、`config.exe`、`UnityCrashHandler`、`UnrealCEFSubProcess`、`delfile`、`chromedriver`、Textractor 和特定反作弊安装程序等。名称规则由目录发现器和主程序排序器共用。

该规则解决以下两种情况：

- `D:\文件夹A\分类AA` 没有游戏 EXE，会继续发现 `分类AA\游戏C`。
- 中间目录只有 `setup.exe` 或崩溃处理器时，不会阻断更深层的真实游戏。

如果中间目录确实存在一个未被识别为辅助程序的普通 EXE，当前实现仍会把中间目录作为游戏并停止向下。这是递归模式的已知启发式限制。

## 4. 排除规则

每个根目录拥有独立排除项：

- 普通相对路径同时排除自身及后代。
- glob 使用 `/` 或 `\` 都可以，匹配时不区分大小写。
- `Mods` 可排除根目录下的同名目录，`**/Mods` 可排除更深层目录。
- 符号链接和 Windows 重解析点不会被递归跟随。

主程序排序器无条件跳过候选游戏目录内的 `Mods`、`redist`、`_CommonRedist`、`runtime`、`tools` 和 `support` 子树。扫描发现器不会无条件忽略所有 `Mods` 目录，因为某些用户可能把独立游戏放在这种目录结构中；需要时应使用根目录排除规则。

根目录列表提供设置入口，可编辑扫描模式、递归深度和排除规则。误操作加入的排除项可以在这里删除，保存后重新扫描即可让目录再次出现。

本轮性能优化设计确认：新建根目录时，界面默认填入 `Mods` 和 `**/Mods` 两条普通排除规则，用户可以在首次保存前或以后设置中删除。规则不扩展为 `mod*`，避免误排除 `Models`、`Modules`、`Modern` 等真实目录；现有根目录不做迁移，开发阶段由用户重建可舍弃数据库。

## 5. 主程序推荐

扫描器会在候选游戏目录内查找可能的 EXE，并按稳定规则排序：

- 明确辅助程序直接排除。
- 根目录 EXE 优先，嵌套越深越降权。
- `Source`、`Debug`、`obj`、`_redist` 等工具路径降权。
- 文件名与游戏目录名精确、相似或有足够长标题片段时加分。
- PE 产品名或文件描述与游戏目录名相似时加分。
- Unity 的 `UnityPlayer.dll + 同名 _Data/globalgamemanagers` 运行时结构提供强证据。
- Unreal 启动器和 `*-Win64-Shipping.exe` 结构提供强证据。
- 文件大小只提供很小的辅助分数，不能主导结果。

排序相同时按相对路径稳定排序。自动第一名写入 `detected_main_exe_relpath`，用户采用的入口写入 `main_exe_relpath`。

用户可手动选择游戏目录内现存的 `.exe`。手动值在重新扫描和确认移动后保留；引擎检测优先使用仍然有效的手动 EXE。自动建议继续单独更新，便于解释和回退。

## 6. 扫描会话与状态核对

扫描分为两条语义明确的路径：

- `quick`：启动时只核验数据库中已经属于该根目录的游戏；直接子目录和递归根目录行为一致，不枚举未知目录、不发现新游戏。
- `full`：用户点击根目录“扫描”或新建根目录后触发；按根目录模式重新发现候选，新增游戏，并在成功后核对真正消失的游戏。

全局“启动时快速核验游戏”保存在 `data/config.json`，默认开启。关闭后程序启动只读取数据库，不访问游戏目录；开启后只为勾选“参与扫描”的根目录提交 `quick`。根目录关闭“参与扫描”时不参加启动核验，手动“扫描”按钮禁用，后端也必须拒绝扫描请求。新建根目录的“添加并扫描”在保存成功后立即启动一次 `full`，使按钮名称与实际行为一致。

### 6.1 增量分析缓存（已实现）

扫描仍使用 `os.scandir()` 确定性发现目录；性能优化不替换为递归 glob。真正需要避免的是对每个未变化游戏重复执行 `os.walk()`、读取所有候选 EXE 的 PE 元数据和重新识别引擎。

新建数据库直接包含独立的 `game_analysis_cache` 表。缓存以游戏 ID 为主键，至少保存实际分析的主程序相对路径、文件大小、纳秒修改时间、主程序排序规则版本、引擎规则版本和分析时间。正式主程序、引擎和证据仍保存在 `games`；缓存只是可丢弃的复用依据，删除游戏时级联删除。开发阶段不为现有数据库编写升级或回填逻辑，程序也不得自动删除 `data/library.db`，由用户在实施后自行重建。

缓存决策固定为：

- 主程序路径、大小、修改时间和两类规则版本均一致时，复用已有自动分析结果，不调用 EXE 排序器、PE 读取或引擎识别器。
- 主程序仍存在但文件大小或修改时间变化时，只重新读取当前 EXE 并识别引擎，不遍历整个游戏目录。
- 只有主程序消失、主程序排序规则变化、新游戏、缓存缺失，或用户主动“重新检测主程序和引擎”时，才完整遍历候选目录并重新排序 EXE。
- 只有引擎规则版本变化时，只重新识别当前有效 EXE。
- 无有效 EXE 的游戏不建立可复用命中；后续核验仍允许重新发现主程序。
- 游戏确认移动、根目录重映射或用户重新选择主程序后使对应缓存失效。

文件指纹有意只覆盖当前主程序，不递归记录整个游戏目录。Unity、Ren'Py 等引擎的外部辅助文件单独变化、但主程序及规则版本均未变化时，正常扫描会继续复用缓存；用户认为游戏内容已经变化或需要重新取证时，使用详情中的“重新检测主程序和引擎”执行无缓存完整分析。该边界避免为了捕捉低频外部变化而重新引入每次扫描遍历整个目录的成本。

缓存结果与扫描观察结果在同一核对事务中提交。扫描取消、失败或根目录不可访问时，临时观察与待写缓存一起放弃；分析失败保留上一次有效自动结果，不写入新缓存。手动主程序和手动引擎继续受现有标记保护，缓存命中、缓存失效和单游戏强制检测都不得覆盖人工值。

### 6.2 路径状态与失效判定

快速核验先确认根目录状态，再检查已知游戏：

- 根目录不存在、磁盘未挂载、权限不足或其他原因导致根目录不可访问时，根目录卡片显示持久错误并提供“重映射”和“删除”；其下游戏状态保持不变，避免整盘离线造成批量误判。
- 根目录可访问，而单个已知游戏目录明确返回不存在或已经不再是目录时，`quick` 可以在本次成功事务中把该游戏标为 `missing`。
- 单个游戏目录发生权限或其他无法区分“消失/暂时不可读”的 I/O 错误时，保留原状态并记录警告。
- 已失效游戏目录重新出现时，快速核验可以恢复为 `installed`；新路径和新游戏仍只能由 `full` 发现。
- `full` 只有完整成功后才统一标记所有未观察到的安装为 `missing`；取消或失败不改变可见游戏状态。

### 6.3 全局共享并发与进度

扫描分析使用独立的全局共享工作池。并发数保存到 `data/config.json`，允许 `1～4`，默认 `1`；非法值规范化为 `1`。单根目录和多个同时扫描的根目录共用同一上限，不得按根目录分别创建工作池。目录发现保持稳定顺序，候选游戏的 EXE 搜索、PE 读取和引擎识别进入共享池；SQLite 仍由现有单写线程提交。设置变更从下一次扫描开始生效，封面与存档任务不计入此上限。

`quick` 的已知游戏总数可提前取得，使用确定进度；`full` 的目录发现总量未知时继续使用不确定进度，完成发现后按候选总数显示确定的分析进度。准备、发现、核验、分析和核对等所有活动阶段都显示后端报告的当前耗时，不能只在最终摘要显示耗时。进度详情和结束摘要分别记录已核验、缓存复用、重新分析、完整分析、不可访问和警告数量；缓存计数不改变新增、更新、失效等业务统计。

### 6.4 单游戏重新检测

游戏详情“游戏设置”提供“重新检测主程序和引擎”。操作进入同一个全局扫描分析池，只处理当前游戏，忽略缓存并完整搜索 EXE；成功后原子更新自动建议、自动引擎结果和缓存。人工主程序、人工引擎、标题、版本号和启动参数均保持不变。任务失败或取消时保留原结果并显示稳定错误。

## 7. 游戏身份、重叠与移动

- 安装路径使用 Windows 规范化键全库去重。
- 相同根目录内的相对路径也有唯一约束。
- 标题、版本号、主程序和引擎的手动值与自动检测值分开保存。
- 重新扫描不能覆盖有效手动值。
- 新候选与失效游戏的标题及 EXE 名足够相似时，可提出移动建议。
- 只有用户确认移动后，才把旧游戏 ID 迁移到新路径；封面、存档位置和手动配置随旧 ID 保留。

移动建议只是启发式结果，不自动合并记录。

### 7.1 标题与版本号分离（已实现）

游戏作品名与发行版本是两个独立元数据。`title` 只保存作品名；可空的 `version` 保存版本号。数据库同时保存 `detected_title`、`detected_version`、`title_is_manual` 和 `version_is_manual`，使重新扫描可以分别更新自动值，又不会覆盖用户手动修改或主动清空的版本号。界面需要组合展示时在运行时生成，不在数据库中持久化第三份拼接标题。

数据库已升为 schema 2。结构升级只增加 `version`、`detected_version` 和 `version_is_manual` 等必要字段，不解析、不拆分也不回填 schema 1 中已有的标题。升级后的后续成功扫描会对本次观察结果应用新拆分规则，并只更新未被人工保护的字段；开发阶段可由用户自行重建可舍弃数据库，不提供一次性旧数据整理工具。`title_is_manual` 与 `version_is_manual` 相互独立：用户手动清空版本号也视为明确设置，后续扫描不得自动填回。

扫描器取得候选目录末级名称后，只调用一次无文件系统副作用的 `split_title_and_version(raw_name)`。拆分保守且只匹配字符串末尾明确的版本标记，标记不区分大小写，包括 `v`、`ver`、`version` 和 `build`；标记与作品名之间允许空格、点、下划线、短横线或中英文括号。拆分后标题不能为空，版本号保留用户目录中的原始大小写与数字写法，但不包含用于分隔作品名的标点或外层括号。

应当拆分的代表样本包括：

- `AoiChan.v1.0.8` → `AoiChan` / `v1.0.8`。
- `Game Name - Ver 1.42` → `Game Name` / `Ver 1.42`。
- `作品名（version 2.0）` → `作品名` / `version 2.0`。
- `Title_build_1234` → `Title` / `build_1234`。

裸数字、年份、`DLC`、`PC`、`x64`、`Final` 或其他没有明确版本标记的尾缀不得自动拆分。例如 `Need for Speed 21 Heat`、`Resident Evil 4` 和 `Game 1.05` 都保持原样；无法确定时宁可不拆，由用户在游戏设置中手动调整。

游戏设置通过单个原子命令同时保存标题和可空版本号。标题去除首尾空白后不能为空；版本号只去除首尾空白，空字符串规范化为 `NULL`。任一字段验证或数据库写入失败时两个字段都不改变。重新扫描分别遵守标题与版本号的手动标记；确认移动继续保留旧游戏 ID 上的人工元数据，并刷新新目录对应的两个检测值。

## 8. 根目录删除与重映射

- “重映射”用于整个游戏库搬盘后更换根路径，同时重新计算所属游戏路径键。
- 删除根目录不会删除游戏文件、封面或存档。
- 当前实现会把该根目录下的游戏全部改为 `missing`，并移除它们与根目录的关联。

详情抽屉的危险操作区按状态提供不同操作：

- 已安装游戏使用“从库中移除并忽略”。后端在一个事务中把该游戏的精确相对路径加入当前根目录排除项并删除游戏记录，避免下次扫描立即重新加入。
- `missing` 游戏使用“删除失效记录”，只删除已失效记录，不能借此删除仍安装的游戏。
- 两项操作都要求明确确认；删除记录会级联删除其库内存档位置，并清理 GameShelf 管理的封面文件，不删除游戏目录或用户原始封面。
- 根目录设置可以继续编辑排除项，删除误加规则后重新扫描即可恢复收录。

“删除根目录”的既有语义不变：移除根目录配置并把原属游戏标记为 `missing`，不等同于逐个“移除并忽略”。

### 8.1 事务式批量处理

主页批量管理通过一个 `remove_games` 桥接接口提交项目数组，前端不循环调用现有单条接口。每项包含非空 `gameId` 和确认时看到的 `expectedStatus`；原始数组必须有 1～500 项。后端按 ID 去重，相同 ID 与相同预期状态只处理一次；同一 ID 出现冲突状态则拒绝整批。携带预期状态是为了让后端能够发现确认框出现后发生的 `installed`/`missing` 状态变化。

后端把以下操作放在同一个数据库写入任务和 `BEGIN IMMEDIATE` 事务中：

1. 在同一写事务中读取全部去重后的游戏记录，任一 ID 不存在便拒绝整批。
2. 验证当前状态必须等于 `expectedStatus`，且只能是 `installed` 或 `missing`；`save_only` 不能借此删除。
3. 对每个已安装项目重新验证所属根目录存在、相对路径非空且不能为绝对路径或越过根目录。
4. 按根目录合并精确排除项，每个受影响根目录只更新一次。
5. 在删除前记录 GameShelf 受管封面的相对路径，然后删除全部游戏记录；外键负责级联删除库内存档位置等关联记录。
6. 内部事务结果返回已安装处理数、失效处理数、更新根目录数和待清理封面路径。

任一验证或数据库操作失败时事务整体回滚，不更新任何排除项、不删除任何游戏记录。数据库提交成功后，封面服务才逐个清理记录下来的受管封面；路径必须继续通过 `data/covers` 边界验证。公开接口只返回处理计数、更新根目录数和 `cleanupWarnings`，不向前端暴露内部文件路径。封面文件删除失败只记录日志并返回警告，不回滚数据库，也不接触用户最初导入的图片、游戏目录或外部存档。

批量操作与扫描共享同一个数据库写入线程。扫描核对不能仅使用扫描开始时的排除项快照：提交观察结果前必须重新读取根目录最新排除项，并跳过已经被精确排除的观察结果，防止进行中的扫描在批量删除提交后把游戏重新加入。

如果确认后记录不存在、状态变化或路径验证失败，接口返回稳定的“批次已过期”类错误。前端刷新一次游戏库、清空旧选择并提示用户重新选择，不接受部分成功。

详情抽屉现有两个单条接口保持对前端的公开合约；实现时复用同一事务命令和提交后封面清理辅助逻辑，避免单条与批量入口形成不同的安全顺序。

## 9. 游戏启动

每个游戏可保存：

- 主 EXE 相对路径。
- 工作目录相对路径。
- 参数数组。
- 环境变量覆盖。

启动前重新验证：

- 游戏状态必须为 `installed`。
- 安装目录和主 EXE 必须存在。
- EXE 与工作目录不能越过游戏目录。
- 环境变量名称和值不能包含非法 NUL，名称不能包含 `=`。

Windows 启动适配器使用参数数组和 `shell=False`，不拼接命令行交给 shell。启动成功后记录 PID 和 `last_launched_at`。GameShelf 当前不注入、Hook 或控制游戏进程。

## 11. 验收基准

- 可添加多个互不相同的根目录，并独立启用、扫描和重映射。
- 直接子目录模式只产出第一层可访问目录。
- 递归模式能发现分组目录下的游戏，并遵守最大深度。
- 只有辅助 EXE 的中间目录会继续向下扫描。
- 普通游戏 EXE 所在目录成为候选并停止向下。
- 排除项、符号链接和重解析点不会被越过。
- 嵌套根目录中的同一游戏只归最具体的启用根目录所有。
- 扫描失败、取消、根目录被删除或盘符离线不会把整批游戏误标为失效，并在根目录卡片保留明确提示。
- 快速核验只检查已入库游戏；根目录可访问且单个游戏目录明确不存在时标为 `missing`，其他 I/O 错误只告警。
- 完整扫描能发现新游戏，并且只有完整成功后才统一标记未观察到的安装为 `missing`。
- 手动标题、手动版本号、主程序和引擎不会被重新扫描覆盖；手动清空版本号后也不会被自动值填回。
- 新扫描只拆分带明确 `v`、`ver`、`version` 或 `build` 标记的尾部版本；裸数字、年份和作品名内数字不会被误拆。
- 标题和版本号由单个原子命令保存，标题为空或写入失败时不产生部分更新。
- 启动不会经过 shell，也不能使用游戏目录外的 EXE 或工作目录。
- 删除根目录后，受影响游戏保留但变为失效。
- 已安装游戏可以原子地从库中移除并加入精确排除项；移除排除项后可以重新扫描恢复。
- 只有 `missing` 记录可以使用“删除失效记录”。
- 批量接口可以混合处理多个根目录下的已安装和失效记录，重复 ID 不重复计数，`save_only` 不参与。
- 任一无效 ID、状态变化、失效根目录或危险相对路径都会让整批回滚；成功时各根目录排除项合并一次且库内关联记录级联删除。
- 进行中的扫描不会重新加入已经由单条或批量操作写入精确排除项的游戏。
- 批量处理不删除游戏目录、外部存档或用户原始封面；受管封面清理失败只返回警告。
- 扫描期间显示不确定进度、当前目录、计数和耗时，结束后保留明确摘要。
- 启动核验可以全局关闭；关闭时只读取数据库，开启时只核验已启用根目录，新建根目录保存后自动完整扫描。
- 缓存命中不调用 EXE 遍历、PE 读取或引擎识别；文件、排序规则或引擎规则变化只执行必要层级的重新分析。
- 扫描并发数为全局共享 `1～4`，默认 `1`；单根目录和多根目录的重型分析总数都不超过设置值。
- 新根目录默认带有可删除的 `Mods` 与 `**/Mods`，不会用 `mod*` 模糊排除其他目录。
- 单游戏强制重新检测只更新自动分析和缓存，不覆盖任何人工配置。

2026-08-18 游戏库增量扫描与缓存实现后的完整自动门禁为 Python 714 项、前端 33 个测试文件共 142 项；快速/完整扫描、缓存分层复用与失效、全局共享并发、事务回滚、路径异常、单游戏重新检测和桥接契约均有自动回归覆盖，Ruff、mypy、Vue 类型检查、生产构建及 schema 2 源码冒烟全部通过。标题与版本号的既有真实目录验收仍有效；本轮大型目录性能、并发 1/2/4 和五档缩放人工验收尚未执行。
