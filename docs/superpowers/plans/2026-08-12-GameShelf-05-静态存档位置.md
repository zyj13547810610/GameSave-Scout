# GameShelf 存档位置管理

> 文档性质：当前有效的模块设计与验收基准；适用版本：V0.1 及后续迭代；最后更新：2026-08-21；状态：核心功能、静态性能索引、引导式寻找存档及 V0.2.1 批量存档使用的 Ludusavi 路径反向索引均已实现；V0.3.0 内置存档规则扩展与后续自定义规则编辑器设计已确认，尚未实施。后续修改直接维护本文，不再为小修复单独新建设计文档或实施计划。

## 1. 模块目标

GameShelf 为每个游戏管理一个或多个存档位置，让用户可以查看、验证并直接打开这些位置。路径既可以由用户手动添加，也可以由静态规则给出候选建议。

本模块只负责“记录存档在哪里”，不读取、复制或修改存档内容。

### V0.1 已实现范围

- 手动添加目录、文件、通配符或注册表形式的存档位置。
- 一个游戏可以保存多个存档位置。
- 显示路径是否存在、匹配文件数和最近验证时间。
- 打开存档目录，或在资源管理器中定位存档文件。
- 删除已记录的位置。
- 用户明确点击“查找存档”后，使用本地静态规则提供候选位置。
- 用户主动开始引导式检测，启动游戏后结合一次实际保存查找未知存档。
- 候选仍须经过审核后才能成为正式存档位置。

引导式寻找存档的详细行为、限制和验收证据见模块 06。

### 后续版本

- V0.2 已实现：批量扫描已知与受限目录，展示所有发现的存档位置，并尝试反推已安装、已删除或未入库游戏。
- V0.3.0：先补强内置游戏专属与引擎通用存档规则，并与引擎识别规则共用来源、状态、校验和诊断基础层。
- V0.3.x 后续：增加独立的自定义引擎与存档规则编辑器。
- 更晚版本：存档备份、恢复、同步和版本管理。

引导式寻找存档已经完成 V0.1 当前范围；批量存档发现的最终设计见模块 06，备份属于后续版本。

## 2. 用户操作流程

### 2.1 手动管理

1. 用户在游戏详情中展开“存档位置”。
2. 选择目录、文件、通配符或注册表位置；目录和文件使用系统选择器。
3. GameShelf 将绝对路径转换成可迁移的路径模板后保存。
4. 已保存位置显示类型、来源、实际路径和存在状态。
5. 用户可以打开、重新验证或移除该位置。

手动添加的位置视为已确认数据，可信度为 `1.0`，静态建议不能覆盖它。

### 2.2 静态查找

1. 打开游戏详情时不自动匹配规则。
2. 展开存档区域时也不自动匹配规则。
3. 只有用户点击“查找存档”后，才加载自定义清单、查询由 Ludusavi 清单派生的 GameShelf SQLite 索引和运行引擎提示；GameShelf 不启动 Ludusavi 程序或调用其命令行接口。
4. 实际存在的位置进入“已找到”；规则可以可靠推导但当前不存在的位置折叠到“可能路径 / 未发现”。可信度、正式或实验状态继续作为候选标签与排序依据。
5. 用户勾选候选项并确认后，候选项才写入数据库。

静态查找是可选辅助。即使规则缺失、损坏或匹配失败，手动管理仍须正常工作。

## 3. 存档位置模型

每条已保存位置包含：

| 字段 | 含义 |
| --- | --- |
| `id` | 稳定 UUID |
| `game_id` | 所属游戏 |
| `kind` | `directory`、`file`、`glob` 或 `registry` |
| `path_template` | 用于迁移和解析的路径模板 |
| `display_path` | 当前电脑上的可读路径 |
| `path_key` | Windows 规范化去重键 |
| `source` | `manual`、`dynamic`、`ludusavi`、`engine` 或 `legacy_scan` |
| `confidence` | 来源给出的可信度 |
| `evidence` | 规则来源和匹配依据 |
| `confirmed` | 是否已由用户确认 |
| `enabled` | 是否启用 |
| `last_verified_at` | 最近验证时间 |

已保存位置按 `game_id + kind + path_key` 去重。静态候选在合并时还会规范化普通文件系统路径的类型，避免同一实际路径因来源表达不同而重复显示；注册表位置单独处理。

## 4. 便携路径模板

程序不直接持久化任意绝对文件系统路径，而是优先折叠成以下模板：

| 令牌 | Windows 位置 |
| --- | --- |
| `<game>` | 当前游戏安装目录 |
| `<home>` | 用户主目录 |
| `<winAppData>` | Roaming AppData |
| `<winLocalAppData>` | Local AppData |
| `<winLocalAppDataLow>` | LocalLow |
| `<winDocuments>` | 文档 |
| `<winSavedGames>` | Saved Games |
| `<winProgramData>` | ProgramData |
| `<winPublic>` | 公共用户目录 |
| `<winDir>` | Windows 目录 |

折叠时选择匹配到的最长根路径，例如 Unity 存档优先表示为 `<winLocalAppDataLow>\厂商\游戏名`。展开时拒绝未知令牌、绝对后缀、UNC、额外嵌套令牌和包含 `..` 的越界路径。

不在这些便携根目录内的路径不自动保存；用户需选择可安全表示的位置。

## 5. 位置类型与打开规则

- `directory`：目录必须存在；点击后在资源管理器中打开。
- `file`：文件必须存在；点击后在资源管理器中定位该文件。
- `glob`：显示当前匹配数量；点击后打开最近的现有父目录。
- `registry`：使用 `HKEY_CURRENT_USER` 或 `HKEY_LOCAL_MACHINE`；手动添加的键必须存在，接受规则建议时需要额外确认，未确认的位置不能打开。

验证操作只更新存在状态、匹配数量和验证时间，不创建目录或文件。通配符匹配数量设置上限，避免异常规则导致无界遍历。

## 6. 静态建议来源

建议来源按以下顺序执行并合并：

1. 用户自定义清单。
2. GameShelf 内置游戏专属规则。
3. GameShelf 当前有效的 Ludusavi 官方清单派生索引。
4. 基于已识别游戏引擎的保守提示。

相同位置由多个来源命中时只显示一次，同时保留所有来源证据，并采用其中更强的分组和最高可信度。数据库中已经存在的位置不再作为建议显示。

### 6.1 内置游戏专属规则

内置游戏专属规则用于补充 Ludusavi 和通用引擎规则未覆盖、但能够从公开资料可靠确认的存档位置。规则使用去除版本号后的游戏标题、稳定产品编号或其他明确身份字段匹配，优先级高于引擎通用规则；仅凭模糊标题不得把专属路径判为高可信命中。

内置规则随 GameShelf 版本发布，不在线更新。每条规则必须记录稳定 ID、来源、正式或实验状态和版本；没有可靠公开依据的游戏不为追求覆盖率添加猜测路径。

### 6.2 Ludusavi 匹配

GameShelf 在更新或恢复重建时只解析与 Windows 有关的 Ludusavi 数据子集，并将其写入摘要绑定的 SQLite 索引；正常查找不解析大型官方 YAML。条目匹配会综合使用游戏标题、安装目录名、可执行文件名和清单别名；规则条件作为候选位置的适用证据展示。

- 确认匹配进入“高可信建议”。
- 模糊匹配进入“可能的位置”。
- 高可信、类别为存档且非注册表的建议可以默认勾选。
- 注册表建议永不默认勾选。
- 建议在用户接受前不写入数据库。

### 6.3 引擎提示

目前引擎提示覆盖：

- Ren'Py：读取脚本中明确的 `config.save_directory` 字符串。
- Unity：从 `*_Data/app.info` 取得公司名和产品名，建议 LocalLow 目录及 PlayerPrefs 注册表键。
- RPG Maker 2000、XP、VX、VX Ace、MV、MZ：只在找到对应世代的现有存档文件时提出建议。
- WOLF RPG Editor：在受限深度和数量内查找已有存档目录或存档文件。
- KiriKiri：只在 `save` 或 `savedata` 目录中发现相应存档文件后提出建议。
- NScripter：只在游戏目录发现 `save*.dat`、`envdata` 或 `kidoku.dat` 后提出建议。

引擎提示必须有本机文件或可靠元数据作为证据，不能只凭“这个引擎通常使用某个目录”就声称已经找到存档。标记为实验性的引擎规则只能进入“实验性引擎建议”。

V0.3.0 在保持上述保守边界的前提下补强 Ren'Py、Unity、Unreal、KiriKiri、NScripter、RPG Maker 和 WOLF，并新增 Godot 通用路径规则。QLIE、Majiro 等同人/Galgame 引擎只有在能够取得可靠路径依据时才增加对应存档规则，不能从引擎名称直接猜测用户目录。

### 6.4 自定义清单

自定义清单位于程序旁的 `data/manifests/custom`，格式与 GameShelf 支持的 Ludusavi 子集兼容。

- 只读取 `.yaml` 和 `.yml`。
- 单个文件最大 8 MiB。
- 最多读取 100 个文件。
- 单个自定义清单损坏时跳过该文件并显示错误，不影响其他清单和手动位置。

## 7. Ludusavi 清单生命周期

### 7.1 三层文件

| 层级 | 位置 | 用途 |
| --- | --- | --- |
| 内置种子 | `resources/manifests/ludusavi` | 首次运行或恢复失败时使用 |
| 当前有效清单 | `data/manifests/ludusavi` | 实际匹配读取 |
| 历史备份 | `data/manifests/ludusavi/previous` | 保留最近两组有效快照 |

官方 `manifest.yaml`、`manifest-meta.json` 和 `manifest-index.sqlite` 作为三件套处理；前两者是可信来源，SQLite 是可删除、可重建的派生索引。元数据记录来源 URL、下载时间、ETag、SHA-256 和可选的上游提交号。

### 7.2 启动与状态查询

- 程序启动时不会联网更新。
- 官方清单状态查询只检查文件组是否完整、元数据与 YAML 的 SHA-256 是否一致、索引摘要和 SQLite 完整性是否有效，不解析大型官方 YAML，也不重建索引；自定义清单仍会单独解析，以便在状态区域报告具体文件错误。
- 首次缺少活动清单时，从有效备份恢复；没有有效备份时再复制内置种子。
- 仓库内置 YAML 固定使用 LF。仅当 CRLF 内容规范化为 LF 后与元数据哈希完全一致时，才允许受控修复换行。

### 7.3 手动更新

只有用户点击“检查并更新清单”后才启动后台更新任务。过程依次显示连接、下载、校验、生成索引和替换状态。

更新必须满足：

- 更新地址仅允许 HTTPS。
- 网络超时为 30 秒。
- 使用 ETag 进行条件请求。
- 响应上限为 64 MiB，并采用流式下载。
- 下载落盘后再次校验 SHA-256。
- 完整解析并验证新 YAML 后，才允许替换活动清单。
- 替换前备份旧的有效文件组，替换使用原子操作。
- 下载、校验或替换失败时继续使用最后一次有效清单，并向用户显示本次失败原因。
- 官方清单不可用时，手动位置、自定义清单和引擎提示仍然可用。

## 8. 性能约束

- 打开游戏详情不得触发大型清单解析。
- 展开存档区域不得触发大型清单解析。
- 官方清单状态查询不得解析大型官方 YAML。
- 静态匹配只在点击“查找存档”后执行。
- 引擎目录探测必须限制深度、文件数量和单文件读取大小。

### 8.1 优化前性能基线

当前活动 Ludusavi YAML 约 17.5 MiB、包含约 52,967 个游戏条目。2026-08-14 在开发机上的只读诊断结果为：

- 单次完整 YAML 解析约 32～46 秒。
- 现有 Python 全量名称匹配约 5.2 秒。
- 当前加载路径还可能在快照完整验证后再次解析同一份 YAML。

因此原首次点击“查找存档”的主要瓶颈是大型 YAML 解析，其次是逐条名称规范化和模糊比较。现已由持久化索引移除正常查询路径中的大型 YAML 解析成本。

### 8.2 已确认的性能目标

- 正常存在有效索引时，冷进程首次查找在开发机上不超过 2 秒。
- 同一运行周期内后续查找不超过 1 秒。
- 索引迁移、缺失或损坏后的单次重建属于恢复路径，不计入正常快速路径，但必须明确处于加载状态并最终结束。
- 性能优化不得改变“只有用户点击查找后才进行静态匹配”的交互边界。
- 详情打开、存档区域展开和状态查询继续保持不解析大型官方 YAML。

### 8.3 派生 SQLite 索引

`manifest.yaml` 与 `manifest-meta.json` 继续作为唯一可信来源。新增的 `manifest-index.sqlite` 只是可删除、可重建的派生数据，不得替代源清单或削弱源文件校验。

索引至少包含：

| 数据 | 内容 |
| --- | --- |
| 索引元数据 | 索引格式版本、源 YAML SHA-256、游戏数和名称数 |
| 规范游戏 | 非别名游戏及稳定内部 ID |
| 匹配名称 | 规范名、安装目录名和已展开到最终游戏的别名，以及预先生成的规范化键 |
| 位置规则 | Windows 文件与注册表规则、标签、条件和原始顺序 |

标签和条件使用安全 JSON 文本保存，只对实际命中的少量规则解码。索引以 SQLite 只读连接查询，SQL 参数全部绑定，不加载扩展，也不执行清单内容提供的 SQL。

内置资源与活动目录都包含 YAML、元数据和索引三件套。手动更新流程为：下载 YAML、完整解析并验证一次、使用同一解析结果构建临时索引、检查索引摘要和 SQLite 完整性、备份旧文件组、替换新文件组。任一阶段失败都继续使用旧文件组。

历史备份同步扩展为三件套并继续只保留最近两组。旧版本遗留的 YAML 与元数据两件套仍可恢复，缺失索引随后按恢复路径重建。

### 8.4 官方索引查询流程

1. 用户点击“查找存档”。
2. GameShelf 校验活动 YAML、元数据和索引的摘要关系与索引格式。
3. 从安装目录名、检测标题、显示标题和主程序名生成去重后的匹配信号。
4. 先查询预规范化名称的精确命中；只要存在精确命中，就只返回去重后的精确候选，不再执行模糊匹配。
5. 完全没有精确命中时，才使用 RapidFuzz 以 `0.86` 阈值查询模糊候选，并归入“可能的位置”。
6. 只读取命中游戏的位置规则，再沿用现有路径模板展开、证据、分组、去重和默认勾选逻辑。
7. 精确和模糊匹配都没有结果时，官方来源返回空结果，不解析官方 YAML，也不重建有效索引。

当前真实索引包含 96,465 个预规范化候选名称。持久化索引后，正常查找不再承担大型 YAML 的解析成本。

自定义清单仍按现有安全上限读取小型 YAML；“查找时不解析 YAML”仅指不解析大型官方 YAML。引擎提示、建议合并和前后端公开 API 保持不变。

### 8.5 恢复、状态和并发

- 索引缺失、损坏、版本不兼容或与有效 YAML 摘要不符时，用户点击“查找存档”才触发一次受锁重建；成功后重新执行查询。
- 多个并发请求共享同一次重建，不得重复解析 YAML 或互相替换索引。
- YAML 本身与元数据摘要不符时先沿用现有备份、内置资源恢复链，不得从损坏或未验证的 YAML 构建索引。
- 索引重建失败时跳过官方来源，自定义清单和引擎提示继续工作。
- Ludusavi 设置状态只执行文件组摘要、索引元数据和 SQLite 完整性快速检查；不解析 YAML、不重建索引、不联网。
- 当前建议接口不增加局部警告字段。官方索引失败的完整原因写入后端日志，并通过 Ludusavi 设置状态显示；查找界面仍正常结束加载并展示其他来源结果。
- 名称缓存以源 YAML SHA-256 标识。更新成功后必须使缓存失效，下一次查询使用新索引。
- 规则查询使用短生命周期只读连接；更新与查询通过提供者锁隔离，避免 Windows 打开的 SQLite 文件阻碍替换。

### 8.6 性能验证方式

常规自动测试使用结构性断言证明有效索引查询不会调用官方 YAML 解析器，不在易受机器负载影响的单元测试中设置墙钟阈值。真实清单性能使用 `python scripts/benchmark_ludusavi_index.py` 测量。

2026-08-14 的内置 `manifest-index.sqlite` 大小为 17,100,800 字节（约 16.31 MiB），包含 51,864 个规范游戏和 96,465 个匹配名称。开发机上三个独立进程的结果为：

| 次数 | 冷查询 | 热模糊查询 |
| --- | ---: | ---: |
| 1 | 0.728 秒 | 0.030 秒 |
| 2 | 0.753 秒 | 0.031 秒 |
| 3 | 0.863 秒 | 0.039 秒 |

三次均满足冷查询不超过 2 秒、热查询不超过 1 秒。真实 YAML 的旧版本迁移重建约 27.71 秒，损坏索引恢复约 19.28 秒；恢复后的后续会话分别约 0.151 秒和 0.126 秒。重建时间属于低频恢复路径，不计入正常快速路径。

### 8.7 V0.2 路径反向索引扩展（已实现）

V0.1 的名称索引继续服务单个游戏详情中的按需静态查询，并保持“只有用户点击查找后才查询”的边界。V0.2 批量存档发现另行扩展可由路径特征反查完整 Ludusavi 游戏条目的派生索引，用于识别从未进入 GameShelf 游戏库的作品；不能把批量扫描实现成对每个目录重复执行全量名称查询或大型 YAML 解析。

当前索引格式 2 在同一 SQLite 文件中保留名称查询并新增根令牌、首段特征和相对路径规则反查；构建脚本继续原子更新 YAML、摘要和 SQLite 三件套。批量规则收集每次扫描只打开一次本地索引并加载所需反向规则；索引缺失、损坏或摘要不符时降级为其他本地来源并记录警告，不在扫描过程中联网或逐目录解析 YAML。

反向索引仍由已验证的 Ludusavi YAML 派生，摘要、格式、更新替换、只读连接和失败降级规则与现有索引一致。唯一且完整的路径规则可以成为高可信归属证据；通用目录、宽泛通配符、模糊标题或只命中引擎结构不得自动确认。反向索引只提供候选与证据，不直接写入 `save_locations`。

### 8.8 V0.3 双规则库静态查找流程

V0.3 保持引擎规则与存档规则结构分离，但两者共用规则 ID、内置或用户来源、正式或实验状态、版本、公开依据、优先级、结构校验和诊断。单游戏静态查找保持用户按需触发：

1. 用户点击“查找存档”后，读取去除版本号的游戏标题、安装目录、主程序、已识别引擎和可用产品身份。
2. 依次运行用户自定义清单、内置游戏专属规则、Ludusavi SQLite 索引和引擎通用规则。
3. 所有结果先展开为安全路径模板，再按类型和 Windows 规范路径去重；同一路径合并全部来源证据。
4. 实际存在的路径进入“已找到”。规则能够可靠推导但当前不存在的路径只进入折叠的“可能路径 / 未发现”，不得创建目录、文件或注册表键，也不得冒充已经找到的存档。
5. 游戏专属规则高于引擎通用规则；用户规则高于内置规则；正式规则高于实验规则。手动确认的位置始终最高且不能被建议覆盖。

有效 Ludusavi 索引只执行 SQLite 查询，不启动 Ludusavi 程序，也不解析大型官方 YAML。只有索引缺失、损坏、版本不兼容或与已验证 YAML 摘要不符时，用户本次点击才触发内部重建；重建失败后跳过官方来源并继续其他规则。

内置规则随 GameShelf 版本更新。后续编辑器生成的用户引擎规则位于 `data/rules/engines`，用户存档规则继续位于 `data/manifests/custom`；两者不得修改冻结资源。本轮只扩展外部规则文件和服务能力，不新增持久业务表，也不要求数据库迁移。

## 9. 故障与安全边界

- 无效路径模板不能落库。
- 注册表只允许受支持的根键，并要求显式确认。
- 自动建议不能覆盖或删除手动位置。
- 规则读取不得修改游戏目录或存档文件。
- 程序不在后台静默联网。
- 清单更新失败不能删除最后一次有效快照。
- 所有后台任务失败都通过稳定错误结构返回，界面不得无限显示加载状态。
- 声明式规则不得执行 Python、Shell、脚本或清单提供的 SQL；未知路径令牌、绝对后缀、目录穿越、重解析点越界和超过读取/匹配上限的规则必须被拒绝。
- 单条用户规则无效时只跳过该规则并返回可展开诊断，不影响其他规则、已有位置和手动管理。

## 11. 验收基准

以下行为必须持续成立：

- 一个游戏可保存多个目录和文件位置，并在重启后保留。
- 相同位置不会因路径大小写或分隔符差异重复保存。
- 游戏目录迁移后，`<game>` 模板在验证和打开时仍能解析到新的安装目录。
- 不存在的位置显示为失效，但不会被自动删除。
- 打开目录、定位文件和打开通配符父目录符合各自规则。
- 注册表建议未确认时不能接受或打开。
- 进入详情页和展开存档区域时不调用静态建议接口。
- 点击“查找存档”后才显示三类来源合并的建议与证据。
- 有精确官方名称命中时不执行模糊匹配；没有精确命中时才显示模糊候选。
- 有效官方索引查询不调用大型 YAML 解析器，只读取命中游戏的位置规则。
- 索引缺失或损坏时只重建一次；重建失败不影响自定义清单、引擎提示和手动管理。
- 官方清单损坏或更新失败时，最后一次有效清单和手动管理保持可用。
- 状态查询能快速结束，不解析 YAML、不重建索引，也不长时间停留在“正在读取清单状态”。
- 更新任务无论成功、无需更新、内容无效或网络失败，界面都会结束加载并显示结果。
- 更新任务在完整验证后生成索引；索引构建或替换失败时继续使用旧文件组。
- 正常有效索引在开发机上满足冷进程首次查找不超过 2 秒、同一进程后续查找不超过 1 秒。

### 11.1 V0.3 规则扩展验收

- 规则结构测试覆盖稳定 ID、来源、正式/实验状态、版本、路径令牌、安全上限和冲突。
- 每条准备转正式的规则都有公开依据、正向最小合成样本和至少一个相似结构负向样本。
- 同一路径由多个来源命中时只显示一个候选，同时保留全部证据和最高优先级。
- 实际存在与仅能推导的路径分别进入“已找到”和折叠的“可能路径 / 未发现”。
- 版本号不参与默认规则名称匹配；使用分离后的游戏标题，避免 `v1.0`、`Ver 1.42` 等版本文本降低命中。
- 缺少真实游戏不阻塞自动门禁；未完成的真实游戏检查必须列入人工验收清单，不能伪装成已经验证。
