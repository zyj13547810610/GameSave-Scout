# GameShelf 游戏引擎识别

> 文档性质：当前有效的模块设计与验收基准；适用版本：V0.1 及后续迭代；最后更新：2026-08-23；状态：V0.1 第一批识别器、首发识别补强、损坏声明式规则降级、V0.3.0 内置规则扩展和 V0.3.1 自定义规则编辑器均已完成；真实游戏规则矩阵继续后置复测。

## 1. 模块目标

GameShelf 在扫描游戏目录时，以只读方式推测游戏引擎，并向用户展示可信度和证据。引擎识别用于分类、筛选、解释和辅助存档定位，不决定一个目录能否进入游戏库。

核心原则：

- 有 EXE 或被直接子目录模式发现的文件夹都可以成为游戏，即使引擎未知。
- 不运行游戏、不加载 DLL、不解包商业资源、不注入进程。
- 多个独立证据优于单个通用文件名。
- 无法确定时宁可显示“未知引擎”，不强行给出结果。
- 用户手动选择始终高于自动结果，并在重新扫描后保留。

## 2. 检测输入与时机

扫描流程先确定候选游戏目录，再推荐主 EXE，最后调用引擎检测。输入包括：

- 游戏目录。
- 当前用于检测的主 EXE；有效手动选择优先，否则使用自动推荐。
- 目录内有限的文件和文件夹结构。
- 小段文本、文件头/尾魔数和有限 PE 版本信息。

检测器不读取存档内容，也不依赖游戏平台元数据。

## 3. 检测器架构

### 3.1 两阶段检测

每个检测器实现：

1. `cheap_probe`：使用少量路径存在性快速判断是否值得深入检查。
2. `inspect`：在受限读取范围内生成 `EngineMatch`。

每个结果包含引擎 ID、可选变体、可信度、证据列表、规则版本和是否为实验性。

### 3.2 结果选择

- 正式识别器最低可信度为 0.70。
- 实验识别器最低可信度为 0.80。
- 最多保留可信度最高的 3 个候选。
- 前两名差值小于 0.08 时标记为歧义，不自动采用第一名。
- 单个检测器异常只生成诊断证据，不中断整个目录扫描。

自动检测值写入 `detected_engine_id` 和 `detected_engine_variant`；界面采用值写入 `engine_id` 和 `engine_variant`。手动设置后 `engine_is_manual = true`，后续扫描仍更新检测值，但不覆盖采用值。

### 4.2 V0.1 首发识别补强（已完成）

这些项目全部使用合成最小目录测试，不提交用户本地商业游戏文件；扫描集成测试同时验证数据库自动结果刷新与手动覆盖保护。

## 6. 声明式规则格式

当前内置规则位于 `resources/rules/builtin/engines.yaml`，结构契约位于 `resources/rules/schemas/engines.schema.json`；用户规则一条一个 YAML，保存到 `data/rules/user/engines`。每条规则包含：

- 稳定引擎 ID 和用户可读标签。
- 可选变体。
- 是否实验性。
- 可信度阈值。
- `all`、`any` 和 `negative` 证据组。

当前支持的安全操作包括：

- 路径是否存在。
- 受限 glob 是否命中。
- 受限 glob 命中文件后，在固定偏移校验文件魔数。
- 小文本是否包含特征串。
- 固定偏移文件魔数。
- 文件头尾受限范围内的特征串。
- PE 版本字段包含指定文本。

规则路径必须是安全相对路径。读取器限制文件大小、读取字节数和 glob 数量，不能通过 YAML 请求执行代码或访问游戏目录外路径。

### 6.1 V0.3 共享规则基础层

V0.3 继续把引擎识别规则和存档位置规则维护为两套独立目录与结构，不把不同用途强行合并成一种大型 YAML；两者共用规则元数据、来源、校验、诊断和冲突处理机制。共享字段至少包括稳定规则 ID、规则类型、内置或用户来源、正式或实验状态、规则版本、公开依据、优先级和启用状态。

- 内置规则使用 `builtin` 命名空间并随 GameShelf 版本发布，不提供在线规则更新。
- V0.3.x 用户规则使用 `user` 命名空间并单独保存在程序旁 `data/rules/user/engines`，不得修改发布包内置文件。
- 内置和用户规则不得静默复用同一个稳定 ID；用户需要调整内置规则时，应复制成新的用户规则并以更高优先级参与候选排序。
- 正式与实验规则遵守同一安全读取边界；状态只影响阈值、排序和界面标识，不能放宽路径、读取或执行限制。
- 本轮规则扩展不新增持久业务表，也不要求数据库迁移。

V0.3.x 继续以文件为唯一事实来源。内置与用户规则连同 `data/rules/settings.json` 中的本地启停设置被编译为不可变快照；每次游戏分析在开始时捕获快照。编辑规则后只影响下一次分析或完整扫描，不自动重跑当前游戏库，也不覆盖人工选择的引擎。

## 7. 主程序与检测联动

引擎检测准确度依赖主 EXE 选择。当前联动规则：

- 自动扫描时先进行主程序排序。
- 用户手动选择的 EXE 如果仍存在且位于游戏目录内，检测优先使用该 EXE。
- 手动 EXE 无效时安全回退到自动建议，但不静默清除手动设置。
- 确认游戏移动时保留有效手动主程序及其架构。
- 检测器失败时保留上次有效引擎状态，不能用一次异常清空结果。

主程序排序的具体规则见模块 02。

## 8. 证据与手动覆盖

详情界面同时显示：

- 当前采用的引擎及其是否手动设置。
- 最近自动检测的引擎、变体和可信度。
- 支持结论的文件或元数据证据。
- 歧义候选和检测器诊断。

用户可以：

- 从已知引擎列表选择。
- 选择“未知引擎”。
- 输入最多 80 字符的自定义引擎名称。
- 清除手动值，重新采用最近自动检测结果。

手动选择只改变游戏库元数据，不改动规则文件。

## 9. 与 MTool 的关系

本项目曾使用用户本地的 MTool 安装目录和其公开支持范围作为调研线索，用于核对引擎名称和常见格式；GameShelf 不复制 MTool 的程序代码、私有数据库或运行时行为。

两者交互目标不同：

- MTool 以用户拖入目标 EXE 为入口，先判断它是否属于受支持引擎，再决定是否启动并提供翻译能力。
- GameShelf 先扫描目录建立游戏库；引擎未知也允许收录和启动，只是不能得到对应的引擎标签或存档提示。
- GameShelf 当前全部使用静态只读证据，不通过启动游戏来判断引擎。

因此，“MTool 不支持就不启动”的限制不适用于 GameShelf。

## 10. 安全与性能约束

- 不调用发现的 EXE、DLL 或脚本。
- 不完整解压归档，不扫描用户目录之外的内容。
- 不跟随符号链接和重解析点越界。
- 文本、二进制和 PE 读取必须有大小上限。
- glob 数量和规则数量必须有上限。
- 单个检测器运行异常，以及已存在但无法解析或校验的声明式规则错误，只影响对应检测器；内置专用检测器、游戏库扫描和应用启动必须继续可用，并记录可诊断错误。
- 商业游戏样本不得提交到开源仓库；测试使用合成夹具和公开格式信息。

## 12. 验收基准

- 未知引擎游戏仍能进入游戏库并设置主 EXE。
- 每个正式检测结果都至少包含一项可解释证据。
- 单一通用文件名不足以给出高可信结论。
- 前两名接近时不自动采用任意一方。
- 单个检测器异常不导致扫描任务整体失败。
- 手动引擎和手动主 EXE在重新扫描、根目录重映射和确认移动后保留。
- Unity 内层运行时、Siglus 汉化场景文件和常见辅助程序目录有回归测试。
- VX Ace 归档与解包结构、MV 根目录与 `www` 嵌套结构都有回归测试。
- Artemis 任意名称根级 `.pfs` 只有在文件头和独立配套证据同时命中时才被识别。
- Unreal 正式检测覆盖 Bootstrap 与 Shipping 两类入口，并排除引擎内部辅助程序。
- 成功重扫会刷新自动识别字段；手动引擎采用值在重扫和检测器异常后保持不变。
- 声明式规则不能读取游戏目录之外的路径，也不能执行文件。
- 实验规则需要更高阈值并在界面中可区分。
- `engines.yaml` 存在但内容损坏时，程序仍能启动并保留内置专用检测器；声明式检测器被禁用，日志明确记录规则加载失败。
- V0.3.x 内置规则只能查看、测试、本地禁用或复制，不能直接写回随包 YAML；用户规则编辑失败时旧快照继续可用。
- 新建或复制的用户引擎规则默认实验；成功只读测试后可由用户标记“用户规则 · 已验证”，修改匹配或证据条件后自动恢复为实验。
- 同一游戏由多条规则命中时继续按证据分数、置信度与优先级排序并保留歧义；用户规则和较高优先级不能覆盖有效的人工引擎采用值。

### 12.1 2026-08-16 损坏规则验收与修复设计

- 初次在独立轻量版冻结副本中验收时，干净规则的发布清单和 JSON smoke 均通过；将 `engines.yaml` 替换为无法解析的 YAML 后，冻结进程退出码为 1，错误能够指出 YAML 解析位置，但 `applicationBootstrap` 未完成，整个应用未启动。因此本项当时未通过，并触发本次修复。
- 根因边界已经定位：`build_application()` 启动期间直接调用 `EngineDetectionService.from_rules_file()`，后者同步调用 `load_engine_rules()`；`RuleSchemaError` 未在检测器组合边界转换为“禁用声明式检测器并继续”，而是直接中止应用构建。
- 测试后已恢复原规则，恢复后的冻结 smoke 再次退出 0。
- 已确认的修复边界：应用构建层只在规则路径仍是现有普通文件、但内容无法解析或结构校验失败时捕获 `RuleSchemaError`，向程序旁 `data/logs/gameshelf.log` 写入 WARNING，然后仅使用内置专用检测器继续启动。V0.1 不增加前端横幅或原生弹窗，避免可恢复的识别能力降级阻断用户。
- 规则文件缺失或不再是普通文件仍属于发布完整性故障，必须保留启动失败；命令行诊断工具继续使用严格规则加载，不改变其失败语义。
- 修复已在应用构建层实现：损坏 YAML 和结构错误写入 WARNING 后使用 `EngineDetectionService.builtins_only()` 继续启动；规则加载前移到数据库迁移和后台写线程之前，缺失文件仍严格失败且不再产生半初始化数据库。`EngineDetectionService.from_rules_file()` 保持严格语义。
- 测试先行证据为新增 3 个用例先全部失败、实现后全部通过；应用与引擎相关回归为 90 项，全量 Python 为 558 项，前端为 88 项，并通过 Ruff、mypy、前端类型检查、生产构建和源码 smoke。
- 随后已从干净提交 `6b29a8f1785dd123904e8e39dc9dadfa3bf89b9f` 正式重建双版本六个产物。在隔离的轻量版冻结副本中将 `engines.yaml` 替换为损坏 YAML 后，JSON smoke 退出码为 0，`applicationBootstrap` 与 `engineRules` 均为 `true`；程序旁普通日志记录“声明式引擎规则加载失败，已仅启用内置检测器”，且未生成 `startup-error.log`。恢复原规则后冻结 smoke 再次退出 0，本修复的源码与冻结版验收均已完成。

## 13. V0.3 内置规则扩展与自定义编辑器

### 13.1 V0.3.0 首批范围

V0.3.0 已按“同人游戏、Galgame 常见引擎优先，其次补充通用引擎”的顺序完成以下 10 个重点项：

- QLIE、Majiro、Malie、ShiinaRio、Entis/ERI/NOA 和 Nitroplus 经证据台账、合成正反样本与规则回归校准后转为正式。
- SoftPal/AmuseCraft 仍主要依赖短魔数且缺少足够真实样本，明确保持实验，不按计划数量强行转正。
- LiveMaker、CMVS/CVNS 和 Godot 已作为正式规则加入，并具备公开依据、合成正向样本和相似结构负向样本。

规则仍不得按计划数量强行转正式。只有稳定文件魔数、目录组合、可解析元数据等证据充分，并且具有正向与相似结构负向回归时才可转正式；只依赖常见文件名、误报风险仍高或公开依据不足的规则继续保持实验。

自动测试使用公开格式资料与合法的最小合成样本。当前电脑缺少的真实游戏仍保留为人工验收矩阵，在具备相应游戏的电脑上复测；仓库不加入商业游戏资源或由其截取的受版权保护载荷。开发者可使用 `detect_directory.py --sanitized` 生成受限深度、相对路径和短文件头的脱敏诊断报告，诊断过程不越过游戏目录或重解析点。

### 13.2 V0.3.1 自定义规则编辑器（已实现，待人工验收）

“规则管理”作为与游戏库、批量存档同级的独立工作台，顶部提供“引擎规则”“存档规则”“Ludusavi”三个标签。正常宽度使用左侧独立滚动规则列表和右侧独立滚动详情/编辑器，搜索、筛选和底部主要操作固定；110%/120% 或窗口过窄时改为先显示全宽列表、选中后进入全宽详情，并提供返回按钮，不把两列压成不可操作的细栏。

引擎规则标签遵循：

- 内置规则只读，可查看 ID、状态、来源、证据和 YAML 预览，也可本地启停、复制为新用户规则或选择一个游戏执行只读测试。
- 用户规则支持新建、修改、启停、复制、导入、导出和删除；显示名称可重复，但稳定 ID 全局唯一，不能复用内置 ID。
- 引导式表单依次编辑规则类型、基本信息、匹配条件和证据；第一版不开放任意 YAML 文本编辑，更不允许代码或脚本。
- 引擎规则继续使用现有受限 `all`、`any`、`negative` 证据操作。保存前执行 schema、安全、ID 冲突、路径边界和完整目录编译，失败时不写入文件。
- 只读测试报告命中证据、排除证据、分数、置信度和最终结论，不修改游戏记录、自动引擎结果、人工采用值或分析缓存。
- 新建和从内置复制的规则默认实验。成功测试后用户可以手动标记已验证，但始终显示为“用户规则 · 已验证”，不冒充 GameShelf 官方验证；修改匹配、证据或路径会自动恢复为实验，修改说明、依据或启停状态不会。
- 编辑器自身保存后热交换规则快照；程序外修改文件需要点击“刷新规则”或重启。已运行的扫描继续使用启动时快照，新任务使用新快照。

离开有未保存修改的编辑器前必须确认。新建和编辑直接使用右侧工作区，不再套大型弹窗；只有删除和覆盖导入等危险操作使用确认弹窗。弹窗位于所有选择框之上，非危险弹窗允许点击遮罩关闭。

### 13.3 共享导入、导出与冲突处理

引擎和存档用户规则共用最小文件交换流程：

- 一个 YAML 文件对应一条规则；导入对话框可一次选择一个或多个 `.yaml`/`.yml`，但第一版不支持 ZIP 规则包、在线市场或自动同步。
- 导入先展示规则类型、名称、稳定 ID、来源、实验/验证状态和完整诊断，用户确认后才写入。
- 与现有用户规则 ID 冲突时可选择生成新 ID 或覆盖该用户规则；与内置 ID 冲突时只能生成新的 `user` ID，永远不能覆盖随包规则。
- 外部规则无论声明什么来源，进入后都标记为用户规则。合法导入可以保留“已验证”状态，但仍显示“用户规则 · 已验证”，不冒充内置或 GameShelf 官方验证。
- 覆盖用户规则和删除规则必须再次确认；任何校验、写入或完整快照编译失败都保留原文件和当前编辑上下文。
- 导出只包含该规则的可移植声明，不包含本地游戏安装路径、测试结果、数据库内容、诊断缓存或其他用户数据。

多条规则可以使用相同显示名称，但稳定 ID 全局唯一。多条引擎规则命中同一游戏时仍保留全部候选和证据，优先级只用于排序与平分处理；不能用用户规则静默覆盖人工引擎采用值。
