# GameSave Scout 基础架构

> 文档性质：当前有效的模块设计与验收基准；适用版本：V0.1 及后续迭代；最后更新：2026-08-26；状态：V0.1 基础能力及后续增强、V0.2.0 自定义分组、V0.2.1 批量存档发现、V0.3.0 双规则资源装配、V0.3.1 自定义规则文件仓储/不可变快照和 V0.3.3 产品技术身份迁移与双版本冻结验收均已实现；配置版本 5、schema 4、任务共享/独占边界、桥接及事务边界保持不变。

## 1. 模块目标

本模块提供 GameSave Scout 其余功能共同依赖的桌面外壳、便携数据目录、SQLite 数据库、后台任务、前后端桥接和本地资源服务。

基础架构必须满足三个核心要求：

- Windows 10/11 x64 上可运行。
- 程序目录与 `data` 可以整体迁移。
- 扫描、清单更新等耗时操作不能阻塞界面。

## 2. 技术栈

| 层级 | 当前选择 |
| --- | --- |
| 桌面容器 | pywebview |
| 后端 | Python 3.12 |
| 前端 | Vue 3、TypeScript、Vite、Pinia |
| 数据库 | SQLite |
| 图片处理 | Pillow |

| 模糊匹配 | RapidFuzz |
| Python 测试 | pytest |
| 前端测试 | Vitest、Vue Test Utils、jsdom |
| 静态检查 | Ruff、mypy、vue-tsc |
| 开发环境 | 项目内 Conda prefix（`.venv`），Python 3.12、Node.js 24 |

选择 pywebview 方案的原因是前端布局和交互迭代更灵活，同时 Python 适合 Windows 文件系统、注册表、进程和 SQLite 操作。前后端边界通过显式桥接 API 维持，不让网页直接访问任意本地文件。

开发环境统一在项目根目录创建，Python 与 Node.js 共用同一个位于项目路径内的 Conda prefix：

```powershell
conda create --prefix .\.venv --override-channels -c conda-forge python=3.12 nodejs=24 -y
conda activate .\.venv
python -m pip install -e ".[dev]"
npm --prefix frontend install
```

后续每次打开终端时先在项目根目录执行 `conda activate .\.venv`。该环境只服务于源码开发，不会被打入最终便携版，也不要求修改系统全局 Node.js。

## 3. 启动与关闭流程

程序启动时按以下顺序组装：

1. 从源码目录或冻结版可执行文件旁确定程序根目录。
2. 创建并验证程序旁的 `data` 目录可写。
3. 初始化日志、SQLite 连接和数据库迁移。
4. 启动单一数据库写入线程与后台任务池。
5. 组装游戏库、扫描、启动、封面、规则目录、引擎和存档服务；先构建最后一次有效的不可变规则快照，再向任务服务注入快照提供器。
6. 在 `127.0.0.1` 随机端口启动只读资源服务。
7. 创建 pywebview 窗口并注入桥接对象。

关闭时停止后台任务、数据库写入线程和本地资源服务。新后台任务在关闭开始后不得继续提交。

以上为 V0.3.1 当前结构。`resources/rules` 是随程序发布的只读默认资源，`data/rules` 是用户可写规则和主动更新后的 Ludusavi 活动快照。规则状态不写入 `data/config.json` 或 SQLite；内置规则本地启停单独保存在 `data/rules/settings.json`。程序已停止加载和创建 `resources/manifests`、`data/manifests` 与 `data/manifests/custom`，但不自动迁移或删除检测到的旧目录。

如果程序目录不可写，启动必须明确失败并提示用户把整个目录移动到可写位置，不能悄悄改用 AppData。临时文件只放在 `data/temp`，写入完成后再原子替换目标文件。

## 5. 配置管理

`data/config.json` 使用带版本号的 UTF-8 JSON。当前字段包括：

| 字段 | 含义 |
| --- | --- |
| `version` | 配置结构版本，当前为 5 |
| `language` | 界面语言，当前默认 `zh-CN` |
| `startupQuickScan` | 是否在启动后快速核验已启用根目录，默认 `true` |
| `scanConcurrency` | 游戏分析全局共享并发数，允许 1～4，默认 1 |
| `orphanScanExclusions` | 后续孤立存档扫描的全局排除项 |
| `uiScale` | 界面缩放档位，允许 `0.8`～`1.2` 的五个固定值 |
| `coverOnlineEnabled` | 是否允许批量封面向导访问 VNDB，默认 `false` |
| `coverVndbCandidateLimit` | 每个游戏的 VNDB 候选上限，允许 1～20 |
| `coverLocalScanCandidateLimit` | 每个游戏的浅层扫描候选上限，允许 1～100 |
| `batchSaveCustomRoots` | 用户明确加入批量存档扫描的自定义目录、启用状态与 1～12 层深度 |

配置保存采用临时文件加原子替换。未知字段、不支持的版本或类型错误必须报告为配置无效，并保留原文件供用户手动恢复。

界面缩放存储在程序旁的 `data/config.json`，不依赖 WebView 页面来源。整个便携目录迁移后会随配置文件保留。

### 5.1 配置版本 2

配置结构已经升级为版本 2，并新增 `uiScale`。允许值固定为 `0.8`、`0.9`、`1.0`、`1.1`、`1.2`；它属于应用偏好，不写入 SQLite。

迁移与容错规则：

- 不存在配置文件时创建版本 2 默认配置，`uiScale` 为 `1.0`。
- 读取版本 1 时保留已有字段、补入 `uiScale: 1.0`，再通过临时文件和原子替换写回版本 2。
- 版本 2 的 `uiScale` 缺失或不在允许档位时回退到 `1.0`、记录警告并尝试原子写回规范值；写回失败不阻止本次启动。其他未知字段、不支持版本和结构错误仍按无效配置处理并保留原文件。
- 正式数据来源只有 `data/config.json`，不再读取或写入 `localStorage`；旧页面来源中残留的值不参与迁移。

启动与保存数据流：

1. Python 在应用组装阶段加载当前配置。
2. `bootstrap()` 在启动 DTO 中返回 `uiScale`，前端收到后应用到 `--ui-scale`。
3. 用户切换档位时前端立即更新当前界面，再调用单独的 `set_ui_scale` 桥接接口。
4. Python 重新验证值并原子写入整份配置；写入过程不经过 SQLite。
5. 保存失败时接口返回稳定错误，前端保留本次运行中的新比例并显示“缩放设置保存失败，下次启动可能恢复默认值”，应用不崩溃。

配置服务在内存中持有最新 `AppConfig` 并串行保存，避免未来多个偏好入口互相覆盖。整个程序目录迁移后，`data/config.json` 与其他便携数据一起保留缩放比例。

### 5.2 配置版本 3（已实现）

模块 03 的批量封面向导已把配置结构升级为版本 3，并新增：

| 字段 | 含义 |
| --- | --- |
| `coverOnlineEnabled` | 是否允许批量封面向导访问 VNDB，默认 `false` |
| `coverVndbCandidateLimit` | 每个游戏保留的 VNDB 候选上限，默认 `5`，允许 1～20 |
| `coverLocalScanCandidateLimit` | 每个游戏保留的浅层扫描候选上限，默认 `10`，允许 1～100 |

迁移与容错规则：

- 不存在配置文件时创建版本 3 默认配置，继续使用 `uiScale: 1.0`，联网保持关闭。
- 读取版本 2 时保留全部已知合法字段和 `uiScale`，补入三个新默认值，再原子写回版本 3。
- 读取版本 1 时先补入 `uiScale: 1.0`，再补入三个新默认值并直接写回版本 3。
- 新字段缺失、类型错误或超出范围时只回退对应默认值、记录警告并尝试原子写回；联网字段的任何非法值都按关闭处理。
- 未知字段、不支持的未来版本和整体 JSON 结构错误继续按无效配置处理并保留原文件，不能静默丢弃用户无法识别的数据。
- 批量封面设置通过单独桥接接口整体校验和串行保存，不能与 `set_ui_scale` 并发覆盖彼此的最新值。
- 配置版本升级不修改 SQLite，也不新增数据库迁移。

### 5.3 配置版本 4（已实现）

游戏库增量扫描把配置升级为版本 4，正式启用 `startupQuickScan`，并新增 `scanConcurrency`。启动开关默认开启；并发数只接受严格整数 1～4，布尔值、浮点数、字符串和越界值均回退为 1，记录警告并尝试写回规范值。

### 5.4 配置版本 5（已实现）

V0.2.1 批量存档发现把配置升级为版本 5，并新增 `batchSaveCustomRoots`。每项使用稳定 ID 保存绝对目录显示路径、启用状态和 1～12 层最大深度；盘符根、相对路径、空路径、控制字符、重复规范路径和越界深度均被拒绝。标准 Documents、Saved Games、AppData Roaming、Local 与 LocalLow 范围是每次扫描的临时选择，不写入配置。

版本 1～4 配置保留全部已知合法字段并补入空的自定义目录列表后原子写回版本 5。新增、更新和移除均通过单独桥接命令串行保存整份配置；失败时内存值和原文件保持原状。自定义目录只影响用户主动启动的批量存档扫描，不触发启动扫描或后台常驻监控。

## 6. SQLite 数据与迁移

当前源码数据库版本为 4，包含：

- `scan_roots`：多个游戏扫描根目录及各自规则。
- `games`：游戏库、独立的标题与可空版本号、各自的自动检测值和手动保护标记、启动配置、封面和引擎结果。schema 2 新增 `version`、`detected_version` 和 `version_is_manual`，既有 `title`、`detected_title` 和 `title_is_manual` 继续负责作品标题。
- `game_analysis_cache`：按游戏保存主程序文件指纹、分析规则版本和分析时间；正式结果仍以 `games` 为准，缓存可安全丢弃并随游戏级联删除。
- `save_locations`：已确认的存档位置。
- `scan_sessions`、`scan_observations`：游戏库扫描会话与观察结果；批量存档复用会话表但使用独立候选观察表。
- `save_detection_sessions`、`save_discoveries`：V0.1 引导式寻找存档的会话与候选。
- `game_groups`、`game_group_memberships`：V0.2.0 自定义分组及游戏多对多成员关系。
- `save_scan_candidates`、`save_scan_observations`：V0.2.1 批量存档跨扫描稳定候选、逐次来源与证据观察。
- `settings`：可扩展的键值设置。

迁移规则：

- 按版本顺序执行 SQL 文件。
- 数据库版本高于程序支持版本时拒绝打开。
- 已有用户表升级前先备份完整 SQLite 数据库。
- schema 1 升级到 schema 2 只增加可空字段，不拆分、改写或回填既有标题；新扫描才按保守规则分别写入标题与版本号。
- `game_analysis_cache` 在 V0.1.4 阶段直接加入新建 schema 2 初始结构，当时没有新增 schema 3，也没有为已经存在的 schema 2 开发库补表或回填；程序不得自动删除 `data/library.db`，人工验收前由用户自行删除可舍弃旧库并重建。
- V0.2.1 直接建立完整 schema 4，不提供 schema 3 到 schema 4 迁移；旧库继续在任何写入前被拒绝，只允许用户自行移走或删除。
- 迁移失败时回滚，错误中给出备份位置。
- 最多保留最近 5 份迁移前备份。

所有写操作通过一个专用写入线程串行执行；普通列表和查询使用短生命周期只读连接，避免跨线程复用 SQLite 连接。

### 6.1 V0.2 schema 3 自定义分组（已实现）

V0.2 新建 schema 3 数据库增加两张规范化关系表：

| 表 | 职责 |
| --- | --- |
| `game_groups` | 保存稳定 UUID、用户显示名称、规范化名称、创建时间和更新时间 |
| `game_group_memberships` | 以 `game_id + group_id` 联合主键保存游戏与分组的多对多关系 |

`game_group_memberships` 的两侧外键都启用级联删除：删除游戏时清理它的成员关系；删除分组时只清理关系，不修改或删除任何游戏。名称去除首尾空格后必须为 1～40 个字符，禁止控制字符；规范化名称必须唯一，使英文名称忽略大小写判重，中文名称原样展示。最多允许 200 个分组，第一版按创建顺序和稳定 ID 显示。

按用户确认的开发期边界，V0.2 不提供 V0.1 schema 2 到 schema 3 的迁移。空数据库直接初始化为完整 schema 3；程序检测到 schema 2 旧数据库时拒绝继续启动，显示中文提示要求用户退出后自行移走或删除 `data/library.db`，不得自动删除、重命名或覆盖旧库。重新建库会丢失旧数据库中的游戏、封面关联、存档位置和其他记录；`data/covers` 中的文件本身不自动删除，但不会自动重新关联。

分组列表和成员关系必须使用固定数量的批量查询加载，不能为每个游戏逐条读取。所有分组写入继续通过专用 SQLite 写入线程和单个事务提交。

### 6.2 V0.2 schema 4 批量存档发现（已实现）

批量存档发现新增两张表：

| 表 | 职责 |
| --- | --- |
| `save_scan_candidates` | 以类型和规范化路径保存稳定候选、首次/最后发现时间、可用性、建议关系、强归组键、最终游戏与审核状态 |
| `save_scan_observations` | 关联一次 `scan_sessions.kind = save_discovery` 会话，保存本次来源、证据和代表文件 |

`save_discoveries` 继续只服务引导式寻找，不再用可空会话外键同时表达两种不同生命周期。批量候选跨扫描复用身份，用户的忽略、关联和仅存档决定不被新观察覆盖；只有完整、可访问且未截断的范围才能把未再次发现的位置标记为失效。删除 `save_only` 卡片时不增加新表或迁移：同一事务先把全部关联候选恢复为 `pending` 并清空审核外键，再删除卡片，让既有外键级联清理库内位置和分组关系。

schema 4 继续沿用开发期“不迁移旧库”的决定。检测到 schema 3 时必须在写入前拒绝，提示用户自行移走或删除数据库；程序不能为了升级自动处理数据库、封面或实际存档。

## 7. 后台任务

扫描和 Ludusavi 更新使用统一 `TaskRegistry`：

- 状态：`queued`、`running`、`completed`、`cancelled`、`failed`。
- 进度包含已完成数量、可选总量和当前阶段消息。
- 前端通过任务 ID 轮询快照。
- 取消是协作式取消；任务在安全检查点响应。
- 未捕获异常写入 `data/logs/gamesave-scout.log`，前端只收到稳定、可读的错误提示。
- 同一资源组可以声明为共享占用或独占占用；多个共享任务可以共存，独占任务与该组内任一共享或独占任务双向冲突，单个任务不能同时声明两种占用。

任务池当前最多同时运行 2 个任务。游戏库 quick/full 使用共享 `disk_scan`，允许多个根目录任务并发；批量存档扫描使用独占 `disk_scan`，因此不能与任何游戏库扫描或另一批量存档扫描同时运行。需要修改数据库的任务仍通过单一写入线程提交事务。

### 7.1 V0.3.1 规则目录与运行时快照（已实现）

规则继续以 YAML 文件为事实来源，不新增持久业务表，也不修改 schema 4。共享规则基础设施分为：

- `UserRuleRepository`：按白名单目录枚举、读取、创建、原子替换和删除一条规则一个 YAML 的用户文件。
- `RuleCatalogService`：合并内置规则、用户规则和 `settings.json`，执行逐文件诊断，并编译不可变运行时快照。
- `RuleManagementService`：向桥接层提供列表、详情、新建、复制、编辑、启停、删除、导入、导出、刷新和只读测试。
- `LudusaviProvider`：独立管理随包快照、活动快照、检查更新、恢复随包版本和一致性状态，不把 Ludusavi 大型清单塞入通用规则目录加载流程。

规则写入采用“草稿校验 → 完整候选目录编译 → 临时文件写入 → 原子替换 → 交换内存快照”。结构、安全、ID 冲突、路径边界或完整编译任一步失败时，不写入目标文件，也不替换当前快照。单个外部用户 YAML 损坏时隔离该文件并保留其他有效规则；若刷新无法形成可用的新快照，则继续使用最近有效快照。

每个游戏分析、静态存档查找和批量存档扫描在开始时捕获一个规则快照，并在任务结束前保持该对象。编辑器保存或启停后立即影响下一次任务，但不改变正在运行的任务，也不自动重扫游戏库或存档目录。第一版不运行持久文件系统监听；用户在程序外修改文件后需要点击“刷新规则”或重启。

## 8. 前后端桥接

桥接统一返回以下两种结构之一：

```text
成功：{ ok: true, data: ... }
失败：{ ok: false, error: { code, message, details? } }
```

约束：

- 前端不接收 Python 对象，只接收可序列化 DTO。
- 请求字段在后端重新校验，不能信任 TypeScript 类型。
- 业务错误使用稳定错误码，避免前端解析异常字符串。
- 文件和目录选择由原生对话框完成。
- 前端不能传入任意路径要求后端读取或提供文件内容。

V0.2 分组桥接增加查询、新建、重命名、删除、单游戏原子替换和批量加入/移出能力。`Game` DTO 增加 `groupIds`，完整分组列表单独返回。单次批量最多接受 500 个游戏 ID，并在验证前去重；任一游戏或分组不存在、名称冲突或输入越界时整次失败。批量加入已经存在的关系、移出本来不存在的关系都计为“未变化”，不作为错误。成功结果返回实际新增、移除和未变化数量，不返回内部 SQL 或文件路径。

## 9. 本地资源服务

前端生产文件和封面通过一个只读 HTTP 服务加载：

- 只绑定 IPv4 回环地址 `127.0.0.1` 和随机端口。
- 每次启动生成随机会话令牌，令牌位于 URL 路径中。
- 只开放 UI 和已由数据库关联的封面路由。
- 封面路径必须位于受管的 `data/covers` 目录。
- 响应带有限制性 CSP，不提供目录列表和任意文件读取。

开发时可使用 `GAMESAVE_SCOUT_DEV_SERVER_URL` 指向 Vite；冻结版忽略该变量并始终加载随包 UI。

## 10. 错误处理与日志

- 用户可处理的问题直接显示中文消息。
- 无法访问扫描根目录不改变已有游戏状态。
- 后台任务异常写入日志，并结束加载状态。
- 数据库、配置或资源初始化失败时不继续启动半可用程序。
- 日志不得主动记录存档文件内容、剪贴板图片内容或环境变量值。

## 12. 验收基准

- 源码运行和冻结版都从正确的程序根目录解析资源与 `data`。
- 整个程序目录移动后，数据库、封面和规则仍可读取。
- 不可写目录会在启动阶段给出明确错误。
- 配置写入和数据库迁移失败不会留下被当作有效文件的半成品。
- 并发后台任务不会直接并发写 SQLite。
- 多个游戏根目录扫描可以共享 `disk_scan` 并发运行；批量存档扫描独占同一组，任一方向的冲突都返回稳定拒绝，任务结束后占用会释放。
- 任务成功、失败和取消后都能进入终态，界面不会永久加载。
- API 对缺字段、错误类型和越界路径返回稳定失败结构。
- V0.3.x 用户规则不写入 SQLite；规则文件和内置启停设置随整个便携目录移动后仍能加载。
- 规则保存失败、单文件损坏和刷新失败不会替换最近有效快照；任务开始后修改规则不会改变该任务的结果语义。
- 内置资源永远只读；本地禁用只改 `data/rules/settings.json`，损坏设置回退为全部内置规则启用并显示诊断。
- 旧 manifest 目录不再参与运行，检测到时只提供诊断和打开目录入口，不自动迁移或删除。
- 版本 1 配置自动迁移为版本 2 并默认使用 100% 缩放；合法缩放切换后重启和迁移整个便携目录仍能恢复。
- 非法缩放值回退到 100%；配置保存失败不撤销本次界面缩放，并显示明确警告。
- 版本 1/2 配置能迁移为版本 3 并保留合法缩放；新增联网开关默认关闭，两个候选上限的非法值分别回退默认值。
- 版本 1/2/3 配置能迁移为版本 4，并保留既有合法字段；启动快速核验开关可持久化，并发数只允许严格整数 1～4且非法值回退为 1。
- 版本 1～4 配置能规范化为版本 5；批量存档自定义目录只接受安全绝对路径、启用状态和 1～12 层深度，标准范围临时选择不写入配置。
- 新建 schema 2 数据库包含 `game_analysis_cache`；缓存随游戏删除，现有 schema 2 开发库不被程序自动迁移或删除。
- V0.2 新建 schema 3 包含分组与成员关系表、唯一约束和外键级联；旧 schema 2 被明确拒绝并提示人工移走或删除，不被程序自动改变。
- V0.2.1 新建 schema 4 包含跨扫描候选与观察表；忽略、人工关联、已记录和仅存档状态不会被后续观察覆盖，旧 schema 3 被明确拒绝且不被程序自动改变。
- V0.3.0 同时装配严格校验的 `engines.yaml` 与 `saves.yaml`；存档规则结构错误只禁用该建议来源并记录诊断，必需资源缺失仍在创建数据库前严格失败。批量候选的 `builtin` 只扩展观察 JSON 和筛选枚举，接受后映射到既有 `engine` 来源，不修改 schema 4。
- 分组列表和游戏关系使用固定数量的批量查询；单游戏替换和批量加入/移出均经过串行写入器并具有完整事务回滚。
- 本地资源服务无法读取白名单之外的文件，也不监听局域网地址。
- Python 与前端的自动化测试、类型检查和构建命令可独立执行。
