# GameShelf 引导式与批量存档发现

> 文档性质：当前与后续版本模块设计；适用版本：V0.1 及后续迭代；最后更新：2026-08-23；状态：V0.1 引导式寻找存档当前范围已完成，并通过自动验证及普通保存、纯自动保存、取消、关闭处理、多缩放、窄窗口和启动器脱离降级的本机人工验收；V0.2.1 批量存档发现、孤立反推和仅存档卡片已经实现并建立自动闭环，既定真实 pywebview 人工验收已完成；V0.3.0 已让批量扫描复用内置存档规则且不改变 schema 4；V0.3.x 用户规则快照接入设计已经确认，尚未实施；完整目标 Windows 10/11 设备矩阵未执行且不记为通过。

## 1. 版本范围

当前版本划分：

- V0.1 包含手动存档位置、按需静态建议和用户主动启动的“引导式寻找存档”。
- V0.2 实现用户主动启动的“批量寻找存档”：同时展示已安装、已失效、未关联和已记录位置，并把孤立存档反推作为结果类型之一。
- V0.3.0 已让批量扫描复用新的内置存档规则基础层；存档备份、恢复、同步和版本管理继续后置。

引导式寻找存档是 V0.1 发布门槛，但它不是常驻后台监控器：GameShelf 启动时不自动监控，用户日常启动游戏时也不默认采集文件变化。只有用户在单个游戏详情中明确确认开始，才创建一次受限会话。

V0.1 引导式寻找和 V0.2 批量存档发现是两个独立子项目，两者源码均已完成。V0.2 复用规则、路径规范化、后台任务和存档位置写入能力，但不复用引导式会话状态，也不演变为全盘扫描或常驻后台监控。

## 2. V0.1 用户操作流程

现有“查找存档”和新增“引导式寻找”是两个独立入口：

- “查找存档”只在用户点击后查询游戏专属规则、Ludusavi 索引和引擎提示。
- “引导式寻找”创建文件变化检测会话，并由向导启动游戏。

标准操作流程：

1. 用户在游戏详情的“存档位置”区域点击“引导式寻找”。
2. GameShelf 展示启动程序、默认监控范围、不可用范围、定向注册表键和隐私说明。
3. 用户调整勾选范围并点击“确认开始”。
4. GameShelf 建立观察器；所有观察器就绪后，使用现有安全启动配置启动游戏。
5. 用户进入游戏，创建或覆盖一次存档。
6. 用户回到 GameShelf，点击“我刚刚保存了”。
7. GameShelf 记录保存时间，再等待约 3 秒接收延迟写盘，然后自动停止监控并分析变化。
8. 用户审核候选位置；只有明确接受后才写入 `save_locations`，来源为 `dynamic`。

普通流程不要求用户再点击一次“停止并分析”。对于只有自动存档、无法准确标记保存时间的游戏，用户可以直接点击“停止并分析”；此时仍分析整个会话，但结果整体更保守且不默认勾选。

关闭游戏详情抽屉不会结束会话。主页显示当前游戏、阶段和持续时间，用户可以返回向导。全程序同时最多只有一个活动引导会话。

## 3. V0.1 后台执行流程

后台按以下顺序执行：

1. **范围预览**：验证游戏状态、主程序、当前活动会话、默认目录可访问性和定向注册表规则；此时不启动监控。
2. **会话准备**：创建 `preparing` 会话，规范化并去重用户批准的根目录，建立轻量元数据和定向注册表基线，启动全部文件观察器。
3. **启动游戏**：观察器全部就绪后调用现有 `GameLauncher`，记录根 PID，状态进入 `monitoring`。
4. **事件聚合**：将创建、修改、移动和删除事件按 Windows 路径合并，只保留路径、事件类型、接收时间和受限文件元数据。
5. **保存标记**：记录“我刚刚保存了”的时间，继续观察约 3 秒后进入 `settling`。
6. **收尾补偿**：停止观察器，获取定向注册表结束快照；只有溢出或观察器失败的根目录才执行受限元数据补扫。
7. **过滤评分**：过滤噪声、合并目录候选、计算可信度并生成人能理解的证据。
8. **持久化审核项**：以事务写入最终候选和会话摘要，释放内存原始事件，会话进入 `completed`。
9. **接受候选**：用户明确接受后，复用存档位置服务折叠便携模板并写入正式位置。

正常监控不会递归建立完整 AppData 快照，也不会周期性遍历 AppData。文件变化由 Windows 事件接口被动报告。

## 4. 默认范围与用户批准

启动前默认勾选：

- 当前游戏安装目录。
- Documents。
- Saved Games。
- AppData Roaming、Local 和 LocalLow。
- 已确认存档位置的父目录。

ProgramData 默认不勾选，只作为可选范围展示。用户可以在确认开始前添加其他本机目录。额外目录必须位于 `<game>`、`<home>` 或现有 Windows 已知文件夹令牌能够表示的范围内；无法折叠为便携路径模板的目录在 V0.1 中明确拒绝，避免检测完成后产生无法保存或无法迁移的候选。

路径规范化后去重，嵌套范围只建立一个观察器。不可访问目录明确展示并跳过，不请求管理员权限。用户明确选择的目录如果在确认后失效，则本次启动失败，不静默缩小用户批准的范围。

V0.1 只支持本机目录。UNC 和网络共享显示为不支持；用户仍可通过手动添加维护网络存档位置。

符号链接、目录联接和其他 Windows 重解析点不能让事件或补扫越过用户批准的范围。观察器、聚合器和补扫器都必须执行边界验证。

注册表只比较以下特定键：

- 当前游戏的 Ludusavi、游戏专属规则等静态来源明确给出的键。
- 用户已经确认的注册表存档位置。

不得遍历整个注册表。注册表快照只保存键和值的名称、类型、长度和摘要，不持久化原始值。

## 5. 组件边界

| 组件 | 职责 |
| --- | --- |
| `GuidedSaveSessionService` | 编排单活动会话、状态转换、启动游戏、保存标记、停止、取消和关闭清理 |
| `WindowsDirectoryWatcher` | 在批准根目录中使用 Win32 事件接口采集变化并明确报告溢出 |
| `BoundedMetadataScanner` | 只对溢出或失败范围执行有深度、条目数和时间限制的补扫 |
| `WindowsProcessTreeTracker` | 判断向导启动的进程树是否仍存在，不进行文件写入归因 |
| `RegistryMetadataReader` | 比较批准注册表键的元数据摘要 |
| `GuidedChangeAggregator` | 规范化路径、合并重复事件和记录时间证据 |
| `score_guided_changes_with_summary` | 过滤噪声、合并目录、评分并生成解释性证据 |
| 会话与候选仓库 | 读写 `save_detection_sessions` 和 `save_discoveries` |
| 桥接接口 | 校验预览、开始、标记、停止、取消、审核、接受和活动会话关闭选择请求 |
| Vue 向导与状态栏 | 范围确认、会话进度、保存标记、警告和候选审核 |

引导会话不占用现有 `TaskRegistry` 的通用工作线程。监控可能持续数十分钟，若占用当前两个通用工作线程之一，会影响游戏扫描和 Ludusavi 更新。引导服务使用隔离的观察线程和受控生命周期。

## 6. Windows 监控与进程跟踪

V0.1 使用项目内自建的窄范围 Win32 适配器：

- 通过 `ctypes` 调用 `ReadDirectoryChangesW`，不新增 Watchdog、watchfiles 或 pywin32 运行依赖。
- 每个去重后的批准根目录拥有独立句柄和固定容量事件缓冲。
- Windows 返回零字节或适配器检测到队列容量用尽时，将对应根目录标记为溢出。
- 停止和取消使用可中断 I/O；若取消请求恰逢下一次读取尚未挂起，停止流程在原有总超时内重试取消，直到关闭句柄并确认观察线程退出。
- 进程树通过 Windows Tool Help 进程快照跟踪根 PID 及其子进程。

文件系统事件通常不能可靠证明由哪个 PID 写入，因此进程树只控制会话生命周期，不参与文件归因或候选加分。

进程树可靠退出时，立即停止观察并进入自动分析；此时整个已观察进程树均已退出，不再额外等待 3 秒。只有用户点击“我刚刚保存了”后才保留约 3 秒延迟写盘等待。如果启动器很快退出且无法继续跟踪实际游戏，显示“无法可靠判断游戏是否仍在运行”，保持监控并等待用户点击“我刚刚保存了”或“停止并分析”。

## 7. 会话状态与交互

状态定义：

- `preparing`：验证范围、建立轻量基线和启动观察器；游戏尚未启动。
- `monitoring`：观察器就绪且游戏已启动，等待保存标记或手动停止。
- `settling`：保存标记后等待约 3 秒，或在手动停止、可靠进程退出后立即执行补扫和评分。
- `completed`：候选已持久化，可以立即或稍后审核。
- `cancelled`：用户取消，未生成候选。
- `failed`：准备、启动、监控或分析失败。
- `interrupted`：GameShelf 异常退出后，下次启动识别到的残留活动会话。

数据库约束和服务锁共同保证全程序最多一个 `preparing`、`monitoring` 或 `settling` 会话。

“停止并分析”保留已采集变化并生成候选；“取消会话”清理观察器且不生成候选。点击“我刚刚保存了”后重复提交相同请求是幂等的，不会创建多个收尾操作。

已完成但尚未审核的候选保留在数据库中。再次进入该游戏详情时可以继续审核，或明确丢弃旧结果后开始新会话。

正常退出 GameShelf 时如有活动会话，提示“停止并分析”“取消会话”或“返回程序”。异常退出、断电或强制终止不尝试跨重启恢复观察器；下次启动将残留状态改为 `interrupted`。

## 8. 资源上限

V0.1 固定以下上限，不提供高级配置界面：

| 项目 | 上限 |
| --- | --- |
| 活动会话时长 | 30 分钟 |
| 保存标记后的等待 | 约 3 秒 |
| 单会话不同变化路径 | 20,000 |
| 内存事件队列 | 50,000 条 |
| 过滤前候选 | 500 项 |
| 最终展示候选 | 200 项 |
| 单个补扫根目录深度 | 8 层 |
| 单个补扫根目录条目 | 100,000 项 |
| 单个补扫根目录时间 | 5 秒 |

重复事件直接聚合，不随事件次数线性增长。队列或路径上限触发后标记对应根目录溢出，不继续无限增长。

30 分钟只是用户忘记返回时的防遗忘上限。到期后自动进入 `settling` 并分析已有变化。正常流程在点击“我刚刚保存了”后的约 3 秒等待结束后立即分析。

补扫只检查路径、创建时间、修改时间和大小，只保留会话时间窗口内的变化。深度、条目或时间上限触发后显示“结果可能不完整”。

## 9. 聚合、过滤与评分

候选使用可解释的确定性规则评分，不使用不透明模型。

主要加分依据：

| 证据 | 影响 |
| --- | --- |
| 在保存标记前后 5 秒内变化 | 强加分 |
| 距离保存标记超过 5 秒但不超过 15 秒 | 中等加分 |
| 距离保存标记超过 15 秒 | 保留候选，不予时间加分 |
| 同一目录内多个文件协调变化 | 加分 |
| 与当前游戏静态规则一致 | 加分 |
| 位于游戏目录、确认位置父目录或可信引擎结构 | 加分 |
| 文件名或文件组合具有存档特征 | 小幅加分 |

点击“我刚刚保存了”后仍固定等待约 3 秒以接收延迟写盘；这段时间内的变化自然落入前后 5 秒的强加分窗口。评分仍分析整个监控会话，不会删除超过 15 秒的变化，只是不为其提供时间加分。单靠扩展名不能产生高可信建议。无保存标记时可以分析整个会话，但候选整体降权且不默认勾选。

过滤与降权规则：

- 明确的日志、缓存、临时目录、着色器、遥测和崩溃转储直接过滤或强降权。
- 浏览器、聊天软件等其他程序产生的高频变化降权。
- 只修改访问时间、最终文件不存在或只出现删除事件的路径不单独成为候选。
- “临时文件创建后重命名覆盖”的原子保存合并到最终文件。
- 已经存在于当前游戏正式存档位置中的路径不再作为新候选。

同一目录中多个相关文件优先合并为目录候选。只有单个文件具有明显独立存档特征时才生成文件候选。候选按 Windows 路径去重。

结果分组：

- 高可信位置：`confidence >= 0.85`。
- 可能的位置：`0.60 <= confidence < 0.85`。
- 低可信变化：`confidence < 0.60`，默认折叠。
- 注册表候选：独立分组，永不默认勾选。

高可信文件系统候选可以默认勾选。没有保存标记、发生溢出或补扫截断时，任何候选都不默认勾选。

每项候选至少展示路径、可信度、与保存标记的时间关系、代表性变化文件、静态或引擎证据，以及溢出、补扫和截断状态。代表性文件只展示有限数量。

## 10. 数据结构与开发期建库策略

当前仍处于开发阶段，不为现有临时数据库增加迁移兼容代码。实现时直接修改 `src/gameshelf/db/migrations/0001_initial.sql` 中的最终表结构，schema 版本暂时保持 1。

实施前确认 GameShelf 进程已经关闭，将现有 `data/library.db`、`data/library.db-wal` 和 `data/library.db-shm` 移动到 `data/db_backups` 中一个独立的时间戳目录，然后让 GameShelf 创建新数据库。测试数据库继续从修改后的初始脚本全新创建。

`save_detection_sessions` 保存：

- 会话和游戏 ID。
- 状态及开始监控、保存标记、结束时间。
- 向导启动的根 PID。
- 用户批准的范围。
- 不可访问、溢出和截断范围摘要。
- 进程跟踪是否降级。
- 候选、过滤等结果计数。
- 稳定错误代码和可读错误摘要。

部分唯一索引保证全库最多一个活动会话。应用启动时把残留活动状态改为 `interrupted`。

`save_discoveries` 保存：

- 所属检测会话。
- 路径模板、显示路径和 Windows 去重键。
- 目录、文件或注册表类型。
- 可信度、结构化证据和代表性变化文件。
- 首次、最后变化时间及与保存标记的时间差。
- 是否受到溢出或截断影响。
- 是否满足安全默认勾选条件。
- `unreviewed`、`accepted` 或 `ignored` 审核状态。
- 接受后创建的正式存档位置 ID。

同一会话、同一类型和同一路径只能存在一个候选。不得持久化原始高频事件流、存档内容或注册表原始值。

## 11. 桥接接口

已提供以下窄接口：

| 接口 | 作用 |
| --- | --- |
| `preview_guided_save_detection` | 返回启动程序、可选范围、不可用项和隐私说明 |
| `start_guided_save_detection` | 重新验证范围、启动观察器并启动游戏 |
| `current_guided_save_detection` | 返回当前活动会话；没有活动会话时返回最近一个仍有未审核候选的完成会话 |
| `guided_save_detection_status` | 按会话 ID 返回最新状态，供前端在进入 `settling` 后持续读取完成结果 |
| `latest_guided_save_detection_for_game` | 返回指定游戏最近一个仍可继续审核的会话 |
| `mark_guided_save_saved` | 记录保存时间并启动约 3 秒自动收尾 |
| `stop_guided_save_detection` | 无保存标记时手动停止并分析 |
| `cancel_guided_save_detection` | 取消且不生成候选 |
| `list_guided_save_discoveries` | 读取已完成候选 |
| `accept_guided_save_discoveries` | 事务式接受所选候选并幂等创建正式位置 |
| `discard_guided_save_detection` | 明确丢弃尚未接受的旧结果 |
| `resolve_guided_close` | 处理“停止并分析后退出”“取消会话并退出”或“返回程序”的关闭选择 |

前端只在会话处于 `preparing`、`monitoring` 或 `settling` 时按约 1 秒间隔读取指定会话状态；进入终态后立即停止轮询，但保留完成会话用于审核。不新增 Python 主动执行任意 JavaScript 的回调通道。

## 12. 前端界面

在现有静态“查找存档”附近增加独立“引导式寻找”按钮。范围确认面板显示：

- 当前游戏和将启动的程序。
- 默认监控目录及勾选状态。
- 不可访问或不支持的目录。
- 定向注册表键。
- 只读取路径和元数据、不读取或修改存档内容的说明。

会话面板按状态显示：

- `preparing`：正在准备监控，游戏尚未启动。
- `monitoring`：游戏名、持续时间、变化数量、“我刚刚保存了”“停止并分析”和“取消会话”。
- `settling`：约 3 秒写盘等待与分析进度，禁止重复提交。
- `completed`：候选分组、证据、警告、接受和丢弃操作。
- 失败、取消和中断：可读原因及重新开始入口。

关闭详情后，主页顶部显示“正在为《游戏名》寻找存档”、阶段、持续时间和“返回向导”。状态栏不展示原始文件路径。

另一个游戏存在活动会话时，“引导式寻找”按钮保持可见但不可启动，并说明当前正在监控哪个游戏。

候选审核沿用现有存档建议卡片的视觉语言，但与静态结果分开。接受所选候选后刷新正式存档位置列表。

## 13. 错误处理与清理

- 至少一个有效范围才允许开始。
- 全部观察器启动成功后才能启动游戏；部分启动失败时关闭已经建立的观察器。
- 游戏启动失败时立即停止观察器，会话进入 `failed`，不生成候选。
- 监控期间单个目录失效时，其余目录继续；失效范围标记为不完整。
- 事件或队列溢出不终止会话，收尾时对受影响范围补扫。
- 进程跟踪失败时降级为手动结束，不声称游戏已退出。
- 取消必须在 `preparing`、`monitoring` 和 `settling` 中清理线程、句柄和内存事件。
- 候选分析使用事务：完整写入候选和完成状态，或会话失败且不留下半批候选。
- 接受多个候选使用单次事务；任一候选无效或不属于会话时整体拒绝。
- 正常关闭处理活动会话；异常退出由下一次启动标记 `interrupted`。
- 日志只记录会话 ID、阶段、计数和稳定错误码，不记录存档内容、注册表原始值或高容量事件列表。

所有失败、取消和中断都只影响本次会话。已有 `save_locations` 和实际存档文件保持原样。

## 14. V0.2 批量存档发现（V0.2.1 已完成）

### 14.1 产品定位与入口

V0.2 的用户入口命名为“批量存档”，页面标题为“批量存档发现”。它是用户主动启动的批量扫描与审核工作台，不再只显示狭义孤立存档：

- 已安装且尚未记录的位置显示为“待添加”。
- 已安装且已经记录的位置仍显示为“已记录”，但不进入待处理计数。
- 匹配本体失效记录的位置显示为“可能的孤立存档”。
- 无法唯一匹配 GameShelf 现有游戏的位置归为“未关联游戏”；外部规则若能识别名称仍显示该名称，完全无法识别时标题才显示“未知游戏”。
- 已忽略、已处理和不可用候选保留独立筛选。

应用左侧栏增加“游戏库”和“批量存档”两个一级导航。批量存档使用独立全页面工作台，不把第三个批量按钮塞入主页固定筛选区。扫描不会在启动、进入页面或日常启动游戏时自动运行；只有用户点击“开始扫描”才创建任务。

### 14.2 总体流程与组件边界

批量任务采用规则优先的混合扫描：

1. 定向规则阶段批量展开游戏库、游戏专属规则、完整 Ludusavi 清单、引擎提示和受限注册表规则。
2. 受限发现阶段扫描 Documents、Saved Games、AppData、Local、LocalLow 和用户批准的自定义目录。
3. 聚合器把存档槽和代表文件合并成可加入详情的目录、单文件或注册表位置，随后规范化、去重和归组。
4. 匹配器判断已记录、已安装、本体失效或未关联，计算可信度并生成可读证据。
5. 仓储持久化跨扫描候选、会话观察和用户审核状态。
6. 审核服务事务式执行批量确认、修改关联、创建仅存档卡片、忽略和恢复。

后端保持五个独立职责：扫描协调器、候选提供器、聚合与匹配器、候选仓储、审核服务。V0.1 引导式会话继续使用自己的观察器、评分和候选状态；两者只共享无状态路径工具、规则读取与已确认存档位置写入辅助函数。

同一时间只允许一个批量存档扫描。它与游戏库 quick/full 扫描互斥，避免同时争抢磁盘；VNDB 等非磁盘网络任务不必互斥。离开工作台后任务可在 GameShelf 进程内继续，主页面显示可返回的进度入口；退出程序时将活动任务标记为中断，下次启动不自动恢复。

### 14.3 扫描范围与配置

标准范围包括：

- 所有现有游戏的 Ludusavi、游戏专属和引擎定向位置。
- 完整 Ludusavi Windows 文件及注册表规则的可展开位置。
- Documents、Saved Games、AppData Roaming、AppData Local 和 LocalLow 中受支持的已知结构。
- `<winAppData>\RenPy`、LocalLow 公司/产品层级及其他强引擎结构。
- 用户主动增加的自定义目录。

标准范围默认勾选，用户可以临时取消。自定义目录、启用状态和深度写入 `data/config.json`，但保存配置不会自动开始扫描。自定义深度为 1～12 层，默认 6 层；第一版拒绝把整个盘符根目录作为自定义范围。对游戏安装目录只检查规则明确指向的位置和少量已知存档结构，不递归遍历整个游戏本体。

注册表第一版只检查 Ludusavi 或游戏专属规则明确声明的键，不遍历注册表、不模糊搜索键名，也不修改、导出或删除值。注册表候选单独标识，接受前必须再次确认。

### 14.4 资源上限、进度与部分失败

定向阶段按游戏或规则显示确定进度；受限发现阶段显示当前范围、当前目录、已访问条目、候选数和耗时。文件系统使用单路顺序枚举，规则比对可以在内存中并行；第一版不增加新的磁盘并发设置。

固定硬上限：

- 每个自定义根目录最多访问 100,000 个文件系统条目。
- 单次任务总计最多访问 500,000 个条目。
- 单次最多保留 10,000 个规范化候选。
- 每个候选最多保存 20 个代表文件名称。
- 不跟随符号链接、目录联接点或其他重解析点。
- 跳过 Temp、Cache、GPUCache、崩溃转储和其他明确无关缓存目录。

达到上限时保留已有结果并把对应范围标记为截断。单个规则或范围失败不终止其他范围；所有范围不可访问时会话标记为不可用。用户取消后保留本次已经发现的候选，并标记结果不完整。取消、失败、中断、截断或范围不可访问都不能把本次未见到的旧候选标记为失效。即使没有候选，进度也必须进入完成状态并显示“未发现存档候选”。

完成摘要显示新发现、待处理、已记录、已忽略、不可用、自动归组、不可访问范围、截断范围和总耗时。

### 14.5 候选粒度、反推与可信度

候选以“可加入游戏详情的存档位置”为单位。一个目录中的 `save01.dat`、`save02.dat` 和配置文件只形成一条目录候选，并在证据中显示代表文件和计数；只有真正独立的单文件存档或注册表键单独显示。

识别顺序：

1. 先与现有 `save_locations` 的同类型规范化路径精确比对；完全相同标记为“已记录”。只有父子关系时不直接判重。
2. 批量展开库内游戏规则，唯一匹配时建议对应游戏并显示其当前安装状态。
3. 对完整 Ludusavi 清单建立“展开路径到游戏”的本地反向索引，不要求游戏已经进入 GameShelf。唯一规则命中可给出外部游戏名，多条规则命中则保留多个可能名称。
4. 路径中的 `RJ...`、`VJ...`、Steam/App ID、Unity 公司/产品组合和注册表厂商/产品键作为稳定或中等身份依据。
5. 目录名与 GameShelf 标题、Ludusavi 标题及别名只做规范化模糊匹配；`save`、`savedata`、`config` 等通用词不参与核心相似度。
6. Ren'Py、Unity、RPG Maker 等通用结构只能证明引擎，通用文件名和相近修改时间不能单独证明游戏身份。

高可信度要求唯一规则身份、稳定产品编号或现有游戏精确匹配，允许预选但仍不得自动写入。中低可信度只显示建议。完全无法识别时保持“未知游戏”，不为追求命中率虚构标题。

自动归组只接受同一个现有游戏 ID、同一个 Ludusavi/游戏专属规则条目或同一个稳定产品身份。模糊名称、相同引擎、相似文件名和相近时间只能给出“可能属于同一游戏”的提示。用户可以手动选择多个独立候选，一次关联同一游戏或创建一张包含多个位置的仅存档卡片。

### 14.6 schema 4 与跨扫描状态

批量存档发现采用新建 schema 4 数据库，不提供 schema 3 到 schema 4 的迁移。程序检测到旧库时只拒绝启动并提示用户自行移走或删除 `data/library.db`，不得自动删除、覆盖或改写数据库和封面文件。

数据分三层：

| 表 | 职责 |
| --- | --- |
| `scan_sessions` | 使用 `save_discovery` 类型保存批量会话范围、阶段、计数、规则版本、截断与错误 |
| `save_scan_candidates` | 保存跨扫描稳定候选、规范化路径、首次/最后发现时间、可用性、匹配、归组和最终审核状态 |
| `save_scan_observations` | 保存某次会话为什么发现该候选、当时来源、证据和代表文件 |

现有 `save_discoveries` 继续只负责 V0.1 引导式候选，不承载批量候选。候选以类型加规范化路径形成稳定身份；同一路径再次扫描时更新最后发现时间和最新观察，不覆盖用户的忽略、关联或仅存档决定。强归组键、建议游戏 ID、外部可能名称、最终游戏 ID 与存档位置 ID 分别保存，不能混用一个“建议名称”字段表达不同状态。

只有范围可访问、未截断且完整扫描后未再次发现候选时，才标记“位置已不存在”。范围不可访问时保持状态未知。不可用路径再次出现时恢复可用并沿用处理记录。清除不可用记录只删除 GameShelf 的候选和观察历史；已经接受的 `save_locations` 以及磁盘内容保持不变。

### 14.7 工作台与响应式布局

工作台右侧依次为固定标题操作区、运行时进度、固定搜索筛选栏、唯一候选滚动区和按需出现的底部批量操作栏。页面不产生额外外层滚动条。扫描设置使用锚定浮层；点击浮层内部保持打开，点击浮层外任意区域关闭，临时选择的本次扫描范围不被清空。

筛选提供全部、待处理、已安装游戏、本体失效、未关联游戏、已记录、已忽略和不可用，并可叠加关键词、可信度和来源。状态、可信度和来源在选择后立即应用；关键词停止输入 300ms 后应用，按 Enter 可立即应用；每次变更回到第一页。默认展示全部，但按高可信待处理、中低可信待处理、本体失效/未关联、已记录、已忽略、不可用排序。

候选卡片显示推测游戏名、匹配分类、位置类型、路径、来源、可信度和首要证据；展开后显示完整规则、代表文件和其他可能游戏。强证据多位置使用同一候选组展示，数据层仍保留独立位置。

单项操作包括添加、更换关联、创建仅存档卡片、忽略/恢复、打开位置、复制路径，以及对未关联候选复制推测关键词后打开 VNDB、DLsite 或 2DFan。宽窗口可以显示列表与右侧证据详情；窄窗口改为单列卡片展开。80%～120% 五档缩放均需支持，960×640 且 120% 时仍必须保留可操作的结果滚动区域；底部操作栏可以换行但不能覆盖结果。

### 14.8 审核、批量写入与仅存档卡片

高可信度只预选目标游戏，不自动勾选或写入。用户可以逐项选择或全选当前筛选中具有明确目标游戏的候选；已记录、已忽略、未关联或只有模糊建议的候选不进入批量确认。提交前显示候选数、涉及游戏数及目录/文件/注册表数量。

确认时重新验证候选、目标游戏和重复路径。整批通过专用 SQLite 写入线程在一个事务中写入 `save_locations`，任一项校验失败则全部回滚，并保留选择、筛选和滚动位置。已存在的同类型规范化路径按幂等结果处理。成功后候选标记为已记录并保留扫描证据；人工更换的目标游戏优先于自动建议。

创建仅存档卡片的确认界面包含必填且可编辑的标题、可空版本、可选引擎、可选多个分组和一个或多个存档位置。单事务创建 `games.status = save_only`、存档位置、分组关系和候选审核结果。仅存档卡片没有安装目录和主程序，不能启动，也不能通过批量移除删除磁盘内容；它可以继续维护标题、版本、封面、引擎、分组和存档位置。以后重新安装游戏时的自动合并不属于第一版。

忽略和恢复只修改候选审核状态。批量清除失效候选、删除候选历史或关闭工作台都不能移动、重命名或删除实际存档。

### 14.9 在线核对边界

截至 2026-08-19，DLsite 和 2DFan 没有可供本项目稳定依赖的正式公开搜索 API 或可下载元数据库；现有网页内部接口和第三方包装不作为自动集成依据。第一版不在后台请求或解析 VNDB、DLsite、2DFan。

若路径中检测到稳定 `RJ...`、`VJ...` 等编号，可以显示产品编号和用户主动打开对应作品页的入口。其他未关联候选只在用户点击时复制界面明确展示的推测关键词并打开系统浏览器；不得发送本地完整路径、代表文件列表或未展示的本地信息。

### 14.10 安全与完成边界

扫描只读取路径、名称、类型、大小、修改时间和有限目录结构，不读取或解析存档正文。所有扫描、忽略、关联和仅存档卡片操作都不能修改、移动或删除实际文件或注册表值。所有自动建议必须展示证据，未经确认不得写入游戏或存档位置。

V0.2.1 已经落地显式启动、阶段进度、硬资源上限、取消与部分失败、跨重启候选状态、完整 Ludusavi 反向匹配、保守未关联结果、事务式审核、仅存档卡片和五档缩放布局；用户已完成既定真实 pywebview 人工验收。

### 14.11 V0.3 共享规则接入（已实现）

V0.3.0 扩展的内置游戏专属规则和引擎通用存档规则已通过模块 05 的统一、已校验候选接口供批量扫描复用，批量工作台不自行解析第二套规则格式。规则来源、稳定 ID、正式或实验状态、版本和证据原样进入观察记录，前端提供“内置规则”来源筛选；用户接受后仍映射到既有 `engine` 持久来源。

- 批量扫描仍只由用户点击“开始扫描”触发，不因新增规则而在启动或游戏库扫描时运行。
- 定向规则阶段只把当前实际存在的文件系统或注册表位置物化为新的批量候选。仅能推导但当前不存在的路径不算“发现”，不写入跨扫描候选表；它们只在单游戏详情的“可能路径 / 未发现”中展示。
- 用户规则高于内置规则，游戏专属规则高于引擎通用规则；同一路径由多个来源命中时合并证据，不生成重复候选。
- 正式与实验规则使用相同扫描深度、条目数、路径和重解析点边界。实验状态不得提高自动归组等级，也不能绕过人工确认。
- 规则文件损坏或单条规则失败时，批量扫描记录部分失败并继续其他来源；不能清空旧候选、误标失效或中断手动审核。
- 共享规则扩展不改变 schema 4，也不要求数据库迁移。

V0.3.x 实施自定义规则编辑器后，批量扫描继续复用模块 05 的统一候选接口，不自行读取 `data/rules/user`。每次批量任务开始时捕获同一个不可变规则快照，任务进行期间的编辑、启停或刷新只影响下一次扫描；不自动重启当前扫描，也不回写既有候选的历史证据。

- 用户游戏专属规则和用户引擎通用规则与内置规则使用相同的路径、glob、注册表、深度、条目数和重解析点边界。
- 旧 `data/manifests/custom` 在 V0.3.x 不再加载；其能力由新游戏专属规则接替，不迁移、不自动删除，也不改变 schema 4。
- 单个用户规则损坏只形成部分诊断，不能中断其他来源、清空旧候选或把未再次发现的位置误标失效。
- 用户规则的来源、稳定 ID、实验/用户验证状态和证据进入观察记录；接受位置仍遵守现有人工确认与事务边界。
