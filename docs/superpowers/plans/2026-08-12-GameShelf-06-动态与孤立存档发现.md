# GameShelf 引导式与孤立存档发现

> 文档性质：后续版本模块设计；适用版本：V0.2～V0.3；最后更新：2026-08-13；状态：尚未实现，不阻塞 V0.1。

## 1. 范围调整

首版原计划同时实现游戏库、静态存档规则、自动文件监控和孤立存档反推，范围过大。当前决定：

- V0.1 只保证手动存档位置和按需静态建议。
- V0.2 实现用户主动启动的“引导式寻找存档”。
- V0.3 实现已删除游戏留下的“孤立存档发现与反推”。

本模块不是常驻后台监控器，不在 GameShelf 启动时自动扫描全盘，也不在用户日常启动每个游戏时默认抓取文件变化。

## 2. 两个独立子项目

### 2.1 V0.2 引导式寻找存档

目标是解决“游戏还在，但用户不知道存档在哪里”。用户从某个游戏详情主动开始一次受控会话：

1. GameShelf 展示将要监控的位置和隐私说明。
2. 用户确认后，程序建立基线并启动该游戏。
3. 用户进入游戏，创建或覆盖一次存档。
4. 用户点击“我刚刚保存了”，可重复标记多次。
5. 用户停止会话，或游戏进程树退出后自动收尾。
6. GameShelf 汇总新增和修改过的文件/注册表元数据，过滤噪声并评分。
7. 用户审核候选项；只有明确接受后才写入 `save_locations`。

### 2.2 V0.3 孤立存档发现

目标是解决“游戏本体已经删除，但 AppData、Documents 或注册表中的存档仍在”。它是独立页面和独立扫描任务：

1. 用户选择默认已知目录或额外扫描目录。
2. 程序依据 Ludusavi、引擎目录结构和文件组合寻找候选。
3. 候选显示可能的游戏名、引擎、可信度和证据。
4. 用户可以关联现有游戏、创建仅存档卡片或忽略。

V0.3 只能“提出可能关系”，不能保证仅凭存档反推出准确游戏。通用的 `save01.dat`、`config.dat` 等缺少上下文时必须保持低可信度和未命名状态。

## 3. V0.2 监控范围

默认候选根目录：

- 当前游戏安装目录。
- Documents。
- Saved Games。
- AppData Roaming、Local 和 LocalLow。
- 可访问的 ProgramData。
- 已确认存档位置的父目录。
- 用户在会话开始前额外选择的目录。

路径规范化后去重。不可访问目录跳过并明确展示，不请求管理员权限。符号链接和 Windows 重解析点不能让扫描越过批准范围。

注册表只比较静态规则或已确认位置指向的特定 HKCU/HKLM 键，不监控或遍历整个注册表。

## 4. 文件变化采集

V0.2 计划使用 Windows 文件系统事件适配器和受限快照降级：

- 事件按 Windows 规范化路径聚合，只保留创建、修改、移动等摘要。
- 不把某个文件变化声称为某个 PID 写入；文件系统事件通常没有可靠进程归因。
- 进程树只用于判断引导会话何时结束。
- 事件队列有容量上限，溢出时对受影响根目录执行时间窗口元数据扫描。
- 降级扫描只检查修改时间、创建时间、大小和路径，不读取文件内容。
- 扫描深度、条目数、候选数和会话时长都有硬上限。

会话结束后只持久化聚合候选和证据，不保存高容量原始事件流。

## 5. 保存时间标记与评分

“我刚刚保存了”是最重要的用户证据。建议初始评分因素：

| 证据 | 影响 |
| --- | --- |
| 在保存标记前后约 2 秒内新增或修改 | 强加分 |
| 在保存标记前后约 10 秒内变化 | 中等加分 |
| 多次保存标记附近重复变化 | 强加分 |
| 位于游戏目录、已知公司/产品目录或确认位置父目录 | 加分 |
| 文件名、扩展名或一组文件具有存档特征 | 小幅加分 |
| 日志、缓存、临时文件、着色器、遥测、崩溃转储 | 过滤或强降权 |
| 高频浏览器缓存及超大临时文件 | 降权 |

单靠扩展名不能产生高可信建议。同一目录内多个协调变化的文件可以合并为目录候选。

候选按 Windows 路径去重，最多展示 200 项。每项必须提供人能理解的证据，不能只给一个不透明分数。

## 6. V0.2 会话状态

计划状态：

- `preparing`：解析游戏、构建范围和建立基线。
- `monitoring`：游戏运行，等待保存标记和文件变化。
- `settling`：停止后等待短暂静默并执行降级补扫。
- `completed`：可审核候选。
- `cancelled`：用户取消，清理观察器和进程跟踪。
- `failed`：初始化或运行失败，保留原有存档位置。

每个游戏最多一个活动会话，整个程序最多两个活动会话。默认最长 6 小时，收尾静默期约 3 秒；最终数值在 V0.2 实施前通过真实测试确认。

## 7. V0.2 候选审核

- 文件、目录和注册表候选分组显示。
- 高可信文件系统候选可以默认勾选。
- 注册表候选永不默认勾选，并需要额外确认。
- 用户接受后折叠为便携路径模板，来源标记为 `dynamic`。
- 未接受候选不写入正式存档位置。
- 没有结果时提供扩大批准范围和手动添加，而不是宣称“游戏没有存档”。
- 事件溢出或扫描截断时必须显示结果可能不完整。

## 8. V0.3 默认查找策略

默认扫描不遍历所有磁盘，而是检查：

- 可直接展开的 Ludusavi Windows 文件和注册表规则。
- `<winAppData>\RenPy` 下具有 Ren'Py 存档结构的目录。
- LocalLow 下有限深度的 Unity 公司/产品目录。
- Documents、Saved Games、AppData 中有强引擎特征的已知结构。
- 用户已经配置的自定义清单位置。

Unity 存档通常独立位于 LocalLow，因此即使游戏本体删除也可能保留；RPG Maker 存档经常位于游戏目录中，本体目录整体删除后可能已经同时消失。不同作品可自定义位置，以上都只能作为候选来源。

## 9. V0.3 扩展扫描

用户可以额外选择一个或多个目录，设置 1～12 层深度，默认 6 层。扩展扫描必须：

- 可取消并显示进度、当前范围和截断信息。
- 每个根目录限制最大访问条目数。
- 跳过 Windows、Program Files、回收站、System Volume Information、浏览器/开发缓存和重解析点。
- 遵守用户设置的全局排除项。
- 只读取路径、文件元数据及受限特征，不读取存档内容。

单个通用扩展名只能产生低可信候选；引擎目录结构、成组文件、规则名称或产品目录可以提高可信度。

## 10. 孤立候选审核

每条发现可执行：

- 关联到现有游戏：创建或复用一个已确认存档位置。
- 创建仅存档卡片：新建 `games.status = save_only` 的游戏记录，并关联来源为 `legacy_scan` 的位置。
- 忽略：保留记录和理由，允许在“已忽略”筛选中撤销。

任何操作都不能移动、重命名、删除或修改实际存档。低可信候选不预选任何操作。

## 11. 数据与隐私

初始数据库已经预留：

- `save_detection_sessions`：V0.2 会话状态、范围、溢出和摘要。
- `save_discoveries`：V0.2/V0.3 候选、证据、审核状态和关联游戏。

正式实现前仍应通过新数据库迁移复审字段，不因表已存在就直接假设设计最终确定。

不得持久化：

- 原始高频文件事件流。
- 存档文件内容。
- 注册表原始值；如需比较，只保存类型、长度和哈希。
- “某 PID 写了某文件”这种无法可靠证明的归因。

## 12. 预期组件

| 组件 | 职责 |
| --- | --- |
| 观察聚合与噪声过滤 | 合并重复事件、过滤缓存并生成解释性评分 |
| 文件系统监控器 | 在批准根目录内采集事件并报告溢出 |
| 时间窗口扫描器 | 对溢出范围进行受限元数据补扫 |
| 进程树跟踪器 | 判断启动器和子进程是否仍存活 |
| 定向注册表快照 | 比较批准键的元数据哈希 |
| 检测会话服务 | 编排 V0.2 状态机与候选持久化 |
| 孤立存档扫描器 | 执行 V0.3 默认和选定范围扫描 |
| 审核服务 | 关联、创建仅存档卡片、忽略和撤销 |
| 前端向导与页面 | 范围确认、保存标记、进度、候选审核 |

## 13. 实施前置条件

开始 V0.2 前必须重新编写独立规格并确认：

- 监控依赖选择和 Windows 兼容性。
- 真实事件吞吐和溢出处理。
- 默认监控范围是否足够透明。
- 对大型 AppData 的性能上限。
- 游戏启动失败、启动器拉起子进程和进程退出的交互。

开始 V0.3 前必须单独确认：

- 默认扫描范围和隐私提示。
- 仅存档卡片在主游戏库中的呈现方式。
- 候选忽略规则能否编辑和撤销。
- 如何评估反推准确率及误关联成本。

## 14. 验收方向

### V0.2

- 只有用户主动开始才监控。
- 保存标记附近的真实测试文件能排到前列。
- 进程树只控制生命周期，不宣称文件归因。
- 不可访问、溢出和截断都有可见提示。
- 取消和失败会清理资源，且不影响已有位置。
- 未经用户接受，不产生正式存档位置。

### V0.3

- 默认扫描能发现代表性的 Ren'Py、Unity 和 Ludusavi 遗留目录。
- 普通 `save01.dat` 在缺少上下文时保持低可信且不命名。
- 扩展扫描边界清晰、可取消、不会静默全盘运行。
- 关联、创建仅存档卡片和忽略都由用户明确触发。
- 所有审核操作都不改动实际存档文件。
