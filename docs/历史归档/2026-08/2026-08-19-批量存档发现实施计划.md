# 批量存档发现实施计划

> **供智能执行器使用：** 必须使用 `superpowers:executing-plans` 按任务逐项执行并在检查点复核；根据本项目约定不得使用子代理。所有步骤使用复选框跟踪。

**目标：** 为 GameShelf 增加用户主动触发的“批量存档发现”工作台，在严格资源上限内扫描、识别和审核本地存档位置，并支持关联现有游戏或创建仅存档卡片。

**架构：** 后端采用“定向规则优先 + 受限目录发现”的两阶段流水线。扫描结果以 schema 4 的稳定候选和逐次观察分层持久化，Ludusavi 索引增加路径反向查询；所有正式写入由独立审核服务在 SQLite 单事务内完成。前端在应用左侧增加一级导航，以 Pinia 保存工作台状态，并使用固定控制区加唯一结果滚动区。

**技术栈：** Python 3.12、SQLite、pywebview、Vue 3、TypeScript、Pinia、Vite、Vitest、pytest、RapidFuzz、Windows Known Folders/Registry/Shell。

**规格：** `docs/superpowers/plans/2026-08-12-GameShelf-06-动态与孤立存档发现.md` 第 14～15 节；跨模块约束同时见总体设计及模块 01、02、03、05。

## 全局约束

- 仅支持 Windows 10/11 x64；程序状态继续位于程序旁 `data` 目录。
- 扫描只能由用户点击“开始扫描”触发；启动、进入页面和启动游戏都不得自动扫描。
- 文件系统枚举为单路顺序读取；不新增磁盘并发设置，不跟随符号链接、目录联接点或其他重解析点。
- 每个自定义根目录最多访问 100,000 个条目；单任务最多 500,000 个条目、10,000 个候选；每个候选最多保存 20 个代表文件。
- 自定义目录深度为 1～12，默认 6；拒绝盘符根目录。标准范围默认勾选，但本次选择不持久化；自定义目录、启用状态和深度写入 `data/config.json`。
- 扫描只读取路径、名称、类型、大小、修改时间和有限目录结构；不读取或解析存档正文，不修改、移动、重命名或删除文件及注册表值。
- 注册表只检查 Ludusavi 或自定义清单显式声明的 HKCU/HKLM 键；接受注册表候选前必须额外确认。
- 自动结果只提供建议和证据；高可信结果可以预选目标，但不能自动勾选或写入 `save_locations`。
- 第一版不得把仅存档卡片与后来重新安装或重新扫描出的游戏自动合并；是否合并留给后续独立设计。
- DLsite、2DFan、VNDB 不做后台抓取。只有用户点击时才打开系统浏览器，参数只能来自候选 DTO 已展示的产品 ID 或推测标题，不能包含完整路径和代表文件。
- 批量存档扫描与游戏库 quick/full 扫描共享 `disk_scan` 互斥组；非磁盘网络任务不受限制。
- schema 4 只初始化新数据库，不提供 schema 3→4 迁移；检测到旧库必须在写入前拒绝并保持原文件不变。
- 取消、失败、中断、截断和不可访问范围不得把未见到的旧候选标记为不可用；只有完整、可访问、未截断的范围才能执行缺失核对。
- 80%、90%、100%、110%、120% 五档缩放均须可操作；960×640 且 120% 时必须保留结果滚动区，底部操作栏不得遮挡候选。

CREATE TABLE path_rules (
  game_id INTEGER NOT NULL REFERENCES games(id),
  location_order INTEGER NOT NULL,
  kind TEXT NOT NULL CHECK (kind IN ('file', 'registry')),
  root_token TEXT NOT NULL,
  relative_pattern TEXT NOT NULL,
