# V0.3.1 自定义规则编辑器 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:executing-plans` in the current session to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. 本项目明确不使用子代理，不创建分支或额外 worktree。

**Goal:** 在保持 SQLite schema 4、不迁移旧清单、不增加后台扫描的前提下，交付独立“规则管理”工作台，让用户以安全表单管理引擎规则、游戏专属存档规则和引擎通用存档规则，并集中管理 Ludusavi 随包/活动快照。

**Architecture:** `resources/rules` 是只读随包资源，`data/rules` 是便携可写规则目录；规则文件是唯一事实来源。`RuleCatalogService` 把内置规则、用户规则和本地启停设置编译成不可变 `RuleSnapshot`，引擎扫描、单游戏静态查找和批量存档任务只在开始时捕获一次快照。编辑器通过严格草稿校验、完整候选目录编译和原子文件事务发布新快照；失败继续使用最近有效快照。

**Tech Stack:** Python 3.12、dataclass/typing、PyYAML、SQLite 只读 Ludusavi 索引、pytest、Vue 3、TypeScript、Pinia、Vitest、pywebview、Windows 文件对话框与注册表只读适配。

**Spec:** `docs/superpowers/specs/2026-08-12-GameShelf-总体设计.md` 第 19.3 节、`docs/superpowers/plans/2026-08-12-GameShelf-01-基础架构.md` 第 7.1/11/12 节、`docs/superpowers/plans/2026-08-12-GameShelf-03-封面与游戏库界面.md` 第 3.4/13 节、`docs/superpowers/plans/2026-08-12-GameShelf-04-游戏引擎识别.md` 第 13.2/13.3 节、`docs/superpowers/plans/2026-08-12-GameShelf-05-静态存档位置.md` 第 6.4/7/11.2 节、`docs/superpowers/plans/2026-08-12-GameShelf-06-动态与孤立存档发现.md` 第 14.11 节、`docs/superpowers/plans/2026-08-12-GameShelf-07-便携版打包与发布.md` 第 7/9/12 节、`docs/superpowers/plans/2026-08-12-GameShelf-开发路线图.md` 第 9.2 节。

## 目标文件结构与职责

```text
resources/rules/
├─ builtin/
│  ├─ engines.yaml                 # 随版本发布的只读引擎规则，多规则文档
│  └─ saves.yaml                   # 随版本发布的只读存档规则，多规则文档
├─ schemas/
│  ├─ engines.schema.json          # 引擎 YAML 的 Draft 2020-12 公开结构
│  ├─ saves.schema.json            # 存档 YAML 的 Draft 2020-12 公开结构
│  └─ README.md                    # 字段、安全原语和一文件一用户规则说明
├─ ludusavi/
│  ├─ manifest.yaml
│  ├─ manifest-meta.json
│  ├─ manifest-index.sqlite
│  └─ LICENSE
└─ README.md                       # 既有规则证据与许可台账

data/rules/
├─ user/
│  ├─ engines/                     # 每个用户引擎规则一个 YAML
│  └─ saves/                       # 每个用户存档规则一个 YAML
├─ ludusavi/                       # 用户更新后的活动三件套；为空即使用随包版本
│  ├─ manifest.yaml
│  ├─ manifest-meta.json
│  └─ manifest-index.sqlite
└─ settings.json                   # 内置禁用项；损坏时安全回退
```

新增后端文件按职责拆分：

- `src/gameshelf/rules/catalog.py`：不可变快照、完整目录编译、原子快照交换和诊断。
- `src/gameshelf/rules/repository.py`：用户 YAML 枚举、单文件/批量原子写入和旧目录探测。
- `src/gameshelf/rules/settings.py`：`settings.json` 严格读取、原子保存与损坏降级。
- `src/gameshelf/rules/serialization.py`：三类规则的规范化映射和稳定 YAML 输出。
- `src/gameshelf/rules/management.py`：列表、详情、草稿验证、只读测试、CRUD、复制和验证令牌。
- `src/gameshelf/rules/import_export.py`：受限导入会话、冲突决策和便携声明导出。
- `src/gameshelf/bridge/rule_controller.py`：严格桥接请求解析和规则 DTO；`BridgeApi` 只保留薄转发入口。
- `frontend/src/features/rules`：工作台、Store、列表、详情、编辑器、导入确认、诊断和 Ludusavi 标签。

核心接口在 Task 3 固定为：

```python
type RuleDefinition = EngineRule | SaveRule

@dataclass(frozen=True, slots=True)
class RuleSnapshot:
    generation: int
    catalog_version: str
    engine_detection: EngineDetectionService
    save_rules: SaveRuleProvider
    rules: tuple[CatalogRule, ...]
    diagnostics: tuple[RuleDiagnostic, ...]

class RuleCatalogService:
    def snapshot(self) -> RuleSnapshot: ...
    def refresh(self) -> RuleRefreshResult: ...
    def compile_candidate(self, files: Mapping[Path, bytes], settings: RuleSettings) -> RuleSnapshot: ...
    def apply_user_changes(self, changes: Mapping[Path, bytes | None], settings: RuleSettings) -> RuleSnapshot: ...
    def publish(self, snapshot: RuleSnapshot) -> RuleSnapshot: ...
```
