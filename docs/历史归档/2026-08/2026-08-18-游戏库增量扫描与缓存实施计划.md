# GameShelf 游戏库增量扫描与缓存实施计划

> **供智能代理执行：** 必须使用 `superpowers:executing-plans` 按任务顺序实施；本项目明确不使用子代理。步骤使用复选框跟踪。

**目标：** 让启动快速核验只检查已入库游戏，并通过持久化分析缓存、全局共享并发和精确失效判定避免重复遍历未变化游戏，同时保留完整扫描发现新游戏的准确性。

**实施状态（2026-08-18）：** 代码、测试、固定文档和生产前端资源均已完成。受影响后端回归 174 项通过；受影响前端 8 个文件共 47 项通过；完整门禁为 Python 714 项、前端 33 个测试文件共 142 项，并通过 Ruff、mypy（104 个源文件）、Vue 类型检查、生产构建和 schema 2 源码冒烟。下方 10 项人工验收均已由用户确认通过。

**架构：** 将目录发现、单游戏分析、缓存决策和并发调度拆成独立单元。`quick` 与 `full` 共用单游戏分析器和全局分析池，但使用不同候选来源与失效规则；分析缓存只验证已有自动结果能否复用，正式主程序和引擎数据仍由 `games` 表保存。前端通过现有后台任务快照展示确定/不确定进度，并在左侧根目录区域管理启动核验和并发设置。

**技术栈：** Python 3.12、SQLite、pytest、Ruff、mypy、pywebview、Vue 3、TypeScript、Pinia、Vitest、Vite。

**固定设计：** [`../../superpowers/plans/2026-08-12-GameShelf-02-游戏库扫描与启动.md`](../../superpowers/plans/2026-08-12-GameShelf-02-游戏库扫描与启动.md)

## 全局约束

- 直接在当前 `main` 工作，不创建分支、worktree 或子代理。
- 开始实施前先确认标题与版本号分离已经位于当前分支；以完成后的 schema 2、扫描载荷和前端契约为基线。
- 不增加 Python 或前端运行时依赖。
- 数据库按开发阶段的新建库处理：只修改 `0001_initial.sql` 的新库结构，不新增 schema 3 迁移、不回填旧游戏、不自动删除 `data/library.db`；用户会在人工验收前自行删除可舍弃数据库。
- `LATEST_SCHEMA_VERSION` 保持 2；发布元数据和 schema 2 冒烟值不因缓存表改变。
- 配置文件可以从版本 3 规范化为版本 4；必须保留现有语言、界面缩放和封面设置。
- `quick` 不发现新游戏；`full` 才发现新游戏和统一核对未观察到的安装。
- 根目录不可访问不能改变其下游戏状态；根目录可访问且单个游戏路径明确不存在时，`quick` 可以把该游戏标为 `missing`。
- 自动分析、缓存命中和强制重新检测都不能覆盖手动标题、版本号、主程序或引擎。
- 全局扫描分析并发允许 1～4，默认 1；单根目录和多个根目录共用一个上限。
- 新建根目录界面默认填入 `Mods` 和 `**/Mods`，不使用 `mod*`；用户可以删除默认规则。
- 每个任务遵循 TDD：先写会因缺少目标行为而失败的测试并运行确认，再写最小实现并运行精确门禁。
- 每个任务门禁通过后提交；不执行 `git push`，除非用户之后明确要求。
